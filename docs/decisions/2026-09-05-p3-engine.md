# 2026-09-05 — P3 decisions: the practice engine

Three places where the docs needed a judgement call, and one design choice that
shaped everything else.

## 1. The engine owns no timers

`docs/05` says all timing uses an injected `Clock`. Taken literally that allows
the engine to call `setTimeout` against a fake clock, but it does not: the host
calls `tick()` from `requestAnimationFrame` and the engine reads the clock.

Two reasons. Cursor and audio must both derive from one timeline or they drift
(docs/05 §3 asks for exactly this), and a 30-second Tempo run becomes a handful
of function calls in a test rather than 30 seconds of wall time. Every timing
assertion in `engineTempo.test.ts` is exact because of it.

## 2. A unison across staves is expected once, not twice

`docs/05` §1.4 asks for a multiset "if the two notes are in different hands",
deduplicated otherwise, with the parenthetical "one key can only go down once".

Those pull against each other: on one keyboard the learner cannot press the same
key twice, so a multiset makes the step permanently unsatisfiable and Wait mode
deadlocks. The pitch is therefore expected **once**, and `PreparedStep` keeps
`noteIdsByMidi` so a single press still colours both printed notes — the
information the multiset was there to preserve, without the deadlock.

## 3. Mastery reports eligibility, not mastery

Part G defines `master` as 97 % at full tempo **twice on different days**. One
run cannot know about another, so `evaluateOutcome` returns `masterEligible`
and the progress store (P7) applies the two-days rule. Calling it `mastered`
here would have been a lie the store then had to unpick.

## 4. Level 1's two rules contradicted each other

`docs/05` §8 gives level 1 "steps only" and "start/end on C". A melody that
wanders and then jumps home breaks the first to satisfy the second — the first
implementation produced a five-semitone leap onto the final note.

The generator now refuses any move it cannot walk back from: before wandering,
it checks that the tonic is still reachable in the notes that remain at one
step each. Both rules then hold by construction, for every seed.

## 5. Bugs the tests found, recorded because each was a real behaviour change

* A duplicate Note-On was counted as a wrong note. `docs/05` §9 requires the
  satisfied set to be idempotent — cheap cables repeat messages, and so do
  learners re-striking a key while holding a chord.
* A note played *early* had no slot to match: slots were opened when the cursor
  reached a step, not when its window opened at `tStep − tolerance`. §3 matches
  within the tolerance either side, so early playing has to find a slot waiting.
* The tolerance boundary was exclusive; §3 writes `≤`, so a note exactly on the
  limit now counts.
* Block triads in generated exercises were written as consecutive notes, making
  a 4/4 bar three times too long. The writer now emits `<chord/>` and excludes
  chord members from the `<backup>` duration.
* Advancing the cursor wiped the colours of the notes just judged. Judgements
  are now kept for the run and the current-step highlight is painted on top of
  them — the same rule P6's Score screen will need.

## 6. What is deliberately not here

* **`velocityHint`** is still unset on ScoreNote (P2 follow-up); the engine
  records the velocity the learner played, which is what the dynamics drill
  needs, but the score's own dynamics are not yet read.
* **Sight-reading level 5+** needs a Markov table trained on a folk corpus at
  build time (P4/P5). Asking for level 5 falls back to 4 rather than pretending.
* **Playback** — sending the non-focused hand to the piano or the speaker
  during a Tempo run (docs/05 §3) — belongs to the Score screen in P6: it needs
  the audio graph and the `tStep` table, and the engine already exposes the
  latter through `prepared.steps`.
