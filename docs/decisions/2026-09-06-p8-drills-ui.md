# P8 — the drills UI: what was decided along the way

Date: 2026-09-06 · Branch: `feat/p8-drills` · Prompt: `prompts/P8-drills-ui.md`

The engine side of drills was built in P3 and never had a face. This phase gave it one, and
in doing so found four things that were wrong rather than merely missing.

---

## 1. The catalog and the engine did not speak the same language

`content/catalog.json` describes a drill the way a curriculum author would: *chords C, F and
G*; *intervals m2, M2, m3, M3*; *progression I, IV, V, I*; *notes from F2 to G5*; *values
quarter, half, whole, rest in 3/4*. The P3 factories take MIDI numbers and semitone counts.
Nothing joined them, so every drill would have run on its defaults and a card saying "C, F and
G" could have asked for B♭m7.

**Decided:** two new files, kept apart on purpose.

- `engine/drills/theory.ts` parses notation — note names (music21's `-` for a flat, because
  that is what the content pipeline writes; `b` is *not* a flat, because `B` is a note), chord
  symbols, roman numerals with case as quality, interval names, note values into bar-filling
  rhythms. It **returns null rather than guessing**, so an unreadable parameter is a visible
  failure and not a silently different drill.
- `engine/drills/fromCatalog.ts` turns an item into a runnable drill, seeded from the item id
  so the same drill is the same on every visit until "Again" asks for a new set.

`tests/unit/drillFromCatalog.test.ts` reads the **shipped catalog**, not a fixture: all 43
runtime drills must build, produce a labelled first prompt, and expect only pitches that exist
on an 88-key piano. A new drill item with a parameter nobody implemented now fails at build
time rather than appearing on the phone as a screen that says "no drill".

## 2. Nothing ever reconnected the piano

Found by writing the first drill test. Every screen that reads MIDI — the Score screen since
P6, the drill screen now — subscribes to `webMidiSource` and assumes something else connected
it. Nothing did. Web MIDI was connected only by pressing "Connect piano" on Settings → MIDI,
by hand, once per page load. With the cable plugged in and permission granted months ago, a
learner opening a drill got silence.

**Decided:** `app/services.autoConnectMidi()`, called at boot. It is gated on
`navigator.permissions.query({ name: 'midi' })` returning `granted`, because in Chrome *every*
`requestMIDIAccess()` raises a prompt and `04` §8 says the app never nags. Granted is the one
case where the call is silent — and also the only case where the answer is already yes. No
Permissions API, or any error, means no auto-connect.

The MIDI mock gained a `permission` option (default `'prompt'`, so existing tests still see a
disconnected app) and the drill tests set `'granted'`, which is what a second launch looks
like. The auto-connect path is therefore covered rather than assumed.

## 3. `el()` was dropping every `false` attribute

The widget helper skipped `value === false` along with `undefined`. So `chip(…, { pressed:
false })` produced a chip with **no `aria-pressed` at all** — which reads to a screen reader as
"not a toggle" rather than "a toggle that is off" — and `data-down: false` on the pedal lamp
wrote nothing. The chips looked fine only because every screen re-set the attribute imperatively
on its first draw.

**Decided:** only `undefined` means "not set". `false` is a value and is written.

## 4. Two catalog items look like duplicates

`drill.technique.five-finger-rh`, `five-finger-lh`, `ht-holds`, `position-shifts` and
`drill.pattern.lh-accompaniment` carry `drill.kind` values (`five-finger`, `arpeggio`) that are
*generated-exercise* kinds, not runtime drill kinds — and the same patterns already exist as
generated notation (`exercise.five-finger.c-major.right` and friends, with `.mxl` files).

They are implemented as call-and-response — demonstrate the pattern, play it back — which is a
real drill and better than a dead row. **But they are probably content mistakes**, and the
owner should decide whether to delete them in favour of the notation, or keep them as an
ear-and-hands version of the same thing. Flagged rather than silently removed.

## 5. Smaller decisions

- **The staff is hand-drawn.** OSMD parses MusicXML and lays out a system — roughly 100 ms and
  400 kB to draw one crotchet, on a screen whose whole point is that the next card appears the
  instant you answer. VexFlow is a smaller version of the same trade. A note on a staff is five
  lines, an ellipse, a stem and up to three ledger lines: 60 lines of SVG, exact, and tested by
  geometry rather than by eye. The clefs are the Unicode musical symbols, which are in the
  Android system font and cost nothing to precache.
- **Spelling follows the drill's own names.** `NOTE_NAMES` in the engine says C♯ and F♯ but E♭,
  A♭ and B♭, so the staff puts E♭ on the E line. Drawing it as D♯ would teach the wrong thing
  quietly and repeatedly. A unit test pins it.
- **Ear cards show nothing.** Printing the interval name on screen would answer the question.
  The card is a headphone glyph and a "Play again" button.
- **The prompt audio is the piano.** Hearing a sine wave and answering on a piano is a
  different task from the one the drill is for.
- **A backing track can neither pass nor fail.** `05` §7 says it judges nothing; it is recorded
  as time spent, with `accuracy: 0` and no pass.
- **`ui/openItem.ts`** now decides where an item opens — PDF viewer, drill screen, Score screen,
  or nowhere (an import placeholder). Four screens were each making that decision separately
  and would have drifted the moment drills got a route of their own. The **file wins over the
  drill block**: a generated exercise carries `drill: { kind: 'scale' }` to record how it was
  made and is still a score.
- **Sight-reading is scored on the first attempt only** (`05` §7) and forced into Tempo mode:
  waiting for each note is not sight-reading, it is decoding. A fresh exercise is generated on
  each open; "Again" on the summary re-runs the loaded one, which is what §8 means by retrying
  a failed sight-read identically.

## 6. Two P7 tests encoded the old limitation

`plan.spec` asserted that "Drill it" opens `#/score/…` and `today.spec` that starting the
session does. Both were true only because a drill had nowhere else to go, and both now assert
the routing `ui/openItem` actually performs. Worth naming because a test that passes for the
wrong reason is how a fixed bug comes back.

## What is not done

- **The rhythm drill has no count-in and no metronome.** It judges onsets against a pattern
  whose clock starts when the card appears, so the learner has to start on their own. A count-in
  would make it a fairer test; it needs the drill's clock and the metronome's to be the same
  one, which is engine work rather than screen work.
- **`ear-progression` is judged as one long ordered sequence** (the P3 decision, unchanged): the
  learner plays every note of every chord in turn. Playing the chords *as chords* would need the
  drill to know where one ends and the next begins, which means a timing rule the framework does
  not have yet.
- **No drill uses the microphone.** The framework takes any `InputSource`, and `MicSource` is
  one, but the drill screen subscribes to MIDI and the screen keys only. Worth adding when the
  owner has the mic path set up on the phone.
