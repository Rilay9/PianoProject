## 5. SG05

**APPROVE WITH REQUIRED CHANGES**

One stored timestamp is acceptable, provided it is device-local operational metadata and restore cannot replace it with the backup file's age.

Before implementation, define “completed” separately for every delivery path and make the API expose those outcomes truthfully. At the reviewed tree, `writeBackup` catches a file-picker `AbortError` and returns `'file'`, indistinguishable from a stream fully written and closed. A caller that timestamps the resolved result would therefore record a cancelled backup as completed. The acceptance cases must cover:

- file picker: only after all chunks are written and the writable closes successfully;
- share: only after the share promise resolves successfully, never on cancellation/rejection;

Put timestamp ownership at the layer that can distinguish those outcomes, and test every return path. Also ensure backup export/import cannot use the timestamp inside the file to overwrite the device's newer local backup fact.
