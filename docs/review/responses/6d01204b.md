# Response to `6d01204b`

## Verdict

**APPROVE**

U125 found the actual mechanism, refuted both current-seam suspects, fixed the U66 contract rather than loosening the browser test, and kept the change local to the engine. The timing trade is accepted as implemented. **Do not introduce a tighter independent miss-display bound.**

The important distinction is that the one-second figure is not a new visual-delay policy. It is the engine's already-existing timestamp-trust boundary: while an input stamp is still trusted, a note delivered late by a stalled main thread can still truthfully be a note that was played inside the window. The engine has no separate fact saying the browser's queued input has drained. Marking the note missed earlier would therefore reintroduce the same false-negative class U66 exists to prevent.

## 1. The mechanism and fix are accepted

The evidence is discriminating enough:

- the hold never lets an already-ended window survive beyond the existing `STAMP_TRUST_MS` rule;

The seven red-first unit cases cover the newly identified boundaries: a second stall, a window ending just after the stalled tick, the exact interval edge, release after the renewed hold, the stamp-trust cap, and the ordinary unstalled case. That is the right level of proof for the mechanism.

The throttled browser counts support rather than define the contract. The fix takes the valid-precondition judging failures from 28/153 on the head to 1/148 in the main comparison; the later logged residuals are deliveries beyond the one-second trust bound. The one unlogged residual in the earlier set remains inference rather than proof, but it does not justify reopening the mechanism given the unit boundary proof and the logged residual set.

## 2. Question 1 — accept the delayed miss under repeated stalls

**Accept it. No tighter bound.**

There are three different cases and they should stay distinct:

1. **No stall:** a miss is marked on the first ordinary tick past the inclusive note window, exactly as before.
2. **One/few stalls:** the engine delays closing only through the short post-stall span needed to let already-queued input arrive.
3. **Pathological repeated stalls:** the uncertainty can be renewed, but only while a stamp that could prove an on-time strike is still trusted; once the window is more than one second behind, the hold stops and the miss is committed.

On a device whose every tick stalls, showing a red miss earlier than that without additional queue-drain information would choose display immediacy over scoring truth: the app could paint a note wrong and then receive a still-trusted timestamp proving it was played in time. U66 explicitly rejects that outcome.

So the accepted invariant is:

> **Do not finalize a miss while the engine still has a principled reason to believe a trusted, already-stamped in-window note may be queued. Once that reason expires, finalize it immediately.**

The implementation does that with the current contracts; there is no need to invent another duration.

## 3. Do not turn the pathological case into a new UI lane now

The phrase “a red mark can appear up to a second late” is a worst case under repeated main-thread stalls, not ordinary Score behaviour and not a reason by itself to add a pending indicator, spinner, or new Score state.

If a real phone later reproduces repeated stalls severe enough that delayed feedback itself confuses a learner, that is new product evidence. At that point the right question would be how to communicate temporary scoring uncertainty without lying about the result — not how to shorten the engine's truth window. No row is opened from the artificial-throttling case alone.
