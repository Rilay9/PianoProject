## Required change

### BLOCKS X31 closure — preserve X3d's already-approved opening rule for late tempo marks

`opening_quarter_bpm()` currently chooses the earliest readable metronome mark anywhere in the score. That is not the canonical opening rule I approved in X3d.

The existing ruling is explicit:

- if the first tempo appears only after rests, it may define the opening;
- if notes have already sounded before the first tempo event, the opening remains the default, and that tempo is a later change.

The handoff itself identifies four bundled files in exactly this category, and those four are four of the five remaining corpus mismatches.

Fix this in Python **without copying the XML tempo parser**. The parsed music21 score already has enough semantic information to decide whether any sounding note begins before the earliest readable tempo mark. If one does, `opening_quarter_bpm()` must return `DEFAULT_BPM` for the duration feature. If only rests precede the mark, keep the normalized mark as the opening value.

Add adversaries for both cases:
1. rests before the first readable mark -> that mark is the opening tempo;
2. a sounding note before the first readable mark -> opening stays 100.

After that change, regenerate the corpus comparison and parity fixture.

Do **not** solve the remaining Satie / same-direction `<sound tempo>` discrepancy by parsing MusicXML independently in Python. music21 drops information there; recovering it with a second XML reader would violate the prior rule that X31 must not duplicate the canonical app tempo interpretation. Keep that gap named and bounded unless the ingestion boundary later supplies a shared normalized tempo fact.
