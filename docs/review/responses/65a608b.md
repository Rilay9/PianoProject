## 3. ACCEPT — L87 row-as-checkpoint shape, with one later storage caveat

For **correctness**, the row-as-its-own-checkpoint shape is accepted.

The tests cover the important invariants: competence/rung truth survives pruning; provenance and evidence versions survive; contrary recent evidence can still change current state; `notShownRecently` remains live; no mastery boolean/checkpoint verdict is stored; backup/restore survives; and the real `recordRun` tidy path invokes the prune.

There is, however, a narrower storage issue the handoff understates:

```ts
export function holdsEvidence(row: SessionRow): boolean {
  if (row.lessonId !== undefined) return true;
  return Array.isArray(row.evidence) && row.evidence.some((result) => result.kind !== 'refusal');
}
```

This preserves **every** old rung-judged row, not merely “one compacted row per run that established something.” `rungState` treats any judged row as enough to make a rung `in progress`, while only some judged rows satisfy requirements, so the conservative predicate is understandable. But it means the nominal session cap can become a soft cap for curriculum-directed practice and the number of retained rows can grow indefinitely.

**Disposition:** LATER WAVE / storage-compaction work, not a C7 correctness blocker. Do not “fix” it by deleting old judged rows with an ad-hoc `passed` test. A future bounded solution must preserve the exact rung/evidence semantics, potentially with a minimal semantic witness/checkpoint rather than another competence state. Record this explicitly so H does not assume `MAX_SESSIONS` is a hard bound after C7.

## 4. REQUIRED NOW — L98 first-open carry-over race

The reported behavior belongs now, not in X.

The current readers do things like:

```ts
const [curriculum, items, rows, plan] =
  await Promise.all([loadCurriculum(), allItems(), rungRows(), getPlan()]);
```

while the one-time C5 carry-over can update the same plan asynchronously. A read that resolves with the pre-carry-over row can therefore build Today/Skills from stale learner state until reload even though the persisted plan has already changed.

That violates the governing rule that Plan, Today and Skills consume one authoritative learner state. It is not merely a presentation race.

**Required small follow-up before D0:**
- make first-use carry-over/migration part of the authoritative plan-read readiness boundary, or otherwise serialize it so a consumer cannot receive the pre-migration plan after the migration has committed;
- do not add per-screen retries or screen-specific “reload after migration” patches;
- prove Today and Skills on first open read the carried plan without reload;
- prove repeated reads remain idempotent and no later stale `getPlan` completion can overwrite memory after `updatePlan`.

The last point matters because `getPlan()` assigns its asynchronous DB result into the shared `memory`; this should be made race-safe at the store boundary rather than patched in each consumer.

**Status:** BLOCKS D0 DISPATCH only until the small fix-forward is green.
