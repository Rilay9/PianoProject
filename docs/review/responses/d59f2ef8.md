Implementation HEAD: d59f2ef8. Seam reviewed: G1d repertoire retention consumes project lifecycle.

## Verdict

APPROVE WITH ONE REQUIRED CHANGE

The intended G82 change is correctly implemented at the retention path:

- Today reads `allProjects()` and passes the rows into `buildSession`.
- The session does not open the project store itself.
- `review()` resolves the project through `projectIn` using the piece/material identity.
- `paused` and `retired` suppress "Keeping this piece playable".
- Other project states and absence of a project preserve the previous retention behavior.
- The lifecycle remains intention truth, not evidence, skill state, encounter history, or progress.
- The guard correctly makes the session a project reader while keeping the sheet as the actor.

That part satisfies the prior ruling.

## REQUIRED CHANGE

BLOCKS G1d closure: a paused/retired piece can still be automatically offered through the repertoire fallback

The handoff's constructed probe exposes a real contradiction, and the implementation confirms the mechanism.

`review()` consults project lifecycle, but `repertoire()` does not. Its fallback explicitly orders learned pieces into the pool and can therefore turn the same paused piece from:

«Keeping this piece playable»

into:

«A piece you know — for variety»

The wording is gentler, but the architectural fact is the same: the app automatically selected music the learner explicitly paused or put away.

That violates the lifecycle truth G1b established.

Fix the ownership, not only that sentence. The session should have one session-owned automatic-project eligibility rule for piece selection, backed by the project rows Today already passes in. `paused` and `retired` should be unavailable to automatic repertoire selection regardless of which automatic slot/reason found the piece.

Do not scatter independent `projectIn()` policy reads across each chooser. Centralize the project lookup/predicate in the session and consume it from retention and repertoire selection. Manual Library access, the project sheet, learner-selected opening, and historical facts remain untouched.

Add the adversary already found by the builder: in a thin catalogue, a paused learned piece must not disappear from retention only to reappear in the repertoire slot.

## Answers to the three questions

### 1. Silent or say why?

Keep it silent.

Today does not need a synthetic "not showing X because you paused it" line. The learner's explicit state already lives in the project sheet and Progress. Adding explanatory inventory for every intentionally omitted piece would turn Today into a report of things it did not choose.

Silence is correct once the selection semantics themselves are correct.

### 2. What if the learner pauses it after Start session?

Keep X1's frozen session snapshot. Do not recompose the running session.

But an explicit learner lifecycle action is not new evidence. It is a current instruction about the music. For a not-yet-started automatic activity, `paused` or `retired` should act as a live veto at the activity boundary.

The later X/session-run seam should:

- leave the persisted composition/history intact;
- when the pending activity is about to start, detect that the project was paused/retired;
- mark that activity skipped/adapted with the explicit project-state reason and advance;
- not silently substitute another activity by recomputing the whole session;
- not interrupt an activity already underway.

That is a follow-up to the session runner contract, not a reason to rebuild today's card whenever project state changes.

### 3. Should A piece you know skip paused and retired too?

Yes. This is the required G1d change above.

A lifecycle state cannot mean "do not automatically keep this piece alive" in one slot while another automatic slot freely picks the same piece because it is learned.

The automatic/manual boundary is the relevant distinction, not the prose reason attached to the slot.

## Classification

- BLOCKS G1d closure: automatic repertoire selection must honor `paused`/`retired`, with one session-owned lifecycle predicate rather than another local special case.
- CONSTRAINS X/session follow-up: a pause/retire after session start is a live veto on a pending automatic activity, implemented as a recorded skip/adaptation without recomposition.
- APPROVED AS BUILT: retention suppression itself, identity lookup, Today passing project rows, the revised one-reader boundary, and silent omission.
- PRUNE/MERGE: do not create separate lifecycle policy in `review()`, `repertoire()`, and the runner. One session-level interpretation of automatic eligibility should own it.
