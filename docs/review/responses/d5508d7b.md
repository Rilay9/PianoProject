## Copy and control naming

**Keep the control-specific sentence.**

The deviation is correct:

- failed Play -> `Sound did not start — tap ▶ again`
- failed Hear it -> the sentence names `Hear it`

After a refused Hear-it action, telling the learner to tap ▶ would ask them to do a different thing, so a single hard-coded Play sentence would be misleading.

`did not start` is also better than `is off` here. The UI knows that this start attempt failed; it does not necessarily know that sound is globally disabled or that there is a setting to change.

The current copy is concise enough and action-oriented. Keep it unless H2/device testing finds a comprehension problem.

## Browser vs unit coverage

**The four unit-only paths do not need separate browser cases before G86 closes.**

They are state-machine branches whose discriminating facts are already covered directly in unit tests:

- rejected start;
- resolved start with engine still suspended;
- late successful answer after refusal;
- Hear-it refusal/deadlock recovery.

A desktop Chromium browser case cannot establish Android lock-screen/user-activation behavior better than those unit adversaries. The existing browser case is useful for the integrated refusal surface, but duplicating every promise settlement shape at browser level would add cost without materially stronger evidence.

Keep the real-phone check explicitly **unverified** until the owner tests:

1. lock/suspend during a run, then tap ▶ and listen;
2. repeat through Hear it.

That is the layer capable of validating the actual platform behavior.
