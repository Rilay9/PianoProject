# Reviewer response — G1b implementation `536d9bc2`

Implementation HEAD: `536d9bc2`. Seam reviewed: **G1b repertoire/project lifecycle**.

## Verdict

**APPROVE**

The implementation preserves the approved truth boundary. A project is the learner's stated relationship with a piece, not evidence of contact, competence, rung completion, or today's session policy. The version-9 `projects` store, `projectStore` writer, project sheet, Progress door, and Stage 9 presentation all consume that one truth without making it stand in for another layer.

The required invariant is now concrete in code and tests:

**Encounter history says what was met. Evidence says what was measured. Skill/rung state says what the evidence supports. Project lifecycle says what the learner intends. Session state says today's plan. One layer may inform another; none substitutes for another.**

### Acceptance findings

- **Store/state machine:** one project row per known material identity, conservative `id:<itemId>` fallback, append-only transition history, optional learner-authored goal/problem/sections, and no migration that manufactures projects from old progress.
- **Learner-driven transitions:** `applyProjectAction` is reached through the project sheet; `OFFERS` is the transition contract and disallowed actions are refused. No timer, run, progress update, or evidence event advances lifecycle state.
- **No manufactured evidence:** the performed action records only the learner-stated project fact/date. The guard cases hold encounter, session/run, progress, rung and skill truths unchanged.
- **Identity:** known material can unify duplicate catalogue identities; id-only fallback does not guess equivalence. Rebuilding the same catalogue id's file continues to find that id's project rather than creating a second project.
- **Doors/presentation:** the finish sheet is the first door and Progress the second. Stage 9 reads project lifecycle for presentation and suppresses the misleading rung-count UI without changing `rungState` or using project state as evidence.
- **Pause/retire/refresh:** pause and retire erase nothing; refreshing does not manufacture novelty.

## Answers to the four build questions

1. **Retention after Pause / Put away:** once session composition begins consuming project lifecycle, `paused` and `retired` must suppress automatic repertoire-retention offers. Offering “Keeping this piece playable” after the learner explicitly paused or put away the project contradicts the intention truth that G1b now owns. This is **CONSTRAINS NEXT BRIEF**, not a G1b defect: G1b correctly did not change the existing session reader before this lifecycle contract was accepted. `maintaining` remains the positive retention state; `refreshing` is active work, not novelty.
2. **I performed it from Learning:** keep it. A learner may perform a piece without first choosing the app's polishing state. Because the action is learner-stated and manufactures no run/evidence, forcing a polishing transition would add an unsupported lifecycle rule.
3. **Songs only:** keep it. Projects belong to whole pieces. Excerpts/phrases/drills/exercises are material or activities; a project's passages belong in its sections rather than becoming independent repertoire projects.
4. **Same catalogue id rebuilt to new material bytes:** keep the conservative fallback as built. The same id may recover its existing project; a different id must not be guessed equivalent merely because names or surrounding metadata resemble one another.

## Sequencing

G1b is closed. G1c may be judged against this accepted presentation truth. X/session composition may consume project lifecycle subject to the retention constraint above: automatic retention must not override `paused` or `retired`.

No unrelated seam is blocked.
