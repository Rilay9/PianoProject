# Response to `handoffs/71730e65.md`

Reviewed the two pre-build briefs at implementation/planning HEAD `71730e65`. This response applies the current holistic-reassessment correction: an old convergence disposition is evidence that a problem was once identified, not authority to preserve the cluster's proposed solution shape.

## CL16 — sight-reading walk version 3

**REJECT**

The problem is not that the brief lacks tests. It is that most of the proposed phrase-shape changes are still defined by improving the generator's own scoring/distribution proxies rather than by a current learner-facing or source-backed sight-reading requirement.

The current code confirms the premises the brief cites: the melodic move is drawn flat up to `maxLeap` (`app/src/engine/sightReading.ts:869–884`); the rest draw excludes only the last slot of the last bar (`:792–799`); the scorer calls final-bar, consecutive and beam-splitting rests `bad` (`app/src/engine/sightReadingScore.ts:581–603`); and the distribution suite deliberately carries low `unitsOne` bounds at levels 6–7 and a named level-1 duplicate cost (`app/tests/unit/sightReadingDistribution.test.ts:398–479`). Those facts establish how the current model behaves. They do **not** establish that the correct product change is to harden the scorer's preferences into generator rules.

In particular:

- S34 proposes biasing the walk because `unitsOne` is low. `unitsOne` is a generated-shape metric, not evidence by itself that a learner receives bad sight-reading material.
- S35a would turn `restFacts.bad` from a soft candidate-scoring preference into a hard generation exclusion. That is exactly the kind of proxy escalation the convergence reset is meant to prevent: a heuristic that helped rank candidates becomes a product invariant merely because it exists.
- S35b adds a bar-long arrival cell principally because the current arrival scorer rewards that shape. A long final note may be musically/readingly sensible, but the score function is not sufficient evidence to change the rhythm vocabulary at levels 2–7.
- S35c is already honestly a measurement/stop question and may remain read-only; there is no reason to manufacture a version-3 change if the current duplicate rate is the natural consequence of the deliberately small level-1 space.

G37 is different. The left-hand facts can express objective alignment with already-taught material and metre: the current pattern table fixes `broken` and `walking` at quarter-note units while `buildLeftHand` fills the bar from that fixed unit (`sightReading.ts:912–963`), and the brief's register claim can be measured against the accompaniment exercise instead of inferred. Those are legitimate correctness/alignment questions.

**Required path forward:** do not dispatch CL16 as one `version 3` implementation lane. Replace it with two differently scoped pieces:

1. **A narrow G37 correctness/alignment seam** may proceed after the register difference is actually measured. It may correct left-hand register and compound-metre unit only where the existing taught-accompaniment/metre contract entails the correction. It must not absorb phrase-shape tuning.
2. **A read/design packet for S34/S35** must first establish the learner-facing sight-reading problem independently of `sightReadingScore.ts` and the distribution bounds. Use representative current version-2 pages across the affected levels/rungs and the existing lesson/reading contract; where a proposed rule is musical rather than mechanical, cite a source-backed reading principle or leave it explicitly unverified. The packet should answer which current pages are actually unsuitable and why. Only then choose whether the remedy is a different walk, a rhythm-palette change, a rest-placement rule, a scorer change, or no change.

A version number is created only when a justified learner-facing generator behaviour actually changes. Do not create “v3” as the goal and then search for enough metric improvements to fill it.

**Stop condition:** if the representative current pages do not establish a material learner-facing problem for S34/S35 beyond the scorer's preferences, close/park those rows rather than tuning the generator to its own tests.

## R23 — one strong application replaces the three-song floor

**APPROVE WITH ONE REQUIRED CHANGE**

The product direction is sound: replacing a raw three-song quota with one genuinely useful application experience is a real simplification, and the current code does contain the count rule in parallel build/app/report paths. The current `thin_lesson_errors` uses a raw `len(songs) < min_options` gate only where a rung actually asks for songs (`tools/content/validate.py:631–667`), while `write_needs` currently lacks that same `required_songs` gate and can therefore report a song shortfall where the rung asks for none (`validate.py:1951–1993`). Fixing that disagreement in the same rewrite is appropriate.

The required change is the definition of **strong**.

`claims.py::status_of` proves a narrower fact: for a measurable claim, an item's measured demands establish the wanted opportunity at the configured density; otherwise the opportunity is incidental/absent/unmeasured/runtime (`tools/content/claims.py:252–330`). Runtime eligibility independently asks whether a candidate provides established opportunity and also applies learner-coping and teaching-use admission rules (`app/src/curriculum/eligibilityCore.ts:202–320`). Therefore **“established for at least one lesson claim” is not sufficient to mean “one strong application experience.”**

As drafted, the gate could count an item that establishes a peripheral claim while missing the concept the application is supposed to reinforce, and it could count generated music/excerpts whose measured opportunity is established even though the runtime teaching-use gate would not admit them for teaching. The brief itself acknowledges that `established` is a notation/detector fact rather than a pedagogical judgement; the validator must not immediately rename that narrower fact `strong` and make it curriculum truth.

1. **Required change — separate application eligibility from opportunity measurement.** Before rewriting the validator, the read-only report must identify, for every rung that currently asks for a song/application run:
   - what specific lesson/rung claim the application is meant to reinforce (not merely “any claim on the lesson”);
   - whether each candidate establishes that target opportunity using the existing measured classification;
   - whether the candidate is otherwise admissible for teaching under the existing teaching-use/source truth where that gate applies;
   - how runtime/creative/ear tasks that cannot be statically classified are represented without falsely passing or failing them.

If the repository already has one canonical composition of those facts, reuse it. If it does not, **stop after the report and return that model gap**; do not duplicate `eligibilityCore.ts` in Python, add a new application-strength field, or weaken “strong” to “establishes any one measurable claim” just so the validator can be rewritten in this lane.

The `write_needs` / `lessonShortfall` missing `required_songs` gating may still be fixed as a bounded consistency correction because the other readers already encode that distinction. But the count-to-quality conversion does not land until the application criterion is honest.

Also narrow item 8: changing the rule may report rungs with no qualifying current application; that report is valuable. Do **not** turn R23 automatically into a repertoire/content-acquisition project. Existing options may be kept/reclassified when evidence supports it; genuinely missing material routes through the source chooser (`learner need -> requirements -> best source -> validate`) rather than being added merely to make the validator green.

**Acceptance:** the new build gate can explain why one candidate counts in product terms—what application target it serves, what measured opportunity supports that claim, and why the app is willing to teach with it—without using “established” as a synonym for “strong.” The build gate, Diagnostics, learner-facing shortfall and ladder report then share that same truth.

**Stop condition:** if no canonical way exists to determine the application target or to combine opportunity with teaching-use truth without duplicating runtime policy, keep the raw three-song rule retired conceptually but do not replace it with a false precision; return the missing model for a small design decision first.
