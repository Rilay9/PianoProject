# Reviewer response — G96a (Entry 179)

## Verdict

**APPROVE**

G96a closes the required G99 correction on its own boundary. The PDF detail sheet no longer states either of the two false things that triggered the fast path, and the implementation leaves the catalogue’s shared `type` field alone.

## Question 1 — `PDF` or `Imported PDF`

Keep **`PDF`**.

`Type` should answer what the object is. The `Source` row immediately below already answers where it came from with *Imported by you*. `Imported PDF` on the Type line would repeat provenance inside the type value and make the two rows less distinct.

Do not change `CatalogItem.type` to make this display happen. The current presentation-only branch is the right boundary for G96a.

## Question 2 — the guessed-from-the-music guard

The positive guard is correct: **where the app actually estimated a MusicXML import from the notes it read, the specific sentence is truthful and should remain.** The test that preserves that case is valuable.

But `item.kind !== 'pdf'` is **not** the general semantic boundary. The second read proves that plain MusicXML/MIDI imports can reach Details with the default level and `levelSource: 'estimated'` even though no estimate ran, and the accompaniment-lab build can carry the same source label without this estimator having read the item’s notes.

That does not reopen G96a: its required change was the PDF false claim, and that is fixed. It does constrain G102. G102 must replace the broad presentation assumption with level-provenance truth: the specific guessed sentence is allowed only where the stored provenance can support “the app estimated this from the music”; otherwise the wording must be neutral or accurately name the source.

## Question 3 — G102 shape

**Split by truth/owner boundary, not by every observation.**

Keep **G102 as one P1 level-provenance row** covering the facts that are actually one problem:

- a plain MusicXML/MIDI import can receive the default level without an estimator run yet read as guessed from the music;
- the accompaniment-lab build can be marked estimated without that claim being true;
- the Edit sheet can save an owner-entered level without changing the source to a human/judged source;
- the stored provenance can name an estimate that never ran.

Those are one semantic defect: `levelSource` currently conflates a computed estimate, a placeholder/default, and a human-entered judgement, and learner wording trusts the conflation.

Do **not** bury the PDF’s `Hands: Hands together` under G102. That is a separate learner-facing metadata truth: the app does not know the hands from a PDF. Record one separate row for that fact.

Do **not** create rows yet for the `item.type` appearances in the Songs filter / Today swap / Skills list merely because the field is shared. First establish the actual learner-visible false behavior at each consumer. The Songs-filter behavior is a real taxonomy question; the two lists were not yet verified. Keep those as observations until the read proves a concrete wrong outcome, then attach them to the existing import/type cluster or create one row only if the product truth is genuinely new.

## Boundary check

The implementation at `showDetail` changes exactly the two G99 learner-facing statements:

- PDF type is rendered as `PDF` without mutating the catalogue type used elsewhere;
- a PDF’s default/estimated level gets neutral wording;
- the known true MusicXML-estimator case remains pinned by the guard test.

The broader level-source model is intentionally left to G102 rather than being smuggled into this fast-path correction.

## Disposition

G96a may close. G102 remains P1 with the narrowed level-provenance scope above; PDF hands is separate; unverified type/list observations do not multiply into rows yet.
