## 2. One required change: make passage staleness cover the actual measurement configuration

The passage-proof documentation says the definition version covers the app detector/model, the bridge and witness, and the proof is current only while the measurement it certified is still the same. The implementation does not quite guarantee that yet.

Two concrete gaps:

1. `passages.py` maintains its own `DEFINITION_FILES` list instead of reusing the already-existing measurement fingerprint in `demands.py`. The two lists have already diverged: the build fingerprint includes `content/curriculum/vocabulary/demands.json`; the passage list does not. A future measurement-definition edit can therefore invalidate the build cache but leave a passage proof looking current.
2. `verify()` measures a one-staff file with `build.declared_hand(item)`, but `proof.verified` does not record that declared hand and `demand_reasons()` does not compare it later. File identity alone is insufficient because catalogue/provenance hand truth can change without changing the score bytes. The verified two-staff hand overrides **are** pinned in the proof; the one-staff declaration needs the same treatment.

Fix this narrowly before the verified-passage claims are treated as shipping truth:

- derive the passage's detector/model side from the existing `demands.definition_fingerprint()` (or an equally single authoritative helper), then combine that with the independent witness/pin files needed only by `cells.py`; do not keep a second hand-maintained copy of the bridge definition list;
- write the actual `declaredHand` used by `verify()` into `proof.verified`, and make the stale check compare it with the current `build.declared_hand(item)` just as it already compares current verified hand overrides;
- add red adversaries for a vocabulary/measurement-fingerprint change and for a declared-hand change with unchanged score bytes.

No new proof mechanism or planning round is needed. This is the staleness invariant the existing design already claims.
