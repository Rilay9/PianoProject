## Verdict

**APPROVE WITH ONE REQUIRED CHANGE**

### BLOCKS NEXT BRIEF — define the ladder's complete, nonrecursive fact path before G2 dispatch

The proposed `transferReading(skill, established, run)` needs the stored relationship and the skill's establishing contexts. At this HEAD, `ladderState` accepts only `Evidence[]`; `EvidenceContext` has material, intent and first contact, but no relationship. `RunHeader.relationship` exists only on transfer-offer runs. Ordinary supporting runs may also demonstrate generalisation, and a legacy or D4 race row may have no relationship. Meanwhile `shownOnRecords` in `curriculum/transfer.ts` calls `ladderState` repeatedly to infer its establishing records. Making the new ladder call that helper would form a recursion, and simply consulting `run.relationship` would silently exclude ordinary runs.

Before dispatch, amend the brief with one explicit path that:

1. supplies each ladder attempt with its own run header and context facts, including an honest unknown when relationship or first contact cannot be reconstructed;
2. identifies establishing contexts from the ladder's replay state without calling a helper that calls `ladderState` back;
3. states how a non-offer supporting run obtains a measured relationship to those established contexts, without treating a current catalogue item as the identity of a historical run or using declared `differsOn` as measured evidence;
4. gives both promotion and challenge protection the same fact path, with the protection threshold permitted to differ; and
5. tests an ordinary new-context success, a transfer-offer success, a legacy unknown, and two failed unfamiliar attempts that should be protected without recursive calls or fabricated facts.

This is a contract and dependency correction, not a request for a broad new framework. G1a remains the prerequisite; its separate post-build gate still applies. X1 must wait for G2's accepted contact input and F2a.

# Reviewer response — G1b pre-dispatch brief `a96395d`

Seam reviewed: **G1b repertoire lifecycle**. G2 remains governed by the earlier section above.

## Verdict

**APPROVE.**

The lifecycle is correctly separated from encounter history, evidence, rung state and session state. A project row answers the learner's intentional relationship with a piece; it does not infer that relationship from runs and it does not become another competence truth.

The proposed `projects` store is an appropriate separate state machine:
- one row per material identity where identity is known;
- id-only fallback where it is not;
- append-only state history;
- optional learner-authored goal/problem/sections;
- no write to encounter, evidence or `ProgressRow` as a side effect.

The important invariant remains:

**Encounter history says what was met. Evidence says what was measured. Skill/rung state says what the evidence supports. Project lifecycle says what the learner intends to do with the music. Session state says today's plan.**

## Question 1 — should any lifecycle state be app-driven?

**No. Keep every lifecycle transition learner-driven.**

Do not automatically drift `maintaining` to `paused`, or infer `learning`, `polishing`, `refreshing` or `retired` from elapsed time or run history.

The app may later *suggest* an action based on history, but the stored lifecycle changes only when the learner chooses it.

`I performed it` → `maintaining` is acceptable as a learner action. If the project row records a date/reason from that action, it remains a learner-stated project fact. It must not manufacture a `performed` encounter, performance run, competence result or evidence event.

This distinction should be pinned by a test.

## Question 2 — Stage 9 / L86 split

**Yes.**

The Stage 9 learner-facing page may read project lifecycle rather than count runs, while the Stage 9 curriculum data remains owned by F.

Do not make `rungState` or session progression treat the project states as requirements. The page is replacing a misleading rung/progress presentation, not creating project-state evidence.

Acceptance should explicitly prove:
- the Stage 9 page shows project state / “not started”;
- no “x of y met” or rung-completion claim is shown there;
- changing a project state changes only that project presentation;
- the same action changes no rung state, evidence, eligibility or skill state.

## Question 3 — first door

**The finish sheet is a sufficient first door. Do not hold G1b for the Library integration.**

The finish sheet is the natural moment for “what next with this piece?” and proves the lifecycle independently of X3/Library presentation.

After X3, the Library may expose the same project state and open the same sheet, but that should consume the one `projectStore` truth rather than become part of the G1b acceptance boundary.

Progress is also an appropriate second door because it is already where long-term activity is reviewed.

## Constraints

1. **Identity migration must fail conservatively.** A project keyed by known material identity may unify renamed/duplicate catalogue ids. An id-only project may not be guessed to be the same piece as another id later.
2. **Retire/pause never erase facts.** No encounter, run, evidence, progression, project history or section note is deleted.
3. **Refreshing is not novelty.** Bringing back an old piece may enter `refreshing` while encounter history still says familiar.
4. **Project state is not session policy yet.** X may later use goal/problem/sections to compose work, but G1b does not make those fields choose anything.
5. **Stage 9 presentation must not mutate the existing rung/evidence model merely to suppress misleading counts.** If that page cannot be made truthful without changing `rungState`, stop that Stage 9 subpart as the brief says.

G1a and X3 are now closed on the branch, so G1b may dispatch.

G1b post-build review is required before X/session composition begins consuming project lifecycle as an input. No unrelated lane waits on it.
