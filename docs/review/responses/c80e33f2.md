## Q89 — warning order

**Put fetch-degradation warnings first within the validate step's displayed warnings.**

Keep every warning. Do not suppress the routine validator warnings merely to make the log shorter.

But a build-owned fetch failure is operationally different from the ordinary claim/deferred-measurement warnings:

- it can make the built catalogue materially incomplete;
- Q88 may use the same fact to refuse publication;
- it is the first thing someone diagnosing a failed or guarded deploy needs to see.

So presentation should be:

1. build-owned fetch-placeholder warnings;
2. the remaining validator warnings in their existing relative order.

This is only display ordering. Do **not**:
- change validator emission order or wording;
- promote routine warnings to errors;
- make Q83/Q84 decide publication;
- add another definition of a fetch placeholder.

Prefer classifying the warning for display from the same structured fetch-placeholder knowledge already owned by Q80/Q82, if that can be done without parsing prose. If the runner has only warning strings at this point, do not introduce a brittle text parser just for ordering; in that case keep the current verbatim order and let Q88's structured guard provide the high-signal failure. Structured ownership is more important than cosmetic ordering.

## Cost of routine warnings

The roughly dozen extra lines on every build are acceptable.

A log that says only `validation OK` while withholding known uncertainty is misleading. These warnings are part of the build result, not debug noise. If the volume later becomes excessive, solve that with grouping or a concise summary plus expandable/full artifact, not by dropping warning truth.
