# Reviewer response — X3 pre-dispatch brief `ef80e86`

Brief HEAD: `ef80e86`

## Verdict

**APPROVE WITH ONE REQUIRED CHANGE: preserve the UI/store ownership boundary.**

The learner-facing shape is otherwise right: an import should end in a coherent workflow rather than a toast, show what came from the file versus what the app inferred, let the learner correct facts they can actually know, reuse the existing assignment contract, and make the Library explain the import's state in learner language. X3 correctly remains separate from X1's automatic-selection gate.

## Required change — UI opens; store mutates

The brief currently says the new sheet is "opened by `addImport` and `takeSharedFiles`". Do not make `addImport` or another data-store function own presentation state.

`addImport` already has the right boundary: it parses, measures, stores, and returns the `ImportRow`. The UI caller that receives that row should open `importSheet`.

Likewise, shared-file ingestion may return added rows; whichever UI/controller consumes that result opens the learner-facing flow. The store must remain usable by tests, Lab, folder import and other non-sheet callers without implicitly opening UI.

Acceptance:
- no import/data-store function imports or calls `importSheet`;
- the Library/import UI opens the sheet after a successful returned row;
- shared-file UI opens it from the returned added row(s);
- non-UI callers of `addImport` preserve their existing behavior;
- the browser regression proves import → sheet through the real UI caller, not through a store side effect.

This is the only required brief correction. X3 may dispatch once that ownership is explicit.

## Question 1 — learner-stated tempo provenance

Use the existing **`authored` fact kind**, with the provenance sentence explicitly naming the learner as the source, for example:

`{ kind: 'authored', via: 'the learner stated this tempo …' }`

Do **not** add a new `stated` provenance kind merely to make the gate treat it identically to authored truth.

The existing material contract already defines `authored` broadly enough to include the learner's correction, and the downstream gate's `FactBasis` explicitly describes authored facts as including learner corrections. A separate kind would create another state that every provenance reader would have to understand while changing no current pedagogical decision.

The important distinction remains in `via`: file-authored tempo and learner-stated tempo are both known source facts, but their source remains visible.

However, **X3 must not fake this through `updateImport`**. At `ef80e86`, `updateImport` cannot patch tempo, provenance, demands, or the untrusted list. Therefore:

- if E-tail lands a semantic store operation that can state the tempo and update the affected provenance/untrusted facts coherently, X3 may call it;
- otherwise X3 ships the rest of the workflow with **Set tempo held/not done**, exactly as the brief's deviation rule says;
- do not widen the generic metadata `updateImport` from the UI merely to make this control work.

A future store operation should own the complete mutation: learner-stated tempo provenance and clearing only the tempo-sensitive `untrusted` facts whose uncertainty that statement resolves. The UI should not reconstruct that state itself.

This does **not** block the rest of X3.

## Question 2 — learner confirming/rejecting the key estimate

**Later row. Do not add the key-right/key-wrong control in X3.**

The current key is an inferred fact that can affect spelling/notation. A button that merely says "yes, that estimate is right" would create a human assertion without defining what happens to:
- the score's written key/signature;
- respelling if the estimate was wrong;
- demand remeasurement;
- provenance of the corrected score;
- any gate facts derived from that notation.

That would repeat the exact mistake X3 is intended to remove for hands: UI certainty floating above source truth.

When key correction is implemented, it should be a semantic correction path like `correctImportHands`: update the stored score/fact, preserve the learner as the source, remeasure anything affected, then render the new provenance. A later brief can decide whether "confirm estimate" is useful once that correction contract exists.

## Accepted product shape

The rest of the X3 brief is approved:

- **What the app read** and **What the app guessed** are separate.
- Provenance is rendered from the current stored row, not from a stale conversion-time message.
- Hand correction uses the existing semantic store path `correctImportHands`.
- The conversion note follows the current provenance after correction.
- `What the notes ask` reuses E2's measured truth.
- Assignment reuses T52's contract: assignment creates a practice option, not evidence and not rung completion.
- Library state is learner-facing and contains no internal ids or track names.
- Wanted-piece placeholders explain the import action without leaking internal taxonomy.
- X3 adds no automatic offer path. L113 remains X1's responsibility.
- A manually opened/imported piece remains reachable as the learner's chosen exploration even when automatic selection would refuse it.

## Important implementation distinction

"Try" in the broader import workflow must mean the learner explicitly opens/plays the imported score. It must not mean the import sheet itself creates evidence or changes recommendation eligibility.

If the learner plays it, normal Score/run machinery may create whatever evidence that actual run measures. Merely importing, correcting, assigning, viewing, or saving it creates none.

## Ownership

- **X3:** import sheet, UI caller wiring, assignment-body reuse, Library wording/state, conversion-note rendering, E45 wording.
- **E-tail/import store:** semantic tempo write if one exists or is added under that owner.
- **X1:** automatic admission of rung-owned/assigned imports under L113.
- **Later key-correction row:** learner confirmation/correction of inferred key with source-truth consequences.

No owner decision is required.

## Sequencing

X3 may dispatch after applying the UI/store boundary correction. It does not wait for the tempo control; that control may remain explicitly held if the semantic store write is absent.

Post-build review should prove the actual learner path:

`import UI → returned stored row → import sheet → hand correction → current provenance → assignment decision → Library state → explicit play if chosen`

with no UI side effect originating inside the store and no evidence produced by import/assignment alone.
