# Reviewer response — L98 handoff `a8a0026`

Reviewed implementation HEAD: `a8a0026`

## Verdict

**ACCEPT. L98 closes, and with it the required C7 fix-forward. C7 may close.**

I reviewed the immutable L98 handoff first, then the named store implementation, targeted six-case regression suite, Entry 83 material, and the governing UI-spec text.

## 1. ACCEPT — the readiness boundary is at the authoritative store

The fix addresses the C7 finding at the correct boundary rather than patching Today or Skills.

`getPlan()` now shares one first read through `loading`. That read performs the one-time pre-C5 carry-over before answering callers. Consequently a first consumer cannot receive the pre-carry-over row merely because the evidence job has not run yet.

The implementation does not add per-screen retries, reloads, redraws, or screen-specific migration knowledge.

## 2. ACCEPT — stale reads cannot republish over newer state

The `generation` guard is the important second half of L98. `publish()` and `forgetCachedPlan()` advance the generation, and `readPlan()` publishes its result only if nothing has replaced or invalidated the row since that read began.

That directly addresses the stale-read overwrite called out in the C7 review, including the restore/cache-forget case.

Writes are also serialized through the store boundary rather than independently racing the first read.

## 3. ACCEPT — carry-over remains one-time and observable by the job

The first authoritative read may perform the carry-over, while `carryOverOnce()` subsequently reports what that read carried once and then returns zero. The due flag is cleared only after the carried row is stored; failure to obtain curriculum leaves the flag in place for a later attempt.

That preserves the C5 one-time migration semantics while moving readiness earlier.

## 4. ACCEPT — targeted regression coverage matches the defect

The six targeted cases cover the seam that mattered:

- concurrent first readers share the same authoritative row;
- a read cannot overwrite a newer `updatePlan`;
- a pre-restore read cannot republish after cache invalidation;
- the first read of a pre-C5 database returns the carried plan;
- Today sees the carried state on its first draw without reload;
- Skills sees the carried state on its first draw without reload.

These are materially stronger than merely asserting that the database eventually contains `carriedOver`.

The reported isolated timeout/load failures are not evidence against L98 based on the discriminating runs in the handoff. They remain suite-reliability work rather than a reason to weaken this seam's assertions.

## 5. P3 — record, do not block L98/C7

The builder's P3 observation is valid: `recordRungWord()` reads the current `rungWords` map before entering `updatePlan()`'s serialized mutation. Two truly concurrent word writes could therefore each derive from the same prior map and the later write could omit the other's new key.

That is **not the L98 first-open/carry-over race**, is not exercised by a reachable simultaneous UI path today per the handoff, and should not hold C7 open. Record it as its own later store-atomicity item. If/when fixed, the read-modify-write should occur inside the serialized mutation rather than adding UI coordination.
