## Verdict

APPROVE

The implementation fixes the stale-report check at the correct boundary.

`UNFETCHED_REASONS` identifies only the reasons emitted by the Mutopia import step for this build's fetch/pin failure. `ladder_report_findings` first compares the real build, and only when such placeholders are present does it perform the counterfactual comparison with those specific rows read as bundled. If that removes the difference, the result is a named warning. If any real catalogue/rung difference remains, the stale-report error survives and names what was set aside.

The tests preserve the important adversaries:

- unfetched Mutopia edition: warning, not stale-catalogue error;
- wrong pinned fetched file: same treatment;
- licence refusal: still a real change;
- kern licence placeholder: still a change;
- song added to the rung: still a change;
- real change beside a fetch failure: still errors;
- strict/personal flavour behavior remains pinned.

The actual ladder renderer is untouched, so Q80 does not redefine catalogue truth merely to make validation pass.

That is the correct continuation of Q75: "this build could not know/fetch it" is not the same proposition as "the catalogue changed."

## Q86: should Pages publish a build that failed to fetch a required public piece?

Guard the deployment.

Keep Q80's validator behavior exactly as built. Do not turn the stale-ladder report back into a network-availability gate.

But a public deployment is a different decision.

The recorded consequence is concrete: during a Mutopia outage, the new build would replace the previously complete phone build with one in which:

- Pine Apple Rag becomes an import-your-own-copy placeholder;
- ragtime.8 loses its bundled stride-bass-establishing option;
- that degraded state remains live until another successful deployment.

There is no product advantage in replacing a known-complete public artifact with a build known to be incomplete solely because an external fetch failed.

So the rule should be:

build/validation may complete with explicit fetch-unavailable warnings; public deployment must not replace the last successful artifact when required fetch-backed public content is missing.

Make this a deploy-side guard, not a reinterpretation of the validator warning.

Prefer a structured build/fetch result or manifest as the guard input rather than grepping human warning text. Q83/Q84's work making fetch failures explicit in logs is compatible with that direction, and Q82 should bring kern/MuseTrainer missing-source behavior under an equally explicit representation.

The guard should distinguish:

- expected catalogue placeholders, such as copyright/licence/import-only material: allowed;
- a build-owned failure to obtain content expected to be bundled in a healthy public build: do not publish;
- deliberate catalogue/product removal: judged through the normal catalogue truth, not mistaken for an outage.

## Classification

- Q80: APPROVE and close.
- Q86: CONSTRAINS DEPLOY: add a narrow deploy-side completeness guard before a fetch-degraded public build can replace the previous successful deployment.
- Do not roll back Q80: validation should continue distinguishing transient build inability from catalogue drift.
- Q82/Q83/Q84 remain useful: normalize missing-source reporting and make the deploy decision observable rather than implicit.
