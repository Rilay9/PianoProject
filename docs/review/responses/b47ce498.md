## 2. Hotspot and latent/regression procedure rules

**APPROVE WITH ONE REQUIRED CHANGE**

The purpose is right, but both proposed rules need to be written as evidence triggers rather than binary rituals before they go into `operating-procedure.md` §11. That section already says a correction is owed only where it changes what happens next, asks for the mechanism and discriminating test, scopes claims, and treats cadence/count rules as subordinate to information value (`docs/prompts/operating-procedure.md:155–246`). A hard three-lane redesign rule would contradict that principle.

1. **Required rewrite of Rule A — hotspot trigger, not automatic redesign.** Three or more fix-forwards on one surface plus a new defect means **no next local fix is dispatched until the brief performs a model check**: are the defects accumulating around the same allocation/state/ownership mechanism, or are they independent faults that merely share a screen? If the same mechanism is accumulating special cases, the next work is a model/design lane. If the check shows a coherent model already exists or the new defect has an independent cause, a bounded local fix remains allowed. The count is the alarm; shared mechanism is the reason to redesign. U122 passes that stronger test now because the current bar actually has multiple independent symptom predicates and state-specific allocation rules (`ScoreScreen.ts:1435–1548`; `style.css:955–1054`).

2. **Required rewrite of Rule B — provenance with an honest unknown state.** A new row that could plausibly be related to recent work records one of: **pre-existing at `<named baseline>`**, **introduced by `<named seam>`**, **unknown**, or **not applicable**, and cites the discriminating comparison when one was made. Reproducing on the immediate predecessor proves only that the newest seam did not introduce it; it does not prove the defect is timeless or identify the seam that did. Content/product/design findings for which tree reproduction is not meaningful use `not applicable`. If a historical reproduction/bisect would not change ownership, priority or the next action, use `unknown` rather than creating process work to obtain a label.

Acceptance: the two procedure rules preserve their purposes — stop repeated local patch accretion and distinguish regressions from newly exposed old faults — without making a lane count or mandatory bisection into a new source of ritual work.

Stop condition: if classifying provenance would require unavailable runtime evidence or a costly historical search that cannot change the disposition, do not guess and do not open another task; record `unknown` with the evidence actually checked.
