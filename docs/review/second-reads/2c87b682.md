## 1. CL05: hidden time is not practice on Drill. Verdict: agree, with notes the builder needs

**The fault is there as described.** `suspendDrill` (DrillScreen.ts:1593-1638) and `resumeDrill` (1644-1652) never touch the metronome (528-533), so the rhythm click goes on scheduling while the page is hidden. `onNote` (678-705) has no check for a hidden page.

**The stop condition is not met.** The rhythm card can be re-anchored with the state the card already holds. After the first tap, `feed` judges each tap as `tMs - startedAtMs` (special.ts:145), and the latch is spent (142). The public `startedAt` (109-111) and `startAt` (102-106) are a complete read/write pair for that origin. `startAt`'s other effects (`plannedStartMs`, `waitingForStart = false`) do nothing once the latch is spent. The screen needs one held value, the moment the page hid, which is the same kind of local as `loopHeld` and `dictationHeld` (509-511). Ownership does not change: the drill owns the origin and the screen decides when (screenLifecycle.ts:35-38). On a rhythm card `meanReactionMs` is the mean onset offset (special.ts:172-180), so re-anchoring the origin is also what keeps the hidden span out of it.

**The other card kinds need a small engine addition.** There, reaction time is the input's `tMs` minus a `promptAtMs` taken from the clock in `next()`: PromptDrill.ts:89/124, simon.ts:557/588, harmony.ts:434/508. That field is private, and `Drill` has no hook for shifting it (types.ts:237-260). Two mechanical routes exist:
- (a) An optional shift method on `Drill`, on the precedent of `reveal?()` (types.ts:258). Each drill moves its own `promptAtMs`, and RhythmDrill moves its origin through it as well.
- (b) A visible-time clock passed through the `clock` option `drillFromCatalog` already takes (fromCatalog.ts:90,174), with `tMs` translated in `toEngineInput` (672). This also has to translate the audio-anchored conversions (1270, 1277, 1315-1317) and the dictation tick (1162). RhythmDrill is built without that clock (fromCatalog.ts:593).

Route (a) touches less. Neither route is a new state or ownership decision.

**One place can refuse hidden input for every card kind.** Every note reaches a drill through `onNote` (678): MIDI (714), on-screen keys (715) and microphone (2480). CC64 reaches it through `onControl` (707), from the message stream (718). The only feed sites are 692, 709 and 1162, and the dictation tick at 1162 is already stopped while hidden. So one guard at the top of `onNote` and `onControl` covers every kind, and it runs before Simon's chain window (689) and the manual-advance hold (685). The guard should read a flag that `suspendDrill` sets and `resumeDrill` clears, not `pageHidden()` (screenLifecycle.ts:46-48), because the boundary also treats `pagehide` as hidden (screenLifecycle.ts:77).

Notes the builder needs:
- **(a) A rhythm card has three phases, and they resume differently.**
  - Count-in, downbeat not yet known: stop the click, and play the count-in again on return. This is safe because `plannedStartMs` is still null, so `latchOnFirstTap` goes back to waiting for the downbeat (special.ts:125).
  - Downbeat known, no tap yet: do not call `startCountIn` again as it stands. With `plannedStartMs` set, `waitingForStart` stays false (125). The latch check against the old origin then passes (140), so a stray tap during the repeated count-in becomes the first onset. The screen cannot tell this phase from the first one: `downbeatKnown` is local to the count-in's closure (1260), `plannedStartMs` is private (special.ts:49), and `startedAt` is already set in `next()` (88). Hoist the flag to screen scope or add a read-only getter.
  - Latched: shift the origin by the hidden span, then restart the click on the next beat of the shifted grid counted from now. `resumeClickAfterFirstTap` (1303-1320) counts from the first tap instead. Capture `clickAnchor` again on return (531, 1254), because the audio clock can stop while `performance.now()` keeps running.
- **(b) A card that opens while the page is hidden still starts its click.** `draw()` calls `suspendDrill` (1140) before `advance()` calls `startCountIn` (1354), and the count-in's `.then` checks only `disposed` and `finished` (1239). The `suspensions` guard already used at 764-767, 818-821 and 2333-2336 closes this.
- **(c) Two playability questions to record, not decide.** Shifting by the exact span, as ruled, starts the judged grid again the instant the page is visible. The next onset can be less than a beat away, and the click only comes back on the next grid beat. A lead-in bar would change what the learner experiences, so it is the reviewer's call; record it as an observation. Also, if the audio context is not running on return (no tap has happened since), the grid would judge against a click the learner cannot hear. Record that as well.
- **(d) The pedal drill measures between two inputs (special.ts:253-254).** A chord before hiding and a lift after returning span the hidden time. `meanReactionMs` is 0 there (324), but the per-answer `reactionMs` (328) feeds coaching.ts:57-76. Either include it or record it as not done.
- **(e) The existing harness cannot prove "no sound".** jsdom has no Web Audio, so `ensureStarted` throws (AudioEngine.ts:81) and the rhythm card takes the no-metronome path (1288-1293). drillLifecycle.test.ts (fake `performance` at 134-135, `setVisibility` at 65-68, `screenKeyboardSource` at 54) proves input and timing only. The "no sound" half needs a stub for `audioEngine` and `Metronome`.

## 2. U105b: the refusal stays whole in a paused run. Verdict: agree, with notes the builder needs

**The rule and the state.** The restriction is in style.css:6155. The comment at 6145-6153 states the old rule, so it has to be rewritten. `data-running` is `session.running` (ScoreScreen.ts:4855), which is the engine's `running` (ScoreSession.ts:375-377). `pause()` sets `paused` and leaves `running` true (PracticeEngine.ts:518-525). A paused run therefore matches the `:not()` today.

**An extra header line in a paused run does not refit or reshape the frozen window.**
1. The header growing a line fires the stage's `ResizeObserver` (WindowRenderer.ts:998-1015), which calls `stageChanged` (2606-2669).
2. The width has not changed, so it is not treated as a rotation.
3. `updateReadAhead` finds nothing to change, because `chooseWindowShape` returns the held shape while the run is frozen (1756-1762). The freeze is therefore not released (1664-1670, 1677).
4. `fitSlots` keeps the frozen scale for a height-only shortfall down to 0.8 (269, 4026-4030).
5. `fitToStage` refuses to re-engrave on a height change alone while frozen (3546-3553; autoFit.ts:113-115).
6. When the line goes, the height returns to its old value, so nothing refits (autoFit.ts:114).

**The tests already show this.** score.head-height.spec.ts:270-297 adds 24-96 px to the header during a frozen run and the cursor scale holds to five places. Lines 215-268 show the same across restarts and also check the zoom. The "cut, not wrapped" guard (177-189) writes its long text with no `data-sound-refused` present, so the wider rule does not reach it. The fuzz seed 4 check (score.fuzz.spec.ts:359-372) compares snapshots within an epoch, and `playPause` resets the epoch (188, 324). The fuzz never raises a refusal. So the header line is not unsafe geometry, and no paused/suspended marker is needed for the header.

Notes the builder needs:
- **(a) The header folds away in a paused run too.** Three seconds after any tap the chrome folds even when paused (ScoreScreen.ts:3425-3427; the comment at 2768-2770 says so). Upright, the header then becomes `display: none` (style.css:2973-2975).
  - After the fold, the sentence appears in the corner chip instead (ScoreScreen.ts:1190). The chip is not clamped (style.css:2376-2390), but its reserve is a fixed 22 px (style.css:2373; WindowRenderer.ts:4952).
  - At the wider face, a second chip line would sit over the top of the sheet. That is overlap in the reviewer's sense.
  - The case should measure the header before the fold, or hold it open the way head-height does (219, 275). It should check the chip separately.
  - If the chip overlap is confirmed, bring it back to the reviewer rather than cutting the sentence. The existing mark (`markRefused`, 3068-3075) is the hook for a stable surface, for example by not folding while the mark stands, but that choice is the reviewer's.
- **(b) Raise the refusal only after `waitForFreeze` (head-height.spec.ts:60).** Before the freeze is taken, at step 0 or earlier, a reshape is allowed by design (1756; `freezeAfterSettle` at 3854-3888). The case would otherwise be measuring that, not the rule.
- **(c) Sideways the sentence is cut on a different surface.** On a phone held sideways the header is hidden (style.css:961-963), and the state line is mirrored into `.score-bar__status` (ScoreScreen.ts:1189). That element is `nowrap` with an ellipsis at 28vw (style.css:2910-2917), so the sentence is cut there both with no run and in a paused run. This rule's selector does not reach it. Record it as an adjacent observation: same invariant, different surface.
