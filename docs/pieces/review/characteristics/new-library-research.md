# New-library research for the easy score-characteristics batch (2026-10-10)

Method: Part A is by local introspection and runs (music21 10.5.0, partitura 1.9.0, one Python process at a time). Parts B and C are web reads; every URL is one I fetched or got from a search result. "(inferred)" marks anything I did not read or run. Web page text came through WebFetch's summariser, so numbers marked [fetch] were not checked against the PDF; numbers marked [pdf] I read myself from the paper PDF with pdftotext.

Scores I ran on (all two-staff piano, from the music21 corpus):
- R1 = joplin/maple_leaf_rag (anacrusis, repeats, endings, key changes)
- R2 = schumann_clara/polonaise_op1n1 (clef changes incl. Treble8vaClef, triplets, dynamics, crescendo, arpeggio marks, fingering, D.C. al Fine)
- R3 = schumann_clara/polonaise_op1n3 (39 grace notes, turns, trills, pedal, fingering)
- R4 = schumann_clara/polonaise_op1n4 (tremolo)
- S = schoenberg/opus19/movement2 (fermatas)
- C = objects I constructed in code (nothing in the corpus had the feature)
I scanned the raw XML of 654 corpus files for features. No two-staff file contains `<octave-shift`, `<glissando`, `<harmony` or `<slash`; so Ottava, Glissando, ChordSymbol and slash were run on constructed objects only.

Summary for part A: m21 reads nearly everything as typed objects; the "statistics" facts (entropy, black-key share, ledger lines, equal-value runs, two-staff relations, density) are small own functions over note lists, or jSymbolic whole-score numbers. pt adds the clean note_array (pitch, staff, voice, onset_beat) that makes per-staff statistics a few numpy lines; pt misses tempo marks on R2.

## B. Difficulty-statistics work (Ramoneda et al., Chiu & Chen, Sébastien et al.)

**CIPI, "Combining piano performance dimensions for score difficulty classification" (Ramoneda, Jeong, Eremenko, Tamer, Miron, Serra; Expert Systems with Applications 238B, 121776, 2024; arXiv 2306.08480).**
- Code: https://github.com/PRamoneda/difficulty-prediction-CIPI (url from https://arxiv.org/html/2306.08480). Licence: the LICENSE file begins "licensed under the GNU Affero General Public License", AGPL-3.0 (read raw LICENSE via curl). Input: a MusicXML path; `compute_difficulty(path)` returns diff_ensemble, diff_p, diff_argnn, diff_virtuoso; `pip install git+https://github.com/PRamoneda/difficulty-prediction-CIPI.git` (https://github.com/PRamoneda/difficulty-prediction-CIPI).
- Features: not hand-crafted. A note-pitch representation plus embeddings from pretrained fingering (ArGNN) and expressiveness (Virtuoso) models; the paper names the 7 Sébastien and 17 Chiu & Chen descriptors as background only [fetch].
- Dataset CIPI: 652 pieces, 9 levels, MusicXML, CC BY-NC-SA 4.0 on request (https://zenodo.org/records/6564422/latest, https://mirdata.readthedocs.io/en/latest/_modules/mirdata/datasets/cipi.html).
- Numbers [fetch], Table 2 (Acc-9 = balanced accuracy over 9 levels; mean (std)): ensemble Acc-9 39.5(3.4), Acc-3 71.3(3.2), Acc±1 87.3(2.2), MSE 1.1(0.2); pitch only 32.2(5.9), Acc±1 76.4(2.8), MSE 1.9(0.2). Abstract (https://arxiv.org/abs/2306.08480): "39.47% balanced accuracy and a 1.13 median square error" (as returned by the summariser, which would not give the abstract verbatim).

**Mikrokosmos-difficulty, "Score difficulty analysis for piano performance education based on fingering" (Ramoneda, Tamer, Eremenko, Serra, Miron; arXiv 2203.13010, 2022; ICASSP 2022 repo name).**
- Code: https://github.com/PRamoneda/ICASSP22, licence MIT per the repo's licence link [fetch]. Dataset repo: https://github.com/PRamoneda/Mikrokosmos-difficulty, no LICENSE file in its file list [fetch]; README: 147 scores in a table (62 beginner, 54 moderate, 31 professional) while the text says 146; MusicXML made by OMR from IMSLP PDFs plus manual correction.
- Features computed from symbolic scores [pdf]: per-note finger and finger-velocity cost from Pianoplayer (P-F, P-V), finger and transition probabilities from Nakamura's HMM (N-F, N-P), and a bare note-onset matrix K as baseline. Models: XGBoost, DeepGRU with attention. Fingering files are PIG format.
- Numbers [pdf, Table 2, 3-class test accuracy %, 50 seeds]: DeepGRU K 64±8, N-F 72±8, P-F 73±6, N-P 71±8, P-V 78±6; XGBoost (avg) K 65±10 ... P-V 68±10. Table 3 Spearman rank correlation (Bartók / Henle) for DeepGRU: K .71±.08 / .71±.09, N-F .82±.06 / .81±.06. The paper says it evaluates "(balanced) accuracy" and warns of large standard deviations.

**PSyllabus, "Can Audio Reveal Music Performance Difficulty? Insights From the Piano Syllabus Dataset" (Ramoneda, Lee, Jeong, Valero-Mas, Serra; IEEE TASLP 2025; arXiv 2403.03947).**
- Audio, not symbolic. Code: https://github.com/pramoneda/audio-difficulty, MIT (README). Inputs: an audio file (CQT 88 bins) and a piano roll made by an audio-transcription model. Dataset: 7,901 pieces, 11 levels, Zenodo 10.5281/zenodo.14794592, research-only licence.
- Numbers [fetch], Table II on PSyllabus (MSE / Acc % / τc): CQT 2.29 / 32.9 / .74; piano roll 1.85 / 36.7 / .77; early fusion 1.81 / 37.3 / .78; late fusion 1.82 / 36.2 / .78. No symbolic features in this paper.

**Related, for completeness: "Predicting performance difficulty from piano sheet music images" (Ramoneda, Valero-Mas, Jeong, Serra; arXiv 2309.16287, ISMIR 2023).** Code https://github.com/PRamoneda/pdf-difficulty (no licence stated on the page I saw). Input: sheet-music images (bootleg score). Abstract [fetch]: "balanced accuracy of 40.34% and a mean square error of 1.33"; Table 5 [fetch] CIPI comparison: Symbolic GRU+Att 39.5(3.4) / 87.3(2.2) / 1.1(0.2); proposed GPT multi-FC 40.3(4.3) / 82.0(1.4) / 1.3(0.1) (Acc0 / Acc1 / MSE).

**Sébastien, Ralambondrainy, Sébastien, Conruyt, "Score Analyzer: Automatically Determining Scores Difficulty Level for Instrumental e-Learning", ISMIR 2012, pp. 571-576** (read the PDF, https://ismir2012.ismir.net/authors/event/papers/571_ISMIR_2012.pdf).
- No code repository found. The only software pointer is a 2012 web beta page (http://e-piano.univ-reunion.fr/tests/ScoreAnalyser/readScore.php). Input: MusicXML.
- Seven criteria (Table 1): playing speed (tempo and shortest note), fingering (from `<fingering>`), hand displacement (jumps over 12 semitones within under 2 beats), polyphony (chord ratio), harmony (accidental ratio), irregular rhythm (`<time-modification>`), length (pages or bars).
- Accuracy: no accuracy percentage. Validation is a PCA on 50 pieces and contingency tables against it and against three teachers' marks (levels 1-3); the text says one major disagreement (3 vs 1, Beethoven Sonata in F) against the PCA. I did not read the table cells.

**Chiu & Chen, "A study on difficulty level recognition of piano sheet music", IEEE International Symposium on Multimedia 2012, pp. 17-23.** I could not obtain the abstract or full text (the IEEE page fetch returned nothing). Second-hand only: the CIPI paper says they extended Sébastien's 7 descriptors to 17 [fetch]; Ramoneda 2023 (https://arxiv.org/html/2309.16287) says they collected 300 MIDI scores, never publicly released, and gives no accuracy or feature list [fetch]. Code: none found. Accuracy: not found.

## C. The four named tools

**musif** (DIDONE project; MusicXML feature extraction). PyPI JSON (https://pypi.org/pypi/musif/json): version 1.3.0 uploaded 2026-09-01, licence field "MIT", Python >=3.10, depends on music21>=9.1, ms3==2.4.2, pandas, scipy. Docs (https://musif.didone.eu/Feature_definition.html): feature groups ambitus (semitone ambitus, highest/lowest note), melody (interval mean/std, step/leap counts and percents, repeated notes), rhythm (average duration, dotted and double-dotted rhythm), density (notes per bar, sounding density), dynamics (mean, gradient, abruptness), key (key signature, mode), core (time signature, grouped Simple/Compound duple/triple, number of beats, measure and note counts), tempo (numeric from MusicXML, verbal), texture (note-count ratio of parts), scoring, harmony, scale degrees, lyrics. The page lists no clef, accidental, ornament or articulation features. It was built for 18th-century opera arias, with a per-part design (inferred: parts rather than staves, so a piano's two staves may merge or split depending on the XML). Input: MusicXML (MuseScore files for harmony features); output a pandas DataFrame/CSV. It says the jSymbolic integration is manual. Covers from the list: ambitus per part, leaps and repeated notes, dotted rhythm, density, dynamics mean, key and time signature class, tempo words.

**pianoplayer** (marcomusy/pianoplayer, https://github.com/marcomusy/pianoplayer). PyPI JSON (https://pypi.org/pypi/pianoplayer/json): 3.0.2 uploaded 2026-03-02, MIT, Python >=3.9, light dependencies (rich; extras for midi, vedo, etc.). Computes a fingering by dynamic-programming search that minimises finger velocity; it does not compute score statistics. Input (README): MusicXML (.xml, .mxl), MuseScore, MIDI, PIG; output `output.xml` (fingering written into the score) or `output.txt`; existing fingering marks are kept as anchors; hand-size presets XXS-XXL; hands treated as independent; ornaments and small notes ignored. For the list: it generates fingering numbers (mark.fingering) and gives a per-note cost that the Ramoneda work uses as a difficulty feature (P-V).

**muspy** (https://github.com/salu133445/muspy). PyPI JSON: 0.5.0 uploaded 2022-04-16 (no newer release), MIT, Python >=3.6, depends on music21, mido, pretty_midi, pypianoroll. Input MIDI, MusicXML, ABC. Metrics page (https://hermandong.com/muspy/metrics.html, reached by a 301 from salu133445.github.io, host not verified as the same author): `pitch_range`, `n_pitches_used`, `n_pitch_classes_used`, `polyphony`, `polyphony_rate`, `pitch_in_scale_rate`, `scale_consistency`, `pitch_entropy`, `pitch_class_entropy`, `empty_beat_rate`, `empty_measure_rate`, `groove_consistency`, drum-pattern metrics. Covers from the list: range, pitch inventory, pitch entropy, polyphony, silent-beat share; it has no clefs, accidentals, staff or marks, and treats a track as one stream (inferred). Stale since 2022; its entropy functions are one-liners over a histogram, so own code is as short as adding the dependency.

**jSymbolic 2** (Cory McKay, jMIR). Latest on SourceForge: 2.2, 2018-06-25 (https://sourceforge.net/projects/jmir/files/jSymbolic/); the GitHub README heading says 2.3 with no date (https://github.com/DDMAL/jSymbolic2). Licence GPL. Java 8+. Input MIDI and MEI only (not MusicXML). 246 features, 1,497 values (https://jmir.sourceforge.net/jSymbolic.html), seven groups: pitch statistics, melodies and horizontal intervals, chords and vertical intervals, rhythm, instrumentation, texture, dynamics. Output ACE XML always, ARFF or CSV optional. Because it reads MIDI/MEI it cannot see clefs, ledger lines, accidental spelling, ottava, fingering, tuplet notation or slurs (inferred); it does cover pitch range and variety, melodic interval histograms, repeated notes, note-duration statistics, note density, voices and register, as whole-piece numbers. music21 reimplements a subset (about 100 feature classes, I ran 38 of them; 2 raise "not yet implemented"), which is the route without Java.
