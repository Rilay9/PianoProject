# What chunk 1 taught about writing rules (2026-10-08)

The checkers of areas 1.A, 1.B and 1.C found 17 rules that gave wrong answers on real scores. The faults fall into a few kinds; every later rules brief cites this page, and every writer checks its rules against each kind before reporting.

1. **The commonest case first.** The syncopation rule missed the most common beginner syncopation (a weak-beat note held past a stronger beat), including the app's own two syncopation drills. Start each rule from the first case a learner meets in the method books, and run it on the project's own generated drills for that characteristic.
2. **Plausible counterexamples, not only positives.** Plain dotted melodies matched the habanera; any 12/8 long-short pair was called a shuffle; violin music labelled Piano was read as piano music; a half cadence was called a modulation. For every rule, name the music that looks like a positive but is not (another style, another instrument, an ordinary pattern) and show the rule rejects it.
3. **A pattern is not a style.** Where the same notes serve several styles (habanera, shuffle, stride, backbeat), code reports the pattern and an agent names the style.
4. **Examples are run, not asserted.** Some named positives were not positives (a lead sheet called a chord chart; an encoding defect used as a ledger-line example; a misspelled chord as a spelling positive). Every example id is run through the rule and its result recorded.
5. **Validation claims are re-run.** A claimed validation of a bound was false (the Chopin runs it threw away had no short values). Every "validated" says what was run, on which items, with what result.
6. **Library traps** (measured in chunk 1): `Stream.recurse().notes` includes chord symbols; `Score.parts` returns one PartStaff per staff; partitura misreads tempo words (allegretto, più/meno mosso, rubato) and reads D.C./D.S. only from `<sound>` attributes no held file carries; `analyze('key')` is Aarden-Essen, which calls a C major scale A minor (Bellman-Budge is the better second witness); the app's `detect.ts` reads staff 2 as bass clef and places ledger lines by sounding pitch; the PDMX files are music21 re-exports that lose cue size and leave some tuplet brackets unclosed (the originals are under `content/scores/pdmx`).
7. **The key is read from the music.** The ending vote reads the whole last bar or last triad, not the last onset; a V7 ending votes a fifth down; keyless chord-root files have no key.
8. **Thresholds carry their basis.** Each threshold is sourced, validated (what was run), or marked open in those words. A source or a passing test is not validation unless it shows the threshold separates the positives from the plausible counterexamples.
9. **Corrections are re-run in the same step.** An apply that changes a rule re-runs it on the examples, including those that failed before; an unre-run correction is a specification, not a fix.
10. **Existing tools first, outside the repo too.** The hand-written detectors for key, key change, hand assignment, melody location, lead-sheet format and spelling failed validation, while the rules that called music21 and partitura for simple reads mostly held. Before writing a detector, search for an existing library, trained model or annotated dataset that does the job (CLAUDE.md's first rule): record what was found, its licence, whether it runs offline, its published accuracy, and measure it on the catalogue. A custom heuristic is written only where nothing serves, and says what was searched (the owner, 2026-10-08).
