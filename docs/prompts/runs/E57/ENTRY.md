## The mechanism, the discriminating test, the red line

**The fault** (`convert.py`, `normalise`'s `elif existing_tempo:` at the base's :1557–1565): `existing_tempo` is every `MetronomeMark` in the score (`out.recurse()`), and the branch removed `existing_tempo[1:]` by list order alone, never asking where a mark stood or what it said. Its comment named the case it was written for, a copy music21's ABC reader gives each voice. The kern parser does the same per spine. Every later, genuinely different tempo change went with them.

**The fix** (`convert.duplicate_tempo_marks`, called from the same branch; nothing else in `normalise`, `insert_tempo`, `tempo_printed_as_text` or the default branch moved): a mark is removed only as a copy of a statement already standing at its place. The test has two halves:
- the same offset in the whole score (`getOffsetInHierarchy(score)`, to a millionth), on any staff or voice;
- the same `getQuarterBPM()` within `SERIALIZATION_TOLERANCE` = 0.01 quarter notes a minute, the value X42 derived and stated in the app's reader (`app/src/score/tempoFromXml.ts`:239, Entry 185, `docs/prompts/runs/X42/ENTRY.md`). The same value is stated in the converter and cited there, and `test_the_tolerance_is_x42s` holds the two equal.

The position is not the bar number. The probe showed music21's ABC reader hanging one voice's copy on the part itself, outside any bar, at the same offset as the other voice's copy in bar 0, so a bar-and-offset key would have stopped collapsing the ABC duplicate (red on `test_only_one_tempo_mark_survives`). Of one statement's copies the first printed one (`number` set) is kept over a sound-only one, whatever the order. A mark whose tempo reads as None (`<per-minute>c. 100</per-minute>`) is never anyone's copy. The file's effective tempo (`result.tempo_bpm`) is still `existing_tempo[0]`'s, unchanged, so no `tempoBpm` moves.

**The discriminating case.** The alternative to the mechanism, that the later marks never reached `normalise` at all (a parser drop), is refuted by the same parse giving all six `*MM` marks in the probe and by the fix alone restoring them. The red lines, on the committed converter (`red-committed.txt`):
- `test_b_the_rondo_shape_keeps_its_two_later_changes`: `Lists differ: [('1', 48.0)] != [('1', 48.0), ('2', 152.0), ('3', 96.0)]`;
- `test_c_a_different_tempo_on_one_staff_at_one_place_survives`: `[('1', 100.0)] != [('1', 100.0), ('1', 120.0)]`;
- `test_d_a_sound_only_copy_gives_way_to_the_printed_mark`: `Lists differ: [] != ['76']` (the printed marking lost);
