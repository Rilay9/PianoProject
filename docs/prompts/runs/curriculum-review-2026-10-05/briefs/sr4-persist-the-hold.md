# Brief: the hold is stored on the run when the app knows it; credit reads the stored fact, never an inference from today's curriculum (lane SR4; 2026-10-06)

**What governs:** `docs/review/responses/sr3-lb1-landing.md` §3 and §4 (read whole: the required shape, the required tests, the scope). Entry 262 (SR3: what lands today, including `heldBelowItsRung` in `session.ts`, which derives the held fact from the stored options against today's writer); Entry 258 (SR2: the route carries the hold as `?hold=`, the material carries only the hold's effect); FABLE §6 and §10; `docs/prompts/operating-procedure.md` §10b, §13, §14. **The ruling, in its words:** the stored phrase is good evidence of what music was generated, not a stable record of why; comparing yesterday's stored options with what today's catalogue says the judging rung would write is a retroactive reinterpretation the run header exists to avoid. Persist the route's hold at run time, when the app actually knows it: an optional run-header provenance field, preferably beside the opening route (`opened.hold?: string`, or an equivalently narrow optional field with a stronger reason), meaning only "this sight-reading phrase was deliberately generated under this lower learner-rung hold while another rung judged the run". SR3's rung-credit exclusion reads that stored fact directly; an unheld run stores no hold; legacy rows with no hold keep their old behaviour and are never guessed or reclassified; `material` stays the exact generated phrase identity; no historical row is rewritten; no DB migration or version bump unless the persistence or backup schema proves an optional field cannot round-trip without one (verify, do not bump ceremonially).

**Decision rationale (operating-procedure §10b).** Learner problem: a run that was genuinely unheld when played could later read as held (and lose its rung credit) if a demand moves to an earlier rung, because the held fact is inferred from today's curriculum. Solution class: the ruled one above; the inference (`heldBelowItsRung`) is removed from the credit path (deleted, or kept only as a test oracle for SR2's offer comparison; say which and why). What reverses it: nothing; it is the run header's existing provenance pattern. Uncertainty: whether the session-row or backup schema whitelists fields (then the round-trip test proves the optional field survives, or a whitelist entry is the one change).
