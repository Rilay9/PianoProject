# G30 — printed fingering only where sourced (`backlog-2026-09-25.md`:222; `responses/questions-53670d2a.md` §3; `responses/questions-90b19bee.md` §1; surviving-work item 11; tier 1 never-teach-wrong)

## The scheduler's dispatch rule, answered first (`product-convergence-current.md`, "Dispatch rule")

1. **What current learner problem exists now.** The learner reads a finger number printed over a note as an instruction — "play this with finger 3" — in 43 of the generator's families today, but the family that wrote it has no source for that number at all. `tools/content/family_contracts.json` states this itself, in the contract's own words, 43 times: "the generator's own convention, not a published source: printed as advice" (checked below, exact count). The app draws whatever fingering a score carries by default (`app/src/score/OsmdView.ts`:179, `drawFingerings: options.drawFingerings ?? true`), so nothing currently stops an unsourced number from reaching the screen as if it were edited guidance.
2. **What current evidence establishes it.** *Checked, not inferred:* a script over `family_contracts.json` (below) finds exactly 43 families whose fingering note says "not a published source," all with `"printed": "printed"` (unconditional printing); two other families print sourced fingering (`hanon`, from the Mutopia edition; `chromatic`, from McLain's *Class Piano*) and are not part of this problem. `tools/content/family_contracts.py`:499 is the build's own consistency gate between the contract's `printed` field and what the generated score actually carries — it already treats "prints fingers the row says none" as a build-stopping fault, which is the existing policy mechanism this lane extends to the 43 unsourced rows, not a new one.
3. **Why this shape is still the best, simplest response.** The ruling is already made and not reopened here: "Print no fingering until it has an explicit defensible source/policy" (`responses/questions-53670d2a.md` §3, quoted in full below) and confirmed again this week, narrowly, against a reopening of CL15's identity work (`responses/questions-90b19bee.md` §1, quoted in full below: "Build the learner-truth correction; do not invent another identity system"). No pianist is in this process to supply a source, so "print none" is the only branch available (surviving-work item 11's own words: "still the simplest... No pianist is in this process, so 'print none' is the only branch available"). The identity mechanism this fix needs already exists and already shipped for exactly this shape of change (CL15's generated-identity continuity relation, built for the family-wide version bumps of `responses/questions-122a5224.md` §CL15) — this brief finds and closes one gap in reusing it (below) rather than building a second one.

## Premises at the lines (checked at HEAD `7d9de990`)

1. **The 43 count is exact and reproducible, and the fix touches exactly those rows — no more, no fewer.** A read over every family's `physical.fingering` entry in `tools/content/family_contracts.json` finds 45 rows with `"printed": "printed"`; 43 of them carry a note containing "not a published source"; the other 2 (`hanon`: "the edition's printed fingers, carried by the data file"; `chromatic`: "McLain's chromatic figure") are sourced and out of scope. The 43: `accompaniment, boogie, cadence, comping, coordination, double_scale, five_finger, four_chord_loop, ii_v_i, interval_reading, intro, latin_groove, meter, modal_vamp, montuno, octave_scale, oompah, open_voicing, ostinato, passing_chord, pedal, pedal_variant, pentatonic, position_shift, power_chord, repeated_notes, riff, rotation, secondary_rag, seventh_voicing, slash_bass, stride, swing_pair, tremolo_octaves, tresillo, triad_inversions, trill, tritone_sub, tumbao, turnaround, voicing, walking_bass, walkup`. This matches surviving-work item 11's count exactly. Families already `"where-sourced"` (fingering printed only on the specific items a source actually covers) or already `"none"` are untouched — this lane does not re-litigate `fingeringVerified` policy for them.
2. **The fix belongs in the generator, not in the renderer, and `OsmdView.ts`:179 is cited as the reason the problem reaches the screen, not as the file to change.** `drawFingerings: options.drawFingerings ?? true` (`OsmdView.ts`:179) is a single per-view flag that draws *whatever* `<fingering>` elements a loaded score's MusicXML carries — it has no family-level or per-note granularity, and it is already a user-visible setting (`settingsStore.showFingering`, `SettingsScreen.ts`:312) a learner can already toggle off entirely, for every score, sourced or not. Turning it off globally, or suppressing it for generated items generically, would also hide `hanon`'s and `chromatic`'s sourced fingering and anything a future authored or imported score prints correctly — exactly the opposite of "only where sourced." The only place that can distinguish "this family's convention is sourced" from "it is not" is the generator that knows which family it is, reading `family_contracts.json`'s own `printed` field; this is also where the ruling's own language points ("the family contracts themselves say the convention is not sourced").
3. **A precedent for printing no fingering at all on an unsourced figure already exists in the same file, unconditionally for one family, and this lane generalises the same judgement call to 42 more.** `generate_exercises.py`:1763–1775 (the broken-sevenths turn figure, G49): "No fingering is printed, from any root, until a source gives one for this figure... A printed finger number is a claim the learner reads as the fingering, whatever `fingeringVerified` says, and no screen reads the flag... The black roots already printed nothing." This is not a new idea; it is the one case where the generator already made exactly this call. The mechanical question "touch each family's own `articulations.Fingering(...)` call site, or strip fingering centrally" is answered in "What to build," as a builder-level implementation choice with no product-semantic consequence (`operating-procedure.md` §11's orchestrator fast path: either shape satisfies "print none," so no separate review round is needed for which one is chosen).
4. **A real, checked risk: removing the only fingering data two of the physical gate's own checks read may newly fail the build, and none of the 43 families has the declared fallback that would prevent it.** `family_contracts.py`:487–490's repeated-note check treats a same-pitch repeat under `FAST_REPEAT_SECONDS` as a fault *unless* a printed change of finger is present (`changes = bool(f1 and f2 and f1[0] != f2[0])`, :372) or the row declares a `repeatedNotes` solution (:488). A read of all 43 contracts' `physical.repeatedNotes` field finds **zero** declare one (checked: a script over the loaded JSON). If any of the 43 families' generated items contain a fast same-pitch repeat today that currently passes only because a printed finger change happens to be present, removing the fingering removes the only thing currently satisfying that check, and the build will newly fail it — not a hypothetical, a mechanical consequence of :372's `f1`/`f2` both becoming empty. Separately, :409–444's crossing check (`crossing_against_the_hand`) only evaluates a pair of notes when each carries exactly one finger (:374, `len(f1) == 1 and len(f2) == 1`); removing fingering does not newly fault this check, but it silently loses its coverage for these 43 families — the same loss every family already at `"printed": "none"` already has, extended, not a new problem, but worth one line in the handoff, not zero. **This is marked unverified until the real build runs**: the only way to know which, if any, of the 43 families actually hits the repeated-note case is to run the regenerated build and read `PhysicallyIndefensible` failures, which is why "What to build" puts this check before any contract file is edited for real.
5. **The generated-identity continuity relation CL15 built already expresses this exact case, with one gap: it was only ever exercised for a family's *first* version bump, and four of this lane's 43 families have already had one.** `material.ts`:45–55, :76–142 describes the relation precisely as the ruling asks for it: a family version bump moves every item's identity; an item whose `music_digest` (Premise 6) is unchanged carries its old identity forward in `provenance.formerGeneratorIdentities`, read by `learnFormerIdentities`/`learnerMaterial` for contact/encounter/competence lookups, with no claim of byte or notation identity (`material.ts`:36–38: D2's exact identity, the review record and every family-scoped read keep reading the row's own current identity regardless). `app/tests/unit/generatedIdentityContinuity.test.ts`:71 and `tools/content/tests/test_family_contracts.py`:506 (`TestGeneratedIdentityContinuity`, methods at :517, :532, :555, :565) are the existing proofs of this relation; this lane adds rows to the same mechanism, not a new one. **The gap:** `tools/content/generator_continuity.json`'s current five entries (`interval_reading`, `pentatonic`, `syncopation`, `tremolo_octaves`, `walking_bass`, all from CL15, Entry 188) each record a *single* identity per item (`family_contracts.py`:195–217, `former_generator_identities` returns `[one["identity"]]`, always one element, read from `docs/prompts/runs/CL15/scripts-continuity_table.py`'s capture, which stores `row["identity"]` as a bare dict, never reading what that row's *own* `provenance.formerGeneratorIdentities` might already hold). Of the 43 families this lane touches, four — `tremolo_octaves`, `pentatonic`, `interval_reading`, `walking_bass` — already carry a CL15-era former identity (the sibling items CL15's own bump preserved). A second bump of these same four families, built the same way CL15's capture script was, would write `generator_continuity.json` entries containing only the *version-just-left* (CL15's post-bump) identity, and `learnFormerIdentities` rebuilds its lookup table **fresh from the latest catalogue alone, never adding to a prior one** (`material.ts`:87–88's own docstring: "the table is the catalogue's alone and is replaced, never added to"). A learner whose stored encounter names the *original*, pre-CL15 identity would therefore stop resolving at all once this second bump lands — not a byte-identity question, a genuine silent loss of contact/competence history for exactly the population the ruling says must not be reset ("do not reset prior encounter/competence merely because an unsupported annotation was removed"). **The fix is still inside the existing schema, not a new one:** `provenance.formerGeneratorIdentities` is already typed and read as a list (`material.ts`:111–120 already loops `for (const one of formerGenerators)`, registering every element); `family_contracts.former_generator_identities()` need only be generalised to return the *union* of (a) the item's pre-existing former identities, read from the current, pre-G30 catalogue, and (b) the version-just-left identity this bump retires, for these four families only — the other 39 need no change to the function's existing single-identity path.
6. **`music_digest` (`family_contracts.py`:164–187) hashes onset, duration, written pitch and tie per part plus tempo and metre — it has no articulation input at all, so it is unaffected by removing a `Fingering` articulation, by construction, not by measurement.** This is the fact that makes Premise 5's relation apply cleanly: every one of the 43 families' items will have an *identical* digest before and after the fix (no item is "changed" by this lane's own test, `TestIdentity.test_one_identity_is_one_piece_of_music` and `test_a_family_s_music_changes_only_with_its_version`'s digest half), so the continuity relation carries every item, not a subset the way CL15's original bump had to split changed from unchanged siblings. One consequence worth stating in the handoff, not hiding: `identity_pins.json`'s family-level pin (`test_a_family_s_music_changes_only_with_its_version`) asserts `contract(family)["version"] == pin["version"]` *and* a hash of all items' digests matches `pin["digest"]` — after this lane, the re-pinned `version` moves (because the contract version bumps) but the re-pinned `digest` is bit-identical to the old pin's, which is itself a useful, checkable confirmation that no music changed, not merely an assertion of it.
7. **No evidence or requirement consumer in the app reads printed fingering as a measured or taught fact — checked, scoped to where a demand, skill or curriculum concept could plausibly read it.** A search of `app/src/demands/`, `app/src/evidence/`, `app/src/curriculum/` and `content/curriculum/vocabulary/*.json` for "finger" finds no detector, demand or skill definition that reads a `Fingering` articulation or a `fingering` field as evidence (`detect.ts`'s only "finger" hits are the *pitch-span* heuristics "five-finger position" and `range.beyond-position`, both computed from which keys are struck, never from what is printed over them — `content/curriculum/vocabulary/skills.json`:101 says this explicitly of the interval-reading family's own first-note marker: "Pitch is the observable... that it shows reading by interval rather than by name rests on the material and the conditions, not on the measurement"). Every other "fingering" hit in `app/src` is a renderer, a score-model extractor, a per-user display setting, or one dev-only diagnostic screen (`DevMicroscopeScreen.ts`:903, echoing the contract's own `printed`/`source`/`note` fields for a developer, not a learner) — none of them is an evidence or requirement consumer in the never-teach-wrong sense, so **no exception is found or needed**; this is a scoped absence (the four locations named), not a claim that nothing anywhere ever reads it.

## Constraints taken as given

1. **Print none until sourced, for exactly the 43 rows named above.** The product decision (`responses/questions-53670d2a.md` §3, reaffirmed `questions-90b19bee.md` §1). Not reopened; "one bounded pianist review may set reusable pattern policies" is explicitly not this lane (no pianist is in this process).
2. **No new identity system, no new schema, no byte- or notation-identity claim between the pre- and post-fix artifacts.** `questions-90b19bee.md` §1, verbatim. The existing `provenance.formerGeneratorIdentities` relation (CL15) is reused, generalised by one function to carry more than one element per item where a family has already been bumped once (Premise 5) — this is using the existing field's existing plurality, not adding a field, a table, or a second relation.
3. **Exact/current identity moves; learner continuity does not.** The regenerated 43 families' items get a new family version (their generator identity's `version` component changes); every item's prior encounter, competence and contact history resolves through the continuity relation to the new identity exactly as CL15's did for its unchanged siblings — with no family in this lane dropped from continuity, since Premise 6 shows no item's music digest changes.
4. **No content acquisition, no pianist review, no pattern-policy design.** This lane prints nothing new and sources nothing; it only stops printing what the family contracts already admit has no source.

## Hypotheses and their refuting tests

1. **Removing the `Fingering` articulation changes no item's `music_digest` in any of the 43 families.** This is the load-bearing claim for the whole relation (Premise 6). **Refuting test:** for at least one item per family (ideally every item), compute `music_digest` on the plan before the fix and again after, byte for byte equal; if any family's digest moves, that family's items are "changed" music by this codebase's own definition and the continuity relation would correctly *not* carry them — which would mean the family's fix is doing more than removing an annotation, and the brief's premise is wrong for that family specifically (stop and report which one, don't force it through).
2. **No family among the 43 has a same-pitch fast repeat that currently passes `physical_faults`'s repeated-note check only because of the printed finger change, and none needs a new `repeatedNotes` declaration.** (Premise 4.) **Refuting test:** run the real build for all 43 families after the generator change and before the contract flip would matter — i.e., with fingering already stripped from the output — and read every `PhysicallyIndefensible` failure. A family that fails here is a genuine finding: either it gets a true, specific `repeatedNotes` solution stated in its contract (e.g., a declared reason the repeat is fine without a finger change — not invented to make the gate pass), or it is reported as a found question, not silently special-cased.
3. **Four families — `tremolo_octaves`, `pentatonic`, `interval_reading`, `walking_bass` — already carry a CL15-era `formerGeneratorIdentities` entry in the current built catalogue, and a naive second bump (reusing `scripts-continuity_table.py`'s single-identity capture unmodified) would silently drop it.** **Refuting test:** load the current `catalog.json` (or re-run the build at current HEAD) and read each of these four families' items' `provenance.formerGeneratorIdentities`; confirm it is non-empty today. Then simulate the proposed capture for the second bump and confirm whether the resulting `generator_continuity.json` entry for these families would, if used unmodified, produce a `formerGeneratorIdentities` list on the *new* build that no longer includes the original (CL15-predates) identity. If true (expected, per Premise 5's reasoning), the capture step for exactly these four families must read and union the existing list, not just the version-just-left identity; the other 39 families need no such union (they have never been bumped before this lane).
4. **No evidence/requirement consumer depends on printed fingering (Premise 7).** **Refuting test:** the grep already run (scoped to `app/src/demands`, `app/src/evidence`, `app/src/curriculum`, `content/curriculum/vocabulary`) finds nothing; the builder re-runs it at dispatch-time HEAD (code may have moved) and also checks `tools/content/` Python-side consumers of `measurement`/`demands` for a "finger" read, which this research did not check as thoroughly — if either turns up a real consumer, that consumer is returned as the stated exception (not fixed, not silently carried), per the ruling's own instruction.

## What to build (decided)

1. **Before touching any contract file:** regenerate the real build at current HEAD and read, per family among the 43, whether any item already contains a same-pitch repeat under `FAST_REPEAT_SECONDS` that depends on a printed finger change to pass `physical_faults` (Hypothesis 2). This is the evidence Hypothesis 2's refuting test needs and determines whether any family needs a stated `repeatedNotes` solution before its contract can safely move to `"none"`.
2. **The fingering-removal mechanism, in `generate_exercises.py`.** Stop appending `articulations.Fingering(...)` for the 43 named families' recipes. Two shapes are both acceptable and the choice is the builder's (Premise 3; no product-semantic difference, no separate review needed, `operating-procedure.md` §11): (a) condition each of the family's own call sites on the contract's `printed` field, matching the existing G49 precedent (:1763–1775) family by family; or (b) a single centralised step — reading `family_contracts.contract(family)["physical"]["fingering"]["printed"]` once per item and stripping every `Fingering` articulation from the built score before `confirm_physical` (:870–888) reads it and before `write` (:898–914) persists it — which has the advantage that the *existing* build gate at `family_contracts.py`:499 ("prints fingers and the row says none") becomes an automatic, exhaustive verifier that every one of the 43 families' output is actually clean, rather than relying on not having missed one of dozens of scattered call sites. Whichever shape, the result is checked the same way (Acceptance, below).
3. **`tools/content/family_contracts.json`:** for the 43 named rows, `physical.fingering.printed` becomes `"none"`; the existing unsourced note stays (it is still true and still informative) or is tightened to say the number is no longer printed, the builder's call; `fingeringVerified` on any affected recipe, if set, is left as `false`/absent since no gate reads it once `printed` is `"none"` (Premise 1's two gates, :503–506, only fire for `"where-sourced"`). Each of the 43 families' `version` in the same file is incremented by one (Constraint 3) — independently per family, exactly as CL15 bumped five families independently in one lane.
4. **`tools/content/generator_continuity.json`:** a new capture, analogous to `scripts-continuity_table.py` but run against the *current* (pre-G30) built catalogue rather than a plan snapshot, since every one of the 43 families' current rows already has real `review.generator_identity` and real built files to hash with `music_digest`. For 39 of the 43 families (every one except `tremolo_octaves`, `pentatonic`, `interval_reading`, `walking_bass`), this is exactly CL15's shape: one identity and one digest per item, keyed to the version being left. For the four already-bumped families (Hypothesis 3), the capture additionally reads each item's *existing* `provenance.formerGeneratorIdentities` from the current catalogue and unions it with the version-just-left identity being captured now, so the new table's entry for these items carries the full chain. `tools/content/family_contracts.py::former_generator_identities` is generalised by the minimum needed to pass that union through (it already returns a `list[dict]`; today every call site populates it with exactly one element — the change is in what the *table* stores for these four families and in not assuming the stored value is a single dict, not in the function's return type or its callers in `build.py`, which already iterate a list).
5. **`tools/content/tests/fixtures/identity_pins.json`:** the 43 rows' `version` field moves to match the new contract version; `digest` stays the value already there (Premise 6) — the re-pin is a version bump with a byte-identical digest, which the test itself (`test_a_family_s_music_changes_only_with_its_version`) then proves, not merely states.
6. **`tools/content/tests/test_family_contracts.py`:** `TestGeneratedIdentityContinuity` (:506) gains a case for the multi-hop union (Hypothesis 3) built on one of the four already-bumped families, alongside its existing per-bump cases (:517, :532, :555, :565); the existing physical-fault test (`TestTheMutationCensus` or the dedicated fingering test, whichever currently exercises :499's gate) gains a case per affected family confirming `physical_faults` finds zero fingers where the contract now says `"none"`.
7. **`app/tests/unit/generatedIdentityContinuity.test.ts`:** a case proving `learnerMaterial`/`learnerMaterialKeys` resolve a *pre-CL15* stored identity for one of the four multi-hop families all the way to the new (post-G30) current identity in one lookup — the TS-side proof that the union in step 4 actually closes Hypothesis 3's gap, not just that the Python table contains it.
8. **Content itemisation (the owner's rule, `operating-procedure.md` §12):** this lane does not change what a lesson teaches, which songs a rung offers, or any taught claim — it removes an unsourced annotation from generated files. The itemised list for the reviewer is therefore one line per affected family (43 lines), not per note: family name, old `printed` value → new, old version → new, and the reason ("the generator's own convention, not a published source" — quoting the row's own prior note). This is itemised in full in the handoff even though no curriculum-fact or lesson-sentence changes, because the generated file's bytes do change for every item of every one of the 43 families and the owner's rule asks for that to be visible, not inferred from a diff stat.
