## The goal, in the orchestrator's words

The app knows what a learner has played, because every run is a row, and since D4 it knows which material that run was. It does not know what the learner has heard or looked at: the Score screen remembers a hearing for one visit and stores nothing, so a phrase played to the learner today and read tomorrow goes on the record as a first reading; a notated piece or an import carries no first-contact fact at all; and the only "seen" the store holds is the sight-reading flag on generated runs. Part 27 asks for one factual encounter history over the build's material identities — viewed, heard, demonstrated, attempted, practised, performed, when, from where — with runs staying the record of runs and the smallest possible complement for what is not a run, so that sight-reading's strict rule is derived from history, D4's contact can say *heard* as well as *played*, an excerpt over practised bars does not restore novelty, a duplicate import does not either, and the lifecycle that follows (G1b) can never become a second source of truth for what was encountered. After G1 the app has that history and its one query, the Score screen writes to it and reads from it, the sight-reading run still stores the fact it was judged on, and every consumer that later needs familiarity asks this one place.

## What is decided

1. **The store.** A new `encounters` object store (`DB_VERSION` 8, an upgrade that creates it and touches no other store) with rows of `{ id, material: Identity | { kind: 'id', itemId }, itemId, kind: 'viewed' | 'heard' | 'demonstrated', at, source, bars?: [from, to] }`. Only non-run kinds are stored here: `attempted`, `practised` and `performed` are derived from `SessionRow` (a run with evidence, a run without, `performance: true`), never copied. `demonstrated` is a hearing the app made as a demonstration (`Hear it`, a bar held down, the lesson's or the excerpt view's *Hear it* on the learner's side); `heard` is any other playback to the learner (*Play it to me*, a Listen run); `viewed` is the notation drawn for the learner on the Score screen, written once per visit with its `source` (Today, a lesson, the Library, the swap sheet, an offer) and a **visit id** (the reviewer's constraint: a timestamp cannot tell the same-visit view that reading needs from an earlier one; the id is minted when the screen opens and stored on the row, and the first-contact derivation compares ids, with tests for a reload, back-and-return, and two tabs). **Hearing kinds follow the user's action:** `Hear it` and a held bar write `demonstrated`; *Play it to me* and a Listen run write `heard`; one playback never writes both, and the query derives `heard` as the superset explicitly where a consumer wants "any playback". Rows are small and never pruned by the sessions cap; they are part of the backup (`exportAll`/`importAll`) and so follow a restore, and a fixture round-trip proves it. **Durability of run contact** (the reviewer's constraint on D4, `responses/9193261.md`): deriving attempted, practised and performed from `SessionRow` is incompatible with "never pruned" while the sessions cap can delete the run whose material is the only proof an item was met (G63). G1 resolves it in the contract, as the reviewer required on this brief (`responses/7863bee.md`): **one mechanism, the compact summary before deletion.** `SessionRow` stays authoritative while a run is present; the retention job, before it deletes a run, folds the facts `familiarity` would otherwise lose — material (or the id-only fallback), the covered passage as printed parent scope, kind, time, source — into one durable summary row per material (`contacts`, in the same new store or beside it), idempotently (folding the same run twice changes nothing; a summary never grows by copying live runs), holding only the durable encounter projection and never evidence; the backup carries it. **The facets are defined by what happened, never by evidence:** every started or completed run is an *attempt* by the threshold already in the run record (the builder names the field); an ordinary practice run is *practised* whether or not it produced usable evidence; *performed* comes only from the run's performance contract (`performance: true`); evidence presence, passing and first-contact eligibility never rename an encounter. **Legacy rows** (no material) fold by id only, and the summary says so (`byId`). **The retention adversary:** practise a passage, force its session row through the real pruning path (the job as it runs, on a fixture store past the cap), then prove the material and the covered passage remain attempted and practised, the other passage remains novel, D4's `contact` still says `met` with `how`, and a backup taken after the pruning restores the same answer.
2. **The identity.** The material is D4's `Identity` where the item has one (`materialOfItem`); an import gains a file identity here — the sha256 of the stored score's bytes as the Score screen loads them (`material.ts`, replacing D4's `none` for imports; D4's `runFacts` then writes it on the import's runs too), so a duplicate import under a new id is the same material; an item with no identity (a drill made when it opens) is recorded by id. Passage scope: `bars` on an encounter names the printed range it covered (a bar held down, a section played to the learner); absent means the whole. A query for a range is met only by an encounter that covers it; an excerpt's familiarity consults its parent's encounters over the cut's printed range (`excerptOf`) as well as its own material, and the whole parent played makes its unchanged excerpt familiar while excerpt A played leaves excerpt B novel.
3. **The one query.** `encounterStore.familiarity(target)` over the store and the session rows: `{ viewed: at | null, heard: at | null, demonstrated: at | null, attempted: at | null, practised: at | null, performed: at | null, byId: boolean }` for a material (or an id, when that is all the caller has), reading the identity hierarchy where the catalogue names it (the composition of an arrangement: another arrangement heard makes the composition `heard` in the query's `composition` facet and leaves the notation `viewed: null`). No booleans named "familiar" or "novel": the consumer decides what its purpose needs from the facts.
4. **Sight-reading's first contact, derived.** The Score screen decides a generated phrase's `unseen` from the query and the visit — first contact means no run of that material, no `heard` or `demonstrated` of it on any visit, and no `viewed` of it on an earlier visit (looking at the phrase before reading it in this visit is what sight-reading is) — and keeps writing `unseen` on the run so the claim can be audited (S8); `seedsOnRecord` stays as the seed-drawing guard, `phraseHeard` stays as the fast path within a visit, and the store is what survives the visit. A notated piece's first reading gets the same fact on its run for the first time (`unseen` written for notated and imported material, read by nothing new in this seam: G2 and X read it).
5. **D4's contact extended.** `progressStore.contact` reads the encounters as well as the runs: `met` gains `how: ('played' | 'heard' | 'demonstrated' | 'viewed')[]`; the transfer offer's "unmet" (D4 item 4) keeps its meaning — unmet by any kind — and its existing cases keep their verdicts. The evidence context's `firstContact` keeps reading the run's `unseen` (item 4 now writes it truthfully); the ladder is untouched.
6. **The adversaries at this layer** (Part 27's, held here, the rest named for G1b): view without playing (`viewed`, not `practised`); hear before playing (no first-contact evidence later: the run's `unseen` false, the ladder never sees `firstContact`); practise bars 1–8 (bars 25–32 still novel); an excerpt over practised bars (no reset through the parent's range); a duplicate import (no reset, by file identity); another arrangement heard (the composition `heard`, the notation not claimed read); a new seed of the same family (realisation-novel, D4's `unmet` with `metById`, unchanged); a planned sight-read heard at noon from the Library and read in the evening (the run says not first contact — the session's own recheck is X's, L32); the same passage after a backup restore (the history follows the learner). Nothing but a viewing or a hearing writes a non-run encounter: no status, no lifecycle action, no assignment. Save without opening, retired-and-returned, one play creating no project, "learn this" before success and pausing deleting nothing are G1b's, and the brief for G1b says so.
7. **Legacy.** Rows before G1 have no encounters: the query answers from runs alone and says `byId` where the run has no material, as D4 does; nothing is manufactured. C7's exposure rows are skill exposure, not material encounters, and are not read here.
8. **Not G1's:** the repertoire lifecycle and its actions (R19, R47, L86, R18: G1b); the session's contact-assumption snapshot and recheck (L32: X); lesson pages read (an encounter with a lesson, not with material: later); the transfer policy (G2); `ProgressRow.status` (left as it is; never the bridge); any screen beyond the Score screen's writes and the Progress history line; `importStore.ts`, `eligibility.ts`, `candidates.ts` (E2's, building); the stage files and lessons (F2's, building).
