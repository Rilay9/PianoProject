## The goal, in the reviewer's words

The import door explicitly accepts either `<score-partwise>` or `<score-timewise>`, and the trimmer treats both as supported forms. The canonical reader explicitly does not read the timewise form: its part traversal finds no `<part>` container around measures in a timewise document, so its events are empty. A timewise file can render through the accepted import path while its written opening tempo and later changes are replaced by the app default in the score model, and the import sheet also reports no written tempo because it calls the same empty reader — the exact contradiction X3d is meant to remove, on an uncovered branch of the door's declared input contract. Make the one reader handle `score-timewise` with the same event, precedence, opening and position rules, or make the import boundary convert timewise to the canonical partwise representation before any tempo consumer runs. Do not add a second tempo reader or silently reject tempo only. Add a real-path regression proving a timewise opening mark and `<sound tempo>` and a genuine later change produce the same sheet text, label, playback and count-in and map as their equivalent partwise score. X24 and X29 remain open until this hole is closed.

## What is decided

1. **The one reader reads both forms.** `tempoFromXml.ts` detects the root form and, for `score-timewise`, walks `<measure>` → `<part>` (the inverted nesting) to yield the same `TempoEvent`s — the same measure index, offset (through backup, forward, chords, graces, divisions and sounding offsets, as the partwise walk does), normalisation, `<sound tempo>` precedence at the same position, opening rule (a tempo before any sounding note opens the piece; a first tempo after sounding notes is a change at its position) and skip rules (metric modulations, the `<metronome-note>` form, marks without a number, words alone, comments). One traversal contract, two nestings; the module note corrected. The orchestrator chose the reader over a boundary conversion because the store's writer and the trimmer stay untouched and no second representation enters the app; if you find the conversion smaller and safer (one function, the partwise text handed to every consumer), say why and take it — but then every consumer, including the sheet, must read the converted text, and E48's writer must still find its place in what the store keeps.
2. **E48's writer on a timewise file.** `withOpeningTempo` writes a `<sound tempo>` beside each mark's direction or at the opening; confirm where it writes in a timewise document and that the reader finds it (the opening rule and precedence hold). If the writer places it where the reader does not look on the timewise form, the fix is on the reader's side unless the writer's placement is wrong on its own terms; say which.
3. **The regression on the real path, red first.** A helper that turns a partwise fixture into its timewise twin (a mechanical re-nesting of the same content, checked by round trip), and for each of X3d's adversary shapes that matter here — an opening mark with a `<sound tempo>`, a mark alone, an opening sound not displaced by a bar-2 mark, a genuine later change, E48's stated tempo written into the file — the timewise twin gives the same `tempoEvents`, the same model map through the real extraction, the same Score label and count-in (the harness X3d used: `scoreModelTempo.test.ts`'s pattern), and the same import-sheet sentence. Red on the committed reader: the timewise twins read no events and the sheet says the file writes no tempo. A browser case on port 4373 is only needed if the sheet's words or the Score label are not already proved by the unit harness; say so either way.
4. **The corpus and the door.** Say whether any bundled score is timewise (search `app/public/content/scores` for `<score-timewise`); and what a learner importing a timewise file saw before (the default tempo, the sheet saying no tempo written) and sees after.
5. **Not X3e's:** `<sound time-only>` (a later wave, the reviewer's ruling); X31 and the store's regex `writesTempo` (later waves with their owners); OSMD's tempo heuristics (never a fallback); any change to the partwise rules as accepted.
