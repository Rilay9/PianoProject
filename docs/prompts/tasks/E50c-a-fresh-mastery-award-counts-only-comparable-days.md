## Hypothesis and its refuting test

**Hypothesis.** `recordRun`'s fresh mastery transition (`progressStore.ts`:242) treats every date already in `masteredOn` as equally valid toward `MASTER_DAYS`, without asking whether the day's supporting run's tempo channel is comparable to the item's *current* standard. For a tempo-repaired item, a day recorded before the repair (against the old file, at the converter's defaulted tempo) is exactly the kind of run `rungState.meetsStandard` already refuses when judging a rung today (`tempoNotComparable`, premise 7); `recordRun` never asks the same question, so that old day can combine with one new comparable day to reach `MASTER_DAYS` and wrongly flip `status` to `'mastered'`.

**Alternative hypothesis, and why it is wrong.** The old run's `masterEligible: true`, as the Score screen computed it at record time, was itself a mistake and belongs fixed at the screen, not the store. This is refuted by the reviewer's own placement of the fix ("`recordRun` still computes a **new** `mastered` transition...") and by the mechanism itself: before the repair existed there was no tempo-repair standard to violate, so the old run's `masterEligible` was a legitimate judgement under the rules of its own day. What is wrong is reading that day's contribution against *today's* repaired standard — a question only `recordRun`'s own threshold check asks, and only at the moment it asks it.

**The refuting test** (must be red on HEAD `e71ef3ad`, green after the fix):
- Record a run for a tempo-repaired item's id, on an old day, with `material` naming the pre-repair file (one the loaded catalogue lists in `provenance.tempoRepairedFrom`), `baseTempo: {bpm: 96, source: 'defaulted'}`, `masterEligible: true`.
- Record a second run for the same item, on a later day, with `material` naming the repaired file, `baseTempo: {bpm: <the written tempo>, source: 'written'}`, `masterEligible: true`.
- Assert the returned row's `status` is **not** `'mastered'` (still `'passed'`), and that `masteredOn` still lists both dates — history kept, neither rewritten nor dropped.
- Control: the same two calls, but with the repaired material on **both** days (no old-file day at all), must still produce `status: 'mastered'` — the guard refuses an incomparable day, it does not raise the bar past `MASTER_DAYS`.
- Control: the existing non-repaired-item cases (`recordTruth.test.ts`:62–86) must be unaffected.
