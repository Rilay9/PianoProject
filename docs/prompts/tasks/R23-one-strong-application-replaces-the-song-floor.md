## Premises at the lines (HEAD `889afb94`)

1. **The floor is a raw count, enforced at one function, mirrored at three more.** `tools/content/validate.py`:57: `MIN_OPTIONS = 3`, with its own comment at :51–56 citing `docs/00 D21`. `thin_lesson_errors` (:631–667) is the actual build-failing gate: a lesson whose rung asks for a song run (`required_songs`, :646–648, true when a requirement's `kind == "runs"` and `from == "songs"`) fails the build when `len(songs) < min_options` (:662–666) — a bare count, nothing about what the songs teach. `write_needs` (:1951–1996) computes the *learner-facing* shortfall (`need_songs = max(0, min_options - len(songs))`, :1988) that the build writes onto `lesson.needs` — **this branch has no `required_songs` check at all**, unlike `thin_lesson_errors`. `tools/content/ladder_report.py`:32 (`OPTION_FLOOR = 3`) and :133 mirror the same number for the human-readable ladder report. `app/src/curriculum/selectors.ts::thinLessons` (:282–298) mirrors `thin_lesson_errors`'s logic exactly, `required_songs` check included (:292: `!asksForSongs(lesson) || lesson.songOptions.length >= minOptions`) — for the on-device Diagnostics screen (`DiagnosticsScreen.ts`:683, "docs/04 §7b"). `app/src/curriculum/needs.ts::lessonShortfall` (:40–53) mirrors `write_needs` exactly, **without** the `asksForSongs` check either — it is read by `LessonScreen.ts`:337 and is what a learner actually sees as "wants one more exercise" on the lesson page.
2. **A found inconsistency, not yet a defect anyone has noticed: the learner-facing sentence can claim a song shortfall a rung never asked for.** Following directly from Premise 1: a lesson whose rung requires no song run at all (`required_songs` false — Stage 0's checklists, improvisation and theory rungs per `thin_lesson_errors`'s own comment, :635–637) with fewer than three `songOptions` still gets `needs.songs = max(0, 3 - len(songs))` written by `write_needs` and read verbatim by `lessonShortfall` and the Lesson screen — a sentence the build's own gate (`thin_lesson_errors`) and the Diagnostics mirror (`thinLessons`) both agree is not actually required. **This is the exact file and function this lane is already rewriting**, not a scope expansion: once `write_needs`/`lessonShortfall` change shape for R23 anyway, they gain the same `required_songs`/`asksForSongs` gating the other two already enforce, so the three readers agree once more. Decided by the orchestrator: fix this inside the rewrite, not as a separate lane — the ruling that an implementation choice already entailed by the existing code contract (three of four readers already agree; the fourth is being rewritten regardless) needs no separate review round (`operating-procedure.md` §11, "The orchestrator may settle a decision that is already entailed").
3. **A checkable "strong" already exists in the codebase and does not need to be invented.** `claims.py`:252–281 (`rung_claims_of`) derives a lesson's measurable claims from its `concepts` (via `skills.json`/`CONCEPT_DEMANDS`) and from `demands.json`'s `taughtAt`. `claims.py`:308–330 (`CHECKED`, `status_of`) classifies each option against each claim as `established` (measured demands provide it at a useful density, `measurement.established`), `incidental` (present, below density), or `absent`. This is exactly the needs-versus-taught gate the decision's own source names (`audit-2026-09-25-outside.md`:1143–1150, point 5: "can the learner cope with this material, and does it provide the opportunity the rung claims"). The generated `docs/prompts/rung-claims.md` already runs this over the whole built catalogue and prints, per rung, which options establish which claims (sampled: the jazz.7 table lists each option's `Establishes` column, established/incidental/absent per claim). "Strong" for R23 is defined as: **the option establishes at least one of the lesson's own claims** — not merely contains notes, not merely is catalogued at the right level.
4. **The app's own eligibility gate (`eligibilityCore.ts`) answers the identical question at runtime, independently.** `app/src/curriculum/eligibilityCore.ts`:202–230 (`opportunity`) and :258–320 (`establishedQuestions`) compute, for a candidate item and a wanted demand or skill, whether the opportunity is `established` or merely `incidental`, the same established/incidental distinction `claims.py` computes at build time. **Claim to verify, not yet checked by me:** whether `claims.py`'s build-time classification and `eligibilityCore.ts`'s runtime classification are provably the same computation over the same inputs, or two independently maintained readings of `measurement.established` that happen to agree today — if the latter, this is a second "one fact, several places" the builder should name even if fixing it is out of this lane's scope (it is not this lane's gate to rebuild; `eligibilityCore.ts` belongs to CL11's cluster, not CL10's).
5. **`required_songs`/`asksForSongs` already distinguishes "this rung needs a song" from "this rung does not."** `thin_lesson_errors`:644–648's comment: "Whether the rung asks for a run of one of its songs (C5's requirement that replaced `songsRequired`)." A lesson with `songOptional: true` or no `runs`-from-`songs` requirement is already exempt from any song-specific count (:655–661, :162–167). R23's new rule applies only where `required_songs`/`asksForSongs` is true today — it does not change which lessons ask for a song-shaped application at all, only what counts as satisfying that ask.
6. **`docs/02-curriculum.md`:74 bundles two separate facts in one bullet; only one of them is this lane's.** The sentence: "Each lesson offers three to six songs and at least two exercises; the learner passes the lesson by mastering **any one song + any one exercise** (configurable to 'two songs' for thoroughness)." The first clause (three to six songs, the authoring quota) is R23's; the second (mastery requires one song + one exercise, optionally two songs) is a *pass/fail* rule read elsewhere (`app/src/data/carryOver.ts`:72–73, `requireTwoSongs`; `app/src/evidence/rungState.ts`:380–381, `songOptions.length >= 2`) and is **not** touched by this lane — R23 changes how many song options a rung curates and what makes one count, never how many a learner must play to pass. The edit to :74 touches only the first clause's number and its "songs" framing; the second clause's sentence stays.
7. **Where the real-music-first check applies here.** §12's rule binds any brief that "adds or keeps generated material for a musical skill." The decision's own list of what may satisfy "one strong application" includes both "an authentic excerpt" and "a technical study, a generated study" side by side, with no stated preference — but §12 itself states one: "Prefer repertoire first for... phrasing... and other style/application work; prefer generation where exact constraints, graduated variation, transfer testing, availability/licensing or the learner's measured need make control more valuable." R23 is precisely application-experience selection, so this lane's "strong" check, where both a real option and a generated option could establish the same claim for the same lesson, prefers the one that already establishes it with the least invented material — i.e. a real song/excerpt first, a generated study only where no real option establishes the claim at that level (the corpus a `rung-claims.md` re-run already shows) or where the lesson's own concept is better isolated by exact control (the same narrow case §12 already carves out for drills). This is stated as policy for "what to build" item 2 below, not as a new per-item sourcing audit — CL18 (repertoire supply) owns finding *new* real material; this lane only orders the choice among options a rung *already has*.

## Constraints taken as given (each with its source and what it protects; the costliest has an alternative measured)

1. **A lesson's application is chosen from its rung's option lists** (the curriculum's rung/option structure). It protects the existing curriculum shape and the learner's choice. Kept.
2. **"Strong" is `claims.py`'s established classification**, not a new detector (the decision's own wording, `backlog-2026-09-25.md`:508). This is the costliest constraint, because a measured demand is a proxy for "teaches the concept": Hypothesis 1's refuting test checks every application kind the decision names has a representation in that classification, and the handoff names any option the classification calls established that a reader of the score would not (one example each way, from the regenerated report), so the proxy's limits are stated, not assumed.
3. **Weak options stay as depth and choice; nothing is pruned for weakness alone** (the audit's Part 12). It protects the Library's depth. Kept; a removal needs its own stated reason.

## Hypotheses and their refuting tests

1. **Redefining "strong" as `status_of(...) == "established"` (Premise 3) is sufficient to satisfy the decision's text without a new detector or a new data field.** Every concept named in the decision's list (whole piece, authentic excerpt, technical/generated study, creative/harmony task, accompaniment, ear/transfer task) already reduces to a catalogue item with measured demands (`measurement.established`) or, for a non-notated task (an ear or creative task), to a runtime item the existing report already marks `— (runtime)` and counts apart (confirmed in the `rung-claims.md` sample: "Chord–scale... | runtime | — (runtime) |"). **Refuting test:** regenerate `rung-claims.md` against the current build and check whether any item the decision's list names (specifically a "creative or harmony task" or an "ear or transfer task") has no representation at all in the report's existing categories — if one exists that the report cannot classify as established/incidental/absent/runtime, the definition needs a fourth bucket before this lane can build against it, and that is found before the validator is rewritten, not after.
2. **The existing `required_songs`/`asksForSongs` boolean is the right unit to rewrite, not a new per-lesson field.** The decision text never asks for *more* song-shaped application options, only a different criterion for the ones a rung already requires. **Refuting test:** grep `content/curriculum/stage-*.json` for every lesson with a `runs`-from-`songs` requirement and confirm each already has a `concepts`/`taughtAt` set `claims.py` can resolve to at least one claim (Premise 3's machinery needs something to check an option *against*) — a lesson with `required_songs: true` but no resolvable claim at all would fail the new rule for every option, including a perfect one, which is a different, pre-existing problem (worth naming, not silently working around with a fallback).
3. **Regenerating the real build's `rung-claims.md` and re-running the new validator rule against it will show exactly how many of today's rungs already pass and how many newly fail**, and that number is knowable before any content is touched. **Refuting test:** this is the first thing built (below), before any JSON edit — if the count of newly-failing rungs is large enough to be a content project of its own rather than a short itemised list, that is reported as a finding, not quietly absorbed into this brief's scope.
