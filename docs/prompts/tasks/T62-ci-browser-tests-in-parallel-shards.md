## What is decided

1. **The goal, in the owner's words and mine.** The owner's: the run takes over an hour, the browser tests are most of it, split them into parallel shards so the whole run is markedly faster. Mine, read against the code above: the same `npm run e2e` test set, divided by `--shard=i/N` across N jobs that each restore rather than rebuild the content and app-build work the first job already did, with the two post-E2E content-mutating steps (render-check, the second validation) kept together, in order, after every shard has finished — not parallelised themselves, since `render_check.py --apply` writes to the catalogue and a second, unsharded validator reads what it wrote, and nothing in this brief re-opens that ordering.

2. **The job graph's fixed shape; N and the exact step split are the builder's, by measurement.** Corrected per `responses/questions-53147902.md` §A and `correction-2.md`'s T62 correction 2 — every job below is a fresh GitHub Actions runner with nothing but what it checks out or restores; no state leaks between jobs except through an explicit artifact.
   - **Job 1** (keep the existing steps, in the existing order, minus "Install Playwright Chromium"): checkout → setup-node → setup-python → restore content-build cache → install Python deps → `npm ci` → Build content → Content pipeline tests → restore/fetch/save MAESTRO → MIDI converter harness → write the MIDI parity reference → generate icons → Lint → Typecheck → Unit tests → **build the app** (`npm run build:app` or `build`, the builder's call) → **two same-run uploads**, each serving a different downstream reader: `app/dist/` (what every shard's `webServer` serves), and a `content-and-render-state` artifact holding `app/public/content/` and `build/render-manifest.json` (what Job 3's `render_check.py`/`validate.py` read, and, for the catalogue, mutate — see "Read first" above for exactly why these two and nothing more). Job 1 never runs `render_check.py`, so the `render-manifest.json` it uploads is exactly what the existing "Restore content build cache" step handed it at job start, unmodified; Job 3 reads those identical bytes from Job 1's own run through the artifact, never by restoring the cross-run cache a second time itself — that substitution is what §A forbids, since a cache hit, miss or save-timing difference between two independent restores is not the same guarantee as "the bytes the producing job actually wrote this run."
   - **Job 2, a matrix of N**, a fresh runner (`correction-2.md` T62 correction 2): checkout the same commit as Job 1 → setup Node → install the app dependencies (`npm ci`) → restore Job 1's exact `app/dist` artifact → install or restore Chromium (the existing `actions/cache`, keyed on the Playwright version; the install step still runs on a cache miss) → run the shard (`run: npm run e2e -- --shard=${{ matrix.shard }}/${{ matrix.total }}`, Decision 4) with the prebuilt-app flag (Decision 3) so the `webServer` serves the restored `dist` instead of rebuilding it → upload that shard's blob report (test-level identity and attachments, Decision 5/§1) as a per-shard artifact, `if: always()` at the step level so a failed or retried test's report and trace are retained regardless of the shard's outcome (Decision 3's `trace: 'on-first-retry'`, folding in §D and correction 1's diagnostics ruling). The checkout supplies the test files, `playwright.config.ts` and `package.json`; the artifact supplies the exact built bytes — `app/dist` alone has neither `package.json` nor `tests/e2e/**` to run against, so neither source substitutes for the other. N starts at 3 or 4 and is set by what the builder actually measures — not a number asserted here as general.
   - **Job 3**, also a fresh runner, with an ordinary `needs:` on Job 1 and on the shard matrix, so it runs only when every shard has passed, exactly as today's single job skips Render and Validate after a browser failure (this keeps render-then-validate after the browser gate, the ordering the reviewer kept): checkout the same commit → setup Node → setup Python and the content tooling's dependencies (`validate.py` needs music21, and without it skips two of its checks without failing, per the second read at `docs/review/second-reads/0d2c3472.md` item 3) → `npm ci` → restore Job 1's `app/dist` *and* `content-and-render-state` artifacts → install or restore Chromium (`render_check.py` is itself a Playwright invocation) → **Render every catalog item** (`render_check.py --apply`) against the restored `app/public/content` → **Validate again** (`validate.py`) against that now-mutated catalogue → **Upload content previews**, `if: always()` at the step level, `with:` block unchanged. Two facts from the second read bind this job. First, `content-render.spec.ts` loads each score from the served `dist` (:294) while `render_check.py` hashes the file under `app/public/content`, so the two copies must be the same bytes: Job 1 takes both artifacts after its last step that writes either (`npm run build` rebuilds content through its `prebuild` script), and Job 3 may skip the `webServer` rebuild only if the builder shows the restored `dist` and `app/public/content` match. Second, today the content cache's post-job save captures `build/render-manifest.json` after Render has updated it; with Render in Job 3, a save in Job 1 would capture a stale manifest and later runs would re-render those files (a time cost, not a correctness one), so the manifest's cache save moves after Job 3's render, the builder's mechanism, stated in the report.
   - **Artifact, not cache, for the job-to-job handoff — read and decided, not left open.** The existing "Restore content build cache" step is keyed on the content pipeline's *inputs* and exists to make a later, independent *run* faster; `pages.yml`/`render-full.yml` both restore the identical key independently — this step is untouched by this lane and must not become the channel Job 2's N shards or Job 3 rely on for identical bytes within one run. `actions/upload-artifact`/`download-artifact@v4` already does exactly this job in this same file (the `content-previews` upload) and guarantees the artifact a sibling job downloads is the exact bytes the producing job wrote, for this run only.
   - **Playwright's own Chromium binary** is a genuine cross-run dependency, not a same-run data handoff — `actions/cache` for it, keyed on the Playwright version, is fine, and each shard job *and Job 3* still needs the install step, since each is a separate runner.

7. **This is a workflow change; it is reviewed before it is pushed, and the builder never pushes it — proof mechanism corrected** (`docs/review/responses/questions-53147902.md` §C, which replaces this item's original `workflow_dispatch`-on-a-disposable-branch route outright). Per the owner's 2026-09-30 rule ("CI changes get reviewed," `operating-procedure.md` §11) this brief and the resulting diff go to the reviewer before any push to the working branch; the builder's worktree is never pushed, per §14, full stop.
   **Why the original route is not used:** GitHub documents that a `workflow_dispatch` workflow must exist on the repository's default branch, which is the working branch here, and its `ci.yml` has no `workflow_dispatch` trigger today. Whether a dispatch against a disposable branch would run with only that branch's trigger is unproven (second read, item 5), so this lane does not rely on it; the push-trigger route below works either way.
   **The corrected proof route:** a disposable, throwaway branch carries its own copy of `ci.yml` that temporarily adds that exact branch name to `on.push.branches` (alongside the working branch, not in place of it). After reviewer approval, the orchestrator pushes the candidate graph — this `ci.yml`, the `playwright.config.ts` changes, the rewritten `test_ci_order.py` — to that branch twice, and reads `gh run view --json jobs` on each ordinary push-triggered run; no dispatch is involved. A push to that branch gets its own `concurrency` group value (`ci-refs/heads/<disposable-branch>`, since the group name is `ci-${{ github.ref }}`), so it cannot take the working branch's one pending slot or otherwise touch the real Q63 contract — the same isolation property the original route claimed for `workflow_dispatch`, produced a different way. The proof-only branch name is removed from `on.push.branches` in the diff that actually lands on the working branch: it is scaffolding for the two proof pushes, not a permanent trigger, and the final diff is reviewed again (or confirmed unchanged from what was already approved) before that landing push.
