# T62 — CI's browser tests run as parallel shards: the single job splits into a content-and-unit job, N Playwright matrix shards (`--shard=i/N`), and a render-check-and-validate job, so the run's wall time drops without dropping a check (backlog T62, P2, `backlog-2026-09-25.md`; the next free after T61, confirmed free: no `T62` appears in any task file or backlog row; the measured baseline is run 36807990772 on `13e1b1a8`, 76m6s total, "E2E tests" alone 41m41s of it; tooling and CI only; a workflow change — sent to the reviewer before dispatch, and never pushed to the working branch by the builder at all)

## The problem

A push to the working branch starts one CI run (`.github/workflows/ci.yml`, one job, `build-and-test`) that takes over an hour, and the reviewer's evidence for a pushed tree — the thing the whole landing-chain/Q63 discipline exists to produce — arrives that late. ## What is decided

1. **The goal, in the owner's words and mine.** The owner's: the run takes over an hour, the browser tests are most of it, split them into parallel shards so the whole run is markedly faster. Mine, read against the code above: the same `npm run e2e` test set, divided by `--shard=i/N` across N jobs that each restore rather than rebuild the content and app-build work the first job already did, with the two post-E2E content-mutating steps (render-check, the second validation) kept together, in order, after every shard has finished — not parallelised themselves, since `render_check.py --apply` writes to the catalogue and a second, unsharded validator reads what it wrote, and nothing in this brief re-opens that ordering.

2. **The job graph's fixed shape; N and the exact step split are the builder's, by measurement.**
   - **Job 1** (keep the existing steps, in the existing order, minus "Install Playwright Chromium" — nothing before the app build needs a browser): checkout → setup-node → setup-python → restore content-build cache → install Python deps → `npm ci` → Build content → Content pipeline tests → restore/fetch/save MAESTRO → MIDI converter harness → write the MIDI parity reference → generate icons → Lint → Typecheck → Unit tests → **build the app** (`npm run build:app` or `build`, the builder's call, consistent with what `webServer` already runs) → **upload `app/dist` as an artifact**. One upload is enough: Decision item 4 below established that `app/dist` already contains the built content via Vite's `publicDir` copy, so there is no separate "built content" artifact to keep in sync with it.
   - **Job 2, a matrix of N**: `needs: job1`, downloads the `app/dist` artifact, `npm ci`, install Playwright Chromium, run the shard's slice, upload that shard's reporter output (for the spec-union check and for ordinary failure triage) as a per-shard artifact. N starts at 3 or 4 and is set by what the builder actually measures (below) — not a number asserted here as general, since the runner's own timing is what decides it, same discipline as everywhere else in this project.
   - **Job 3**: `needs: job2` (GitHub waits for every matrix instance and treats one failure as the matrix job failing — this alone satisfies "a failure in any shard fails the run," no extra wiring). Downloads the `app/dist` artifact (its own webServer rebuild cost on top of that is small and already measured today — see the note below), runs Render every catalog item, then Validate again, then uploads content previews exactly as today.
   - **Artifact, not cache, for the job-to-job handoff — read and decided, not left open.** The existing "Restore content build cache" step is keyed on the content pipeline's *inputs* (the scripts, the sources, the lockfile) and exists to make a later, independent *run* faster; a cache hit or miss changes how long the build takes, never what it produces, and `pages.yml`/`render-full.yml` both restore the identical key independently — this step is untouched by this lane and must not become the channel N shard jobs rely on for identical bytes within one run. `actions/upload-artifact`/`download-artifact@v4` already does exactly this job in this same file (the content-previews upload) and guarantees the artifact a sibling job downloads is the exact bytes the producing job wrote, for this run only — the right tool for "N parallel jobs must all start from the same one build," where a cache's best-effort, eventually-consistent semantics are the wrong fit.
   - **Playwright's own Chromium binary** is a genuine cross-run dependency (same class as `npm ci`'s cache), not a same-run data handoff — `actions/cache` for it, keyed on the Playwright version, is fine, and each shard job still needs the install step (each is a separate runner).

3. **Every shard's webServer must not re-run `build:app`.** `playwright.config.ts`'s `webServer.command` is `npm run build:app && npm run preview`, used by every invocation on CI, including each shard's. Left unmodified, every shard job would pay a full icons+`tsc -b`+`vite build` before its first test — not a correctness problem (the rebuild is deterministic and produces the same `dist` the artifact already has) but exactly the wasted, repeated work this lane exists to remove, and it is realistically close to the **"Build"** step's own measured 4m10s/4m50s, not the much smaller 21s/42s that today's single "Render every catalog item" step shows — that step's speed is best explained by `tsc -b`'s own incremental build-info cache still being warm from the "Build" step moments earlier in the *same* job; a shard starting cold on a fresh runner has no such warm cache. Fix: a narrow, CI-only conditional in `playwright.config.ts`'s `webServer.command` — e.g. a distinct env flag the shard jobs set, selecting `npm run preview` alone when the `dist` artifact is already in place, falling back to today's exact string in every other case (local dev, the render-check job, the tour/corpus/states configs, which have their own config files and are untouched). State the flag's name and show the default path is byte-identical to today's when unset.
   - **This is the one shared app file this lane touches**, and only for this one conditional; state in the report exactly what changed and that every other caller's command string is unchanged.

4. **The `npm run e2e` substring stays in every shard's `run:` line.** `docs/prompts/checks.json`'s `e2e` check has `"ci": "npm run e2e"`, and `test_ci_order.py`'s `test_ci_runs_every_check_the_path_map_names` asserts CI has a step whose `run`/`uses` *contains* that exact substring. This lane does not own `checks.json` (see "Not yours"), so each shard's step must keep that substring literally present — `run: npm run e2e -- --shard=${{ matrix.shard }}/${{ matrix.total }}` (or equivalent) satisfies both the sharding and the existing map entry with no edit to the map. Say in the report that this is why the shard command is phrased that way, so the next reader does not "simplify" it to a bare `playwright test` call and silently break the map's assertion.

5. **Unchanged guarantees, each an acceptance case, each independently checkable:**
   - **Every spec runs exactly once across the shards.** A step (in job 1 before the fan-out, or a cheap step of its own) records `npx playwright test --list --reporter=json` once; each shard's own run records what it executed; a check — in CI, not only locally — asserts the union of what the shards ran equals the full list with no duplicate and no omission. State in the report whether this is a script under `tools/` or an inline step, and show its output on both a passing and (locally, in the worktree, against a deliberately mis-sharded config) a failing case.
   - **The concurrency group and the Q63 contract hold for the whole graph.** `concurrency:` is a workflow-level key in GitHub Actions — it governs the whole *run*, not a job inside it, so splitting jobs does not by construction touch this; verify by leaving the `concurrency:` block's text untouched and keeping `test_ci_order.py`'s `test_the_run_in_progress_completes_and_the_newest_tree_waits` (rewritten job-aware per item 7, but asserting the identical regex against the identical block) green. The two orchestrator-run proof pushes (Evidence, below) are the behavioural check: one run in progress while a second is pushed, the second waits, the run in progress completes.
   - **A failure in any shard fails the run.** By the matrix `needs:` mechanics above; show it with one deliberately broken shard in a worktree-local dry run if the builder can simulate matrix behaviour without GitHub (`act` or similar), otherwise state plainly that this specific case can only be proven on the runner and is one of the two orchestrator-run proof pushes.
   - **Artifacts and content-previews upload exactly as today.** The "Upload content previews" step, `if: always()`, moves to job 3 unchanged in its `with:` block.
   - **`pages.yml`, `docs-integrity.yml`, `render-full.yml` and `docs/prompts/checks.json` are untouched** — grep them for `ci.yml` job/step/artifact names after the change and confirm no hit exists beyond what already existed (none do today, confirmed above).
   - **MAESTRO recordings and the MIDI parity reference stay restored before the steps that read them** — both stay inside job 1, in their existing relative order, since nothing outside job 1 reads `build/midi-real` or `build/midi-parity` (confirmed: no e2e spec references either path; only `midiParity.test.ts`, a unit test, and the Python MIDI harness do, both already in job 1).
   - **The Linux runner's fonts are unchanged.** Every job (`ubuntu-latest`) — do not move any job to a smaller/custom/self-hosted image or a different OS to chase speed; that is specifically the thing a local run cannot prove, and it is the reason this CI exists at all (the runner-font mechanism `docs/prompts/tasks/U105b-…md` and `G101-…md` both cite).

6. **`test_ci_order.py` is rewritten job-aware, not deleted or weakened — owned by this lane.** `read_steps` becomes job-keyed (return `{job_id: [steps]}`, or equivalent); `at`/`assertBefore` take an explicit job (or search across all jobs when a test's intent is "this still exists somewhere," and assert same-job order when the intent is a true dependency) ; every one of the nine existing tests keeps asserting the *same fact* it asserts today, phrased for the new shape — `at`/`assertBefore` for "content built before content tests" stays a same-job (job 1) check; "render check after the app build" may need to become a cross-job check (job 3 `needs` job 1/2, or the artifact job 1 produced, rather than a same-job step order) if the build step that feeds it moves to job 1 per Decision 2 — read the actual diff and decide, and say which of the nine changed from same-job-order to cross-job-needs and why. `test_the_steps_the_failure_messages_name_exist` and `test_ci_runs_every_check_the_path_map_names` must search every job's steps, not job 1 only (the `CITED` step names and the checks-map `ci` strings end up spread across jobs by this change). New loud-failure case worth adding, named with its own red test: two jobs claiming the same step name where the map or `CITED` expects one hit (today `self.at` already asserts exactly one match **within the single steps list**; job-aware, decide and state whether "exactly one across the whole workflow" or "exactly one per job" is right for each cited name, and why).

7. **This is a workflow change; it is reviewed before it is pushed, and the builder never pushes it.** Per the owner's 2026-09-30 rule (`operating-procedure.md` §11, "CI changes get reviewed") this brief and the resulting diff go to the reviewer before any push to the working branch. The builder's worktree is never pushed, per §14, full stop — that rule is not relaxed for this lane. **How the evidence runs happen without that:** the orchestrator, after the reviewer approves, pushes the reviewed `ci.yml` (plus the small `playwright.config.ts` conditional and the rewritten `test_ci_order.py`) to a **disposable branch that is not the working branch** — pushing it to the working branch would both jump the review gate and (per "push deploys") trigger a real `pages.yml` deploy the owner did not ask for. `ci.yml`'s `on.push` only fires for `branches: [claude/piano-teaching-app-bo19td]`, so a push to any other branch starts no run today; add `workflow_dispatch: {}` to `ci.yml` (precedented — `pages.yml` and `render-full.yml` both already combine `push` with `workflow_dispatch` or use it alone) so the orchestrator can run `gh workflow run ci.yml --ref <disposable-branch>` twice and read `gh run view --json jobs` on each — a `workflow_dispatch` run on a different ref gets its own `concurrency` group value (`ci-refs/heads/<disposable-branch>`, since the group name is `ci-${{ github.ref }}`), so it cannot take the working branch's one pending slot or otherwise touch the real Q63 contract. State this in the brief's diff as the one new trigger line, with this reasoning, so the reviewer sees exactly what it is for.

8. **What the builder can do before any push, entirely inside its worktree, with no runner:** parse `ci.yml` with a YAML loader to confirm it is syntactically valid (`python3 -c "import yaml; yaml.safe_load(open('.github/workflows/ci.yml'))"` or equivalent — stdlib has no YAML parser, `pyyaml` is already a transitive dependency of the content tooling per `requirements.txt`, confirm and say if not); run the rewritten `test_ci_order.py` against the new file and show every one of its tests green, with the exact job-aware assertions it now makes; run the spec-union check's own logic locally against `--list` output from the *unsharded* config to prove the comparison itself is sound before it ever depends on real shard jobs existing. None of this proves wall-clock time — that only exists once the orchestrator's two runner proofs land (item 7).

## What is decided

1. **The goal, in the owner's words and mine.** The owner's: the run takes over an hour, the browser tests are most of it, split them into parallel shards so the whole run is markedly faster. Mine, read against the code above: the same `npm run e2e` test set, divided by `--shard=i/N` across N jobs that each restore rather than rebuild the content and app-build work the first job already did, with the two post-E2E content-mutating steps (render-check, the second validation) kept together, in order, after every shard has finished — not parallelised themselves, since `render_check.py --apply` writes to the catalogue and a second, unsharded validator reads what it wrote, and nothing in this brief re-opens that ordering.

2. **The job graph's fixed shape; N and the exact step split are the builder's, by measurement.**
   - **Job 1** (keep the existing steps, in the existing order, minus "Install Playwright Chromium" — nothing before the app build needs a browser): checkout → setup-node → setup-python → restore content-build cache → install Python deps → `npm ci` → Build content → Content pipeline tests → restore/fetch/save MAESTRO → MIDI converter harness → write the MIDI parity reference → generate icons → Lint → Typecheck → Unit tests → **build the app** (`npm run build:app` or `build`, the builder's call, consistent with what `webServer` already runs) → **upload `app/dist` as an artifact**. One upload is enough: Decision item 4 below established that `app/dist` already contains the built content via Vite's `publicDir` copy, so there is no separate "built content" artifact to keep in sync with it.
   - **Job 2, a matrix of N**: `needs: job1`, downloads the `app/dist` artifact, `npm ci`, install Playwright Chromium, run the shard's slice, upload that shard's reporter output (for the spec-union check and for ordinary failure triage) as a per-shard artifact. N starts at 3 or 4 and is set by what the builder actually measures (below) — not a number asserted here as general, since the runner's own timing is what decides it, same discipline as everywhere else in this project.
   - **Job 3**: `needs: job2` (GitHub waits for every matrix instance and treats one failure as the matrix job failing — this alone satisfies "a failure in any shard fails the run," no extra wiring). Downloads the `app/dist` artifact (its own webServer rebuild cost on top of that is small and already measured today — see the note below), runs Render every catalog item, then Validate again, then uploads content previews exactly as today.
   - **Artifact, not cache, for the job-to-job handoff — read and decided, not left open.** The existing "Restore content build cache" step is keyed on the content pipeline's *inputs* (the scripts, the sources, the lockfile) and exists to make a later, independent *run* faster; a cache hit or miss changes how long the build takes, never what it produces, and `pages.yml`/`render-full.yml` both restore the identical key independently — this step is untouched by this lane and must not become the channel N shard jobs rely on for identical bytes within one run. `actions/upload-artifact`/`download-artifact@v4` already does exactly this job in this same file (the content-previews upload) and guarantees the artifact a sibling job downloads is the exact bytes the producing job wrote, for this run only — the right tool for "N parallel jobs must all start from the same one build," where a cache's best-effort, eventually-consistent semantics are the wrong fit.
   - **Playwright's own Chromium binary** is a genuine cross-run dependency (same class as `npm ci`'s cache), not a same-run data handoff — `actions/cache` for it, keyed on the Playwright version, is fine, and each shard job still needs the install step (each is a separate runner).

3. **Every shard's webServer must not re-run `build:app`.** `playwright.config.ts`'s `webServer.command` is `npm run build:app && npm run preview`, used by every invocation on CI, including each shard's. Left unmodified, every shard job would pay a full icons+`tsc -b`+`vite build` before its first test — not a correctness problem (the rebuild is deterministic and produces the same `dist` the artifact already has) but exactly the wasted, repeated work this lane exists to remove, and it is realistically close to the **"Build"** step's own measured 4m10s/4m50s, not the much smaller 21s/42s that today's single "Render every catalog item" step shows — that step's speed is best explained by `tsc -b`'s own incremental build-info cache still being warm from the "Build" step moments earlier in the *same* job; a shard starting cold on a fresh runner has no such warm cache. Fix: a narrow, CI-only conditional in `playwright.config.ts`'s `webServer.command` — e.g. a distinct env flag the shard jobs set, selecting `npm run preview` alone when the `dist` artifact is already in place, falling back to today's exact string in every other case (local dev, the render-check job, the tour/corpus/states configs, which have their own config files and are untouched). State the flag's name and show the default path is byte-identical to today's when unset.
   - **This is the one shared app file this lane touches**, and only for this one conditional; state in the report exactly what changed and that every other caller's command string is unchanged.

4. **The `npm run e2e` substring stays in every shard's `run:` line.** `docs/prompts/checks.json`'s `e2e` check has `"ci": "npm run e2e"`, and `test_ci_order.py`'s `test_ci_runs_every_check_the_path_map_names` asserts CI has a step whose `run`/`uses` *contains* that exact substring. This lane does not own `checks.json` (see "Not yours"), so each shard's step must keep that substring literally present — `run: npm run e2e -- --shard=${{ matrix.shard }}/${{ matrix.total }}` (or equivalent) satisfies both the sharding and the existing map entry with no edit to the map. Say in the report that this is why the shard command is phrased that way, so the next reader does not "simplify" it to a bare `playwright test` call and silently break the map's assertion.
