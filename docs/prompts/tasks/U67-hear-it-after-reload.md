## The goal, in the orchestrator's words

A learner who reloads the page on a piece, or opens a link straight to one, presses Hear it and hears nothing: the screen built its session before any gesture, with a null audio context, and the session keeps it. After U67 the session always plays through a context that exists — obtained inside the Hear it gesture, as the microscope does — and a browser test that opens the screen by address, taps Hear it once and counts scheduled sample starts is red on the committed screen and green after. Nothing else about Hear it changes.

## What is decided

1. **The mechanism — one complete binding, the context and its destination together.** `ScoreScreen` captures both `audioEngine.contextOrNull` and `audioEngine.masterGain` before the first gesture and the session retains both; refreshing the context alone would fix the piano's notes and leave the metronome routed through the stale null destination (the reviewer's required change, `responses/b2a55d0.md`). So: the learner's tap awaits `audioEngine.ensureStarted()`, then binds the resulting context **and** the current master destination as a pair before any `start()` or relevant `resume()`. Provider or setter is the builder's call — a setter carrying `{ context, destination }` is the smaller fit for the existing synchronous session API; a provider is as good only if the gesture handler still performs the asynchronous `ensureStarted()` first and the session reads the pair atomically at every playback and metronome boundary. `ScoreSession` never creates or owns the app's `AudioContext`. A session built cold and bound live later plays, notes and metronome both; a session built with a live pair behaves exactly as today; the microscope, the dev score screen and any test double keep working unchanged.
2. **The regression, red first:** `app/tests/e2e/score.hearIt.spec.ts` (or the existing score spec's file, the builder's call): open `/#/score/<a bundled song>` by address with no prior tap, tap Hear it once, and assert sample starts (the probe's measure — a count under the existing `__pianopath` test hooks at the real `Piano.start` scheduling boundary, reset and read-only for the test, absent or inert outside the hooks (the reviewer's constraint)) are greater than zero; a second case after a prior tap as the control. Red on the committed screen with the count. A unit case on `ScoreSession` for item 1's two states, the cold-then-live case proving the destination pair as well as the context.
3. **Both `session.resume()` sites** reviewed: they need no second `AudioContext` owner — a demonstration resumes only after Hear it has established the live binding, and the ordinary Play path keeps the app-level gesture start contract; if the red-first test proves otherwise, route that gesture through the same binding, never a timer or a second engine.
4. **Not U67's:** the audio engine's design, the practice engine's audio, the microscope, any other screen, latency, the sound itself.
