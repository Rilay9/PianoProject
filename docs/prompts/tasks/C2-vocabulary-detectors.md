## The goal, in the orchestrator's words

Before evidence can be computed, the app needs to say what a skill is and what a demand is, in a form the build can check and a run can read. This task writes the first, small vocabulary: only what the sight-reading rows and their rungs promise, about fifteen demands and a dozen reading skills, keeping today's concept ids wherever they already read as abilities. It moves the demand detectors out of a test file into the app, decides how the content build will use the same definitions, and makes the build refuse a rung that requires evidence of a skill no run can measure. It normalises nothing else: the 283-concept drawer stays as it is except where v0 draws a line through it.

## What is decided

1. **v0's scope** is the reading strand: the demands the nine sight-reading rows' promises name and the taught-at table in `unintended()` (eighths, dotted quarters, ties, sixteenths, syncopation, triplets, compound metre, a key signature, chromatic notes, range beyond a position, the left hand's patterns, leaps past a size) and the reading skills those rows and rungs 1.3, 1.4, 1.5, 2.2, 2.5, 3.4, 4.5, 4.6 practise. Each skill declares its kind, its opportunity (the demand ids), its observable (pitch, timing, or none) and the conditions for its practice and full standards (design §4(c): Keep tempo for time; unseen and guide off for reading at the full standard). Each demand declares its detector id and `copedWithBy` (which skill copes with it) and the rung that teaches it. Skills that read as abilities keep their existing concept ids (reviewer decision 2, the design's §11 item 1); a new id is added only where none exists.
2. **The vocabulary lives beside `concepts.json`** as its own files (skills, demands), validated by the build, with `concepts.json` left in place for everything v0 does not touch and a note saying which ids v0 has taken over. The schema gains `targetSkills`, `demands` and `role` as optional item fields; v0 fills `targetSkills` on the nine sight-reading rows only. The rows' recipe `level` keeps its name: it is a generator parameter under `drill.params`, not the item's `level`, and renaming it would touch the score screen C1 owns; C6 decides its fate with the rest of `level`.
3. **The detector module** lives in `app/src` (one module, its own tests: present, absent and boundary on hand-made phrases for every demand in v0), reading the score model, not the MusicXML string. `sightReadingPromises.test.ts` keeps every assertion and loses its helper code in favour of the module.
4. **One authoritative definition** (reviewer decision 4): investigate, before choosing, whether the content build can run the same TypeScript detectors over every file through Node (the build already drives a browser for the render check; measure the cost on the built catalog) or whether two implementations with a shared golden-fixture set are the honest choice. Write the finding with numbers as relationships and choose; if two, the agreement test runs in CI on fixtures that cover every v0 demand. The catalog need not carry `demands` for every item yet (that is E); the decision and the mechanism are what C2 delivers, proven on the nine rows and on one quarried piece.
5. **The build gate** (design §4 enforcement 3): `validate.py` refuses a rung whose requirement names a skill with `observable: none` or a condition no run can meet, and reports the two it would refuse today (1.5's first-attempt rule; the technique measures that cannot stop a pass) as waivers with reasons until C5 turns them into predicates. `CLAIMING_CONCEPTS`' `minor-triad` key becomes the vocabulary id (G34).
6. **Genre and style** (design §9): no vocabulary entry for a genre; the generated rows' `genre: ["technique"]` and `["drill"]` are left for D to remove, noted in the report.
