## The goal, in the orchestrator's words

E2 built the material gate beside the old one and proved the two agree everywhere but in the one case the reviewer's rule changes on purpose. Beside is not enough: every automatic offer still asks the old gate, so the unknown-forbidden rule protects no learner yet, and a later feature could pick whichever answer it liked. After E2a there is one public gate. `eligibleFor` keeps its name and signature for its four callers and its tests, and its body is the material gate over the candidate contract — the want translated by `requirementsFromWant`, the item by `candidateOf` — with the teaching-use admission and every known-fact verdict preserved byte for byte and the one moved case moved: an unmeasured candidate under an automatic want for a learner not prepared for every demand is refused as `unknown-forbidden`, and a test at the consumer boundary (the session's `usable`, the selectors' tiers) proves no automatic offer can reach it. The old logic is no longer reachable from outside the module. Novelty stops being a fixture: the candidate's contact identity is D4's material identity and the learner's contact reading is D4's `contact` over the stored runs, so a changed excerpt cut is unmet and a run under another id of the same material is met. And the build passes each lesson's concepts and each concept entry's id to `finder.generate`, so the seed list reaches the prompts where the build has a concept, held by a test at the call site.

## What is decided

1. **One gate, without recursion** (the reviewer's required change on this brief, `responses/1b09a1f.md`: today `eligibleForMaterial` calls the exported `eligibleFor` for the admission, coping and opportunity verdicts, so a wrapper the other way would recurse). **The ownership boundary:** the established question logic — the teaching-use admission, the coping question, the opportunity question, the untrusted-tempo marker, the verdict shapes — moves into one private core in a new module, `app/src/curriculum/eligibilityCore.ts`, which imports nothing from `candidates.ts` or `eligibility.ts`. `candidates.ts` (the requirements, validity and the material gate) imports the core and calls it for those verdicts; `eligibility.ts` keeps the public surface — `eligibleFor(candidate, learner, want, vocabulary)` with its signature, `eligible()`, the `Want` union and the verdict types — and its `eligibleFor` delegates to `eligibleForMaterial(requirementsFromWant(want), candidateOf(candidate), learner, …)`. The import graph is core ← candidates ← eligibility, with no edge back: no cycle, and the entry names the three modules' ownership in a line each. Nothing else in `eligibility.ts` computes a verdict; the old body is deleted once the tests are green. **The public verdict type widens** so the existing `eligible(eligibleFor(...))` consumers typecheck without a cast that could hide an outcome: `Eligibility` gains `unknown-forbidden`, `unknown-physical` and the other material verdicts, each `ineligible` or `exploration-only` as the material gate says, and `eligible()` reads them all. `eligibleForMaterial` stays exported for callers that have requirements beyond a want (none yet; X's). No caller file changes: `selectors.ts` and `session.ts` keep their four calls.
2. **The verdicts.** Every existing verdict stays byte-identical except the reviewer's rule's case; `eligibility.test.ts`'s adversary 8 and `gateAtTheConsumers.test.ts`'s unmeasured-option and import-only-row expectations are revised to `{ verdict: 'ineligible', why: 'unknown-forbidden', demands, missing }`, each revision classified with the reviewer's response as the reason. The equivalence probe's method (E2's `probe-every-gate-call`) is rerun once against the merged gate and its result recorded: every moved call the rule's case, none unexpected.
3. **The consumer boundary, through the exported path.** The red-first and boundary tests call the exported `eligibleFor` (and the consumers that call it), never `eligibleForMaterial` directly, so what is proved is the path the app uses: a test through `session.usable()` and the selectors' tiers on a constructed learner not prepared for every demand and an unmeasured, teaching-admitted candidate (a bundled row with no measurement; a score imported before E0 not yet measured): no card row, no tier, no fallback and no offer holds it; the same learner under an exploration want may open it from the Library. One mutant: the gate's unknown-forbidden branch off — the boundary test goes red, not only the unit case. The 21 moved verdicts stay the only movement (the reviewer's constraint), E0's untrusted-tempo marker preserved.
4. **Novelty bound to D4, the gate still pure.** `contactIdentity(candidate)` returns D4's material identity (`materialOfItem` for a catalogue item; the cut's file identity for an excerpt; an import's `none` as D4 left it, so an import is judged by id and says so). `MaterialLearner.contact` is never read from a store inside the gate: the caller passes it, built from the learner's stored history by an adapter over D4's `progressStore.contactIn` (the rows the caller already holds — the session's `ctx` has them).
