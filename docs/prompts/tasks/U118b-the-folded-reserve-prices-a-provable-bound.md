## What is decided

- **Question 1 is not reopened.** Option (iii)'s placement-always/price-only-on-a-genuine-size-pass mechanism, and the two-cell outcome the reviewer read as "no new trade," stand exactly as built (`ScoreScreen.ts`'s `foldedReserve`/`cornerTexts`/`foldedCornerReserve`, `WindowRenderer.ts`'s `packSlots`/`placeSlots`/the pricing pass). This lane touches only the one input the required change names.
- **The sentinel's required property, verbatim:** "a provable numeric-width upper bound for the current runtime representation — e.g. a decimal sentinel as wide as `Number.MAX_SAFE_INTEGER` — rather than a semantic time guess." `Number.MAX_SAFE_INTEGER` is `9_007_199_254_740_991`, sixteen decimal digits, and `String(Number.MAX_SAFE_INTEGER)` prints in full decimal (no exponential notation; JS only switches to exponential above `1e21`) — so `STATE_TEXT.away(Number.MAX_SAFE_INTEGER, …)`, read at premise 4, produces the actual widest decimal string a `number`-typed `seconds` can carry. One fact from the second read (`docs/review/second-reads/0d2c3472.md` item 2) tightens this: the chip does not use tabular digits, so `9007199254740991`, with its narrow 1s and 0s, is not the widest sixteen-digit string the font can draw. The strict bound is sixteen copies of the chip font's widest digit, measured at the chip's geometry; it covers every count `String()` can print for a safe integer (sixteen digits at most; the second read finds reachable counts stay at or under fourteen). Build that, as a string passed to `STATE_TEXT.away`'s `number | string` parameter. Whether the builder keeps the name `AWAY_PRICED_S` for this new value, renames it, or references `Number.MAX_SAFE_INTEGER` directly at the two call sites is the builder's judgement — the required property is the sentinel's decimal width, not its name.
- **The away sentence stays in the reserve.** Not an option to drop it (the ruling says so explicitly); the fix changes what width it is measured at, not whether it is measured.
- **Follow-up 3 is built here, not deferred.** The fix is local to the one case at `windowRendererStage.test.ts:468–486`: give it its own initial `observe()` call (premise 11's pattern) before the width change, then strengthen its assertions so they can only pass if `stageChanged()`'s "turned" branch actually ran on the second observation — e.g. asserting the held scale/shape after the change differs from before in the way a genuine re-price at 390 × 600 would (the same comparative technique the adjacent case `:443–466`, "a width change off a run re-plans for the new width," already uses against an independently-rendered reference), not merely that something "not null" survived. The exact assertion is the builder's judgement; the discriminating property is not.
- **Not a shared-helper fix.** `open()` (`windowRendererStage.test.ts:325–330`) is used by dozens of other cases in this file; adding an unconditional `observe()` call inside it would change every one of them. The fix stays local to the one named case, following the per-test pattern premise 11 already establishes, unless reading the file at dispatch shows every other caller already relies on or is indifferent to that first observation — said and confirmed before changing the shared helper, not assumed.
