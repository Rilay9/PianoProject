## The goal, in the orchestrator's words

D4's contract is that a transfer-intended run records the relationship the offer was made on. The Score screen computes that relationship after it has already let the learner play, so a quick run is stored with `intent: 'transfer'` and no relationship, and a slower one with a relationship recomputed at opening rather than the one the card showed. After D4a the relationship travels with the choice: Today writes the day's offer — skill, item, material, relationship, contact, date — to a durable row when it opens the offer, the Score screen reads that row before the transfer route becomes playable and writes that exact value on the run, and when the row is missing or unreadable the screen says so and opens the item as ordinary practice with no intent, never a partial transfer record. A regression holds the load pending, another changes the history between the offer and the opening, and both prove the stored row is the offer's or nothing.

## What is decided

1. **The snapshot.** When Today opens the transfer offer (`TodayScreen.ts` 275), it first writes the offer's claim — `{ itemId, skill, material, relationship, contact, offeredOn: <date>, cardId or the morning's key }` — to a durable row in an existing store (the `settings` key-value store under one key, or the `plan` store; the builder's call, said in a line; no new object store and no `DB_VERSION` change) and navigates only once the write has resolved. The value is the session's own `relationship` and `contact` (session.ts 444), never recomputed. **Bound to the exact offer instance** (the reviewer's required change, `responses/1cbc38a.md`): the composed card's offer carries a stable instance token (a revision minted when the card is composed, or the offer's own id), the snapshot stores it, the route carries it (`?intent=transfer&skill=…&offer=<token>`), and the read requires an exact match; recomposing the card or swapping the row away supersedes or invalidates the prior snapshot, so a stale URL or a delayed navigation can never consume an earlier offer's relationship. "Today, this item, this skill" names the subject; the token names the teaching decision whose relationship the run records.
2. **The read, before play.** For a route with `intent=transfer`, the Score screen reads the snapshot before it enables ▶ (the same place the route's other preconditions are met): the row must exist, match the route's offer token exactly, name this item and this skill, and be today's. **Pending is pending:** while the read is unresolved, ▶ stays disabled and no run row can be stored — an indefinitely pending read is never modelled as a completed practice run. Once the read resolves: if it matches, `transferRelationship` is the row's value and the run's facts carry `intent` and that relationship together; the unawaited `Promise.all` at 4289 goes. If it resolves to missing, stale (another token, another item, another day, superseded), corrupt or unreadable, the screen prints one explicit line in the help copy's voice ("This offer is no longer on today's card; opened as practice"), the route becomes ordinary practice, and the run is written with no `intent` and no `relationship`: a partial transfer record is impossible by construction — `runFacts` takes either no transfer fact or the pair `{ intent: 'transfer', relationship }`, and its return type keeps the same invariant so no application code can construct an intent-only `RunFacts`.
3. **The regressions, red first.** (a) The load held pending (a fixture whose snapshot read never resolves): begin and finish a run; no row with `intent: 'transfer'` is stored, and the stored row has no relationship. (b) History changed between the offer and the opening (a run of the establishing row stored after the snapshot was written): the stored relationship equals the snapshot's byte for byte and differs from `relationshipOf` recomputed at opening. (c) The snapshot for another item or another day, or missing, corrupt or unreadable: opened as practice, the line shown, neither intent nor relationship. (d) The happy path: the route's token matches, the row's value on the run byte for byte, `intent` beside it. (e) The same day's card recomposed with a different offer, or the row swapped away, after the route was issued: the old route downgrades explicitly to practice. (f) The pending gate: while the read is held, ▶ is disabled and beginning a run is impossible. One mutant for each mechanism: the snapshot skipped on open; the read not awaited; `runFacts` accepting an intent without a relationship; the recomputation used instead of the row; the offer-token match ignored. The implementation handoff shows the reviewer's six verifications in this order: the pending read; the exact-offer happy path; history changed after composition; same-day recomposition or swap; other item or day, missing, corrupt or unreadable; the type and mutant boundary rejecting an intent-only run fact.
