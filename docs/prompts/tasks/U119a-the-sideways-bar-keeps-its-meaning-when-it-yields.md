## Decided by the orchestrator, from the second read (`docs/review/second-reads/0d2c3472.md` item 1)

- **The predicate.** Sideways only (the group is `display: none` upright, `style.css`:2910–2916): the left group's minimum holds when `whereSide`'s right edge sits at or inside `barLeft`'s right edge. Back and `bar n / m` keep their natural widths while clipped and come before the status, so this one comparison covers both, and cutting the status never trips it. It joins `barIsOverfull` inside the existing bring-back-then-remove loop.
- **Which text it prices: the piece's widest location, not the current one.** `fitBarControls` runs on every render (`ScoreScreen.ts`:4866) and `bar n / m` grows during a piece (`drawWhere`, :4714–4726), so pricing the current text could send Hands behind `⋯` partway through and bring it back on restart. Price `bar m / m` (n with as many digits as m), as U118's `cornerTexts` already does (:1239–1240), so a piece's controls stay where they are for the whole piece.
- **Hear it may follow.** If Hands alone does not free the minimum, the existing order continues and Hear it leaves next; that is the existing machinery the ruling names. Report every cell where Hear it leaves.
- **The status ellipsis.** The landscape title rule (`style.css`:1006) sits inside the block U119 already owns, so it is in scope. The second read's candidate: the status mirror gets `flex: 0 1 auto; min-width: 0` so its own `text-overflow: ellipsis` bites, with the title's extra shrink weight scoped off while `data-sound-refused` stands, and U105d's refusal rule untouched. The title must not lose width where nothing was wrong (the 740 × 342 mutant below stays).
- **The ellipsis cuts at a character.** CSS `text-overflow: ellipsis` can give `Pau…`. Build it; report every truncated string the grid produces; the handoff asks the reviewer whether a character-boundary ellipsis meets "visibly read as truncated". A word-boundary cut would need script, and is not built here.
- **The refusal row hazard, read in code, not measured.** `barIsOverfull` counts rows by each child's rounded `top` under `align-items: center` (:2885). Where U105d's refusal wraps to three lines the group grows (:6210–6212), its `top` differs from the controls', and the bar reads as two rows, so Hands and then Hear it would go behind `⋯` while the refusal stands. Measure it (acceptance case 5b). If it happens, the row test counts the controls' rows, not the grown group's, since U105d's ruling let the bar grow during a refusal and did not move controls for it. Stop if that fix changes which controls leave in any other cell.

## Mechanism (what Question 1 and Question 2 ask the builder to measure, not guess)

**Question 1 — teach `fitBarControls` the left group's own minimum.** The shape the response specifies: `fitBarControls()`'s existing loop (premise 1) already tries each `OVERFLOW_ORDER` entry in turn and re-measures after each; it needs one more condition alongside `barIsOverfull()` that becomes true when the left group's semantic minimum — Back whole, `bar n/m` whole, title allowed to go to zero, status allowed to go to zero — would not fit in the box `#score-bar-left` is about to be given. The natural way to measure that without guessing a pixel threshold is the same way `barIsOverfull()` already measures: `getBoundingClientRect()`/`scrollWidth` on the real, laid-out elements (e.g. comparing `backSide`'s and `whereSide`'s own content widths plus the gap between them against `#score-bar-left`'s assigned width, with title and status excluded from the requirement since they are the named yielding content) — run inside the same "bring everything back, then remove one at a time" loop so a new control configuration is only accepted once both `barIsOverfull()` and this new check pass.

**This exact comparison is a claim to verify, not a fact.** I have not run it; it is read off the CSS/JS as the measured shape the ruling asks for, not confirmed by an existing line. The builder may find a more direct measurement (e.g. comparing each of Back's and `bar n/m`'s own `getBoundingClientRect().right` against the group's right edge after a trial layout) that better matches how `overflow-x: clip` actually decides what is cut; either is acceptable as long as it is measured against the real DOM at the cell in question, not a hard-coded breakpoint — the ruling explicitly forbids "the proposed global/sideways threshold."

**Question 2 — the ordinary status's own truncation boundary.** The handoff already tried and rejected one path: giving the status mirror `flex: 0 1 auto; min-width: 0` so it shares the shrink with the title — rejected because it moves the title's own width where nothing was wrong (`Hot Cr…` at 740 × 342 on the wider face, premise 5's comment). A refusal-scoped weight on `.score-bar__title` was identified as the alternative and explicitly marked **not owned** by this lane. One candidate left unexplored by the handoff, offered here as a hypothesis for the builder's own measurement, not a prescribed fix: give `statusSide` alone (not title, not Back, not `bar n/m`) its own `flex: 1 1 auto; min-width: 0` inside the landscape media query, so the element that already carries `overflow: hidden; text-overflow: ellipsis` (premise 6) shrinks to whatever room Back, title and `bar n/m` actually leave it, rather than being held at its full natural width and then clipped from outside. If this reintroduces a side effect on a sibling (the same class of problem the shared-title path had) or otherwise does not measure cleanly across the grid, that is the "new product trade" the stop condition covers — report it and stop rather than force it.
