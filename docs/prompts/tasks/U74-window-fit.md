## The goal, in the orchestrator's words

The Score screen draws the same two-bar scale two ways: opened by a link after a fresh load it fills two systems; opened from Today's card it sits in one small system at the top with the rest of the stage empty. That is the first of the three goods lost on the path every learner takes. The likeliest mechanism, to be tested first and not assumed: on in-app navigation the renderer is created while the stage's size is not yet what it will be (the header, the status line and the bar settle after), so the window's scale is fitted to a wrong height and nothing refits it; a fresh load measures the settled stage. After U74 the renderer owns its stage's size — it measures the stage when the layout has settled and refits whenever the stage changes by more than `worthRefitting` allows — so both paths draw the same, held by a test that opens the same item both ways and compares the system count and the staff height; and the window rule's choice for a short item on a wide stage (E30) is judged on the whole gallery and the corpus, changed only if every size looks better.

## What is decided

1. **Start from the observer that already exists** (the reviewer's required change on this brief, `responses/a1c1fd6.md`). `WindowRenderer` already owns a `ResizeObserver` on its stage (`WindowRenderer.ts` lines 946–959): the stage settles after the initial draw; on a size change the callback calls `stageChanged()` and `fitToStage()`; `dispose()` disconnects it; and the callback **returns at once when `this.disposed || this.fitting`** (line 948), so a notification delivered while a fit is in flight is dropped and never retried. "No observer" is not the diagnosis. The red unit case, on the real renderer against a controlled stage, tells at least four causes apart: (a) a stage change delivered while `fitting` is true, which the current callback drops — does the renderer ever refit afterwards?; (b) a settled height change delivered off-run, which the existing callback should already refit; (c) a width or orientation change, which must replan and may release the run's freeze; (d) route-specific render inputs or timing that produce different shapes even when the final stage box is equal. Say which the two-paths difference is, with the evidence; the browser case (item 3) is the learner-facing proof, the unit case the discriminating one.
2. **The fix on the proven mechanism, inside the renderer.** If the fault is a resize notification lost while fitting: the renderer marks a pending resize and performs one fit after the active fit settles, with convergence (no fit storm: one retry per settled fit) and disposal (a pending resize on a disposed renderer does nothing) covered by cases. If the observer already receives a final settled notification and the difference comes from the routes' inputs, fix that renderer-owned mechanism instead. Extend the existing observer, `refitEngraving`, the settled state (`data-settled`, `fitSettled`) and `dispose()`: no second resize owner, no screen timer. **The run-size contract stays as `refitEngraving` enforces it:** off a run a height change may refit and replan; a width change may re-engrave and replan during a run while preserving the current step (the rotation contract, `score.rotate.spec`); a height-only change during a run keeps the drawn size and must not re-engrave or change the window's shape (a CSS placement update may keep the frozen size without restarting anything). `worthRefitting` compares zooms, not stage dimensions, and is not the trigger. The Score screen's call at line 4354 stays as it is, so `ScoreScreen.ts` (G1's file this week) is untouched; if the proven mechanism lies in the screen, stop and report the lines.
3. **Both paths equal, compared as settled equivalent states.** The browser case opens the same two-bar item from Today (D4's seeded learner, `today.spec.ts`'s `placeAt`) and by a link after a fresh load, at 342 × 740, with the same item, bars setting, viewport, controls and pre-run state; it waits for `data-settled="true"` on the stage on both paths, then records and compares the final stage box, the system count, the bars shown and the staff height — the box recorded so a fit fault is told from genuinely different available space. Today the two differ (the red line); after the fix they are equal within a pixel, and the picture at 342 × 740 from Today shows the scale filling the stage as the link path does. A refit never redraws the system holding the cursor and keeps the current position.
4. **E30, judged, not assumed.** The window rule's choice for a four-bar cut on a desktop-wide stage (two bars with a third empty) is examined on the states gallery and the ten-piece corpus at the gallery's sizes: if a change to `chooseWindowShape` or the scale rule makes every cell better or equal by the three goods, make it and show the gallery before and after; if any cell gets worse, leave the rule and record what a better rule would need. Never a stretched bar: scale up, never space out.
