## Hypothesis and its refuting test

**Hypothesis:** the `elif existing_tempo:` branch's removal of `existing_tempo[1:]` (:1557–1565) only ever fires on same-position duplicates (its documented purpose), so no genuine later tempo change is lost anywhere outside the three kern rows X40 already found. **Refuting test:** read the branch itself — the removal loop tests only list order (`existing_tempo[1:]`), never offset, so any second `MetronomeMark` at any later position is removed regardless of whether it duplicates the first. Confirmed on three real files at three genuinely different bar positions each (premise 3): the hypothesis is refuted for kern. `convert_file` is PDMX's and (for 9 of 64 rows) MuseTrainer's only entry point too (premise 2), so the *mechanism* generalises to them on the same code reading; whether it has actually *fired* on a PDMX or additional MuseTrainer row cannot be shown from what this repository holds (premise 4) — an open count, not a second refutation.

## What is decided

1. **Fix the mechanism, not the branch's symptom on three rows.** Keep every `MetronomeMark` at its own (measure, offset) position; remove a mark only when it is a semantic duplicate of one already kept, not merely co-located with it. The reviewer's correction (`questions-fc9f1a8b-correction.md` §E57): "'Same position' alone is not sufficient to define a duplicate. Two different authored tempo marks can legitimately stand at the same musical position. The converter may collapse only **semantically duplicate co-located marks**: same musical position and the same effective quarter-BPM tempo (allowing only the representation noise already established by the source/parser). A co-located conflicting tempo must survive for the reader/evidence layer to interpret; do not delete it merely because its offset matches the first mark." A duplicate is therefore same (measure, offset) *and* the same effective quarter-bpm tempo, within the representation noise the source/parser already establishes (premise 1, premise 6); a co-located mark with a different effective tempo is a conflict, not a duplicate, and survives for the reader/evidence layer — resolving which of two conflicting co-located tempos is authoritative is not this lane's job. No other change to `normalise()`, `insert_tempo`, or `tempo_printed_as_text`.
2. **Kern: red first, then green, on three pinned acceptance cases, then the three named rows.** The reviewer's correction: "Pin both sides red first: the existing two-voice/same-tempo fixtures remain one mark, while two distinct-position marks survive, and add a same-position/different-tempo guard so the narrower dedup rule cannot regress into 'first mark wins at this offset.'"    b. **Two distinct-position marks survive.** A unit fixture (two `MetronomeMark`s at two distinct offsets, mirroring each of the three sources' `*MM` positions and values from premise 3) proves the branch keeps both where today it keeps one.
