## Premises at the lines (HEAD d5c6491f)

1. **The mechanism.** `tools/content/convert.py:1549` collects every `MetronomeMark` the parsed score already carries: `existing_tempo = list(out.recurse().getElementsByClass(tempo.MetronomeMark))`. The branch at :1557–1565 (`elif existing_tempo:`) keeps only `existing_tempo[0]` for the file's `effective` tempo and unconditionally detaches every other one (`for mark in existing_tempo[1:]: ... mark.activeSite.remove(mark)`), with no test of *where* each mark stands. Its own comment (:1559–1562) states the intent: "music21's ABC reader puts a tempo in every voice, and OSMD dutifully draws all of them: an authored tune came out with '♩=84' twice, once over the staff and once beside the first note" — a same-position duplicate, not a later, genuinely different tempo change. The branch conflates the two.
2. **The single entry point.** `convert_file` (`convert.py:2244–2254`) calls `normalise(score, keep_lyrics=keep_lyrics, tempo_bpm=tempo_bpm)`; `tempo_bpm` defaults to `None`. Every batch importer reaches this same function with `tempo_bpm` unset, so the same branch governs all three corpora:
   - **kern:** `import_kern.py:679–688`, `cached_convert(source_path, dest, title=spec["title"], composer=spec.get("composer"))` — no `tempo_bpm`.
   - **PDMX:** `tools/content/pdmx/quarry.py:448`, `convert_file(raw, destination)` — no `tempo_bpm`.
   - **MuseTrainer:** `import_musetrainer.py:292–319` calls `cached_convert(source_path, dest, title=..., composer=...)` (no `tempo_bpm`) only when `normalisation_reasons(xml)` (`:110–118`) finds a reason — more than one `<score-part>`, or "no tempo of its own" (no `<sound tempo=` and no `<metronome` in the source). 55 of X40's 64 MuseTrainer rows have neither reason and are copied verbatim (`:318`), never reaching `normalise()` at all.
   - The one caller that *does* pass `tempo_bpm`: `author.py:240`, a manual single-file authoring tool, not a batch importer — outside this corpus and this brief.
3. **What X40 already counted, re-read here.** `docs/prompts/runs/X40/kern-mm.txt`'s header line: `{"no *MM (defaulted)": 60, "one *MM, built plays it": 99, "MISMATCH": 3}`, and its three `MISMATCH` rows, each read from a build X40 already ran (fetched kern clones, converted, read through the app's reader and a raw scan):

## Hypothesis and its refuting test

**Hypothesis:** the `elif existing_tempo:` branch's removal of `existing_tempo[1:]` (:1557–1565) only ever fires on same-position duplicates (its documented purpose), so no genuine later tempo change is lost anywhere outside the three kern rows X40 already found. **Refuting test:** read the branch itself — the removal loop tests only list order (`existing_tempo[1:]`), never offset, so any second `MetronomeMark` at any later position is removed regardless of whether it duplicates the first. Confirmed on three real files at three genuinely different bar positions each (premise 3): the hypothesis is refuted for kern. `convert_file` is PDMX's and (for 9 of 64 rows) MuseTrainer's only entry point too (premise 2), so the *mechanism* generalises to them on the same code reading; whether it has actually *fired* on a PDMX or additional MuseTrainer row cannot be shown from what this repository holds (premise 4) — an open count, not a second refutation.

## What is decided

1. **Fix the mechanism, not the branch's symptom on three rows.** Keep every `MetronomeMark` at its own (measure, offset) position; remove only a mark standing at the *same* position as one already kept — the true same-position duplicate the branch's own comment names (premise 1, premise 6). No other change to `normalise()`, `insert_tempo`, or `tempo_printed_as_text`.
2. **Kern: red first, then green, on the three named rows.** A unit fixture (two `MetronomeMark`s at two distinct offsets, mirroring each of the three sources' `*MM` positions and values from premise 3) proves the branch keeps both where today it keeps one; the same-offset guard (a fixture with two marks at offset 0, mirroring `two-voices.abc`/`two-spines.krn`'s shape) proves the dedup is not lost. Where the harness's own copied kern clone is available (see Harness below), rebuild and re-read at least the Rondo through the app's reader (`tempoEvents`) the way X40's raw-scan/reader-dump did, before and after, as the end-to-end case.
3. **PDMX: the code fix lands unconditionally; the count and the re-quarry do not.** The same branch governs PDMX's `convert_file` call (premise 2), so the fix applies there the moment anyone next runs the quarry with the archive present — but no row's committed bytes change in this lane, no PDMX identity moves here, and no claim of "zero affected" is made (premise 4). Record as a follow-up, addressed to the owner (only the owner's machine holds the archive, per `paths.py`): re-run `tools/content/pdmx/quarry.py` against the archive under the fixed converter and diff the 373 non-defaulted rows' new bytes against their committed ones; any row whose bytes change is exactly a row that lost a later mark, and moves an identity under item 4 below the same way the three kern rows do.
