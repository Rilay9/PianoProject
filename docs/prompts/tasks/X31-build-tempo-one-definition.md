## The goal, in the orchestrator's words

The app now reads a file's tempo one way (X3d): a half note = 60 is 120 quarter notes a minute, and the opening is the event that opens the piece. The content build still reads the first `MetronomeMark`'s raw `number`, its beat unit ignored, wherever in the score it stands. So the duration feature the level model was fit on and the duration feature the app computes for the same file are two definitions of one feature, and a marked import's estimated level in the app and the build's level for the same file disagree. One definition: the build reads what the app reads, through music21's own normalisation, not through a Python copy of the app's reader.

## What is decided

1. **Quarter notes a minute, from music21.** The build's `bpm` is the opening mark's `getQuarterBPM()` (music21 normalises the referent — the beat unit and its dots — to quarter notes), never `.number`. A mark whose number music21 could not read (text only, a metric modulation) is not a tempo; the default 100 stays for a file with no readable tempo, as now.
2. **The opening, not the first found.** Among the marks music21 gives, the opening is the one at the earliest offset in the hierarchy (`getOffsetInHierarchy(score)`), ties to the first part; the current code's `tempos[0]` (recursion order) is replaced by that. Do not implement the app's "first tempo before anything sounds" rule or its sound-versus-mark precedence in Python: find out what music21 makes of the three MusicXML forms the app's tests cover — a `<metronome>` with a beat unit and dots, a `<sound tempo>` alone in a direction, both in one direction (MuseScore's form) — on the same fixtures as `app/tests/unit/tempoFromXml.test.ts` (read them; build the same XML in the Python test), and record where music21's reading and the app's agree and where they do not. Where they do not, the build keeps music21's reading and the entry says so, with the count of bundled scores affected (item 4): the reviewer's constraint is one definition, and the definition is the app's; a Python copy of the app's reader is refused, so the gap is named, not closed here.
3. **The model is not refit.** `content/sources/level-model.json` stays as committed; the feature's definition changes under fixed weights. Run `difficulty.fit` on the same samples for information only (the fit report's Spearman before and after, in the run folder), never committed; a refit is its own seam if the report says it should be.
4. **The discriminating test, on the corpus.** For every bundled score the catalogue names (2,011 in X3d's count), the build's opening `bpm` after this change beside the app's opening tempo from `runs/X3d/corpus-models.txt` (the label after at 100 %, and the catalogue's `tempoBpm` where the file says it): a table in the run folder with the count equal, the count differing, and each differing score with both numbers and the form that explains it.
