## Premises at the lines (HEAD `0aa847ed`; confirmed `npx vitest run tests/unit/drillLifecycle.test.ts` is 38 of 38 today)

1. A rhythm card's first open has exactly two entry points, both through `advance()`: the initial mount (`:4081`/`:4132`) and "Again" (`restart()`, `:3330`/`:3337`). `RhythmDrill.next()` (`special.ts:80–90`) returns one prompt only — `if (this.prompt) return null` — so a rhythm item is always a single card, and `advance()` is never called a second time for the same `RhythmDrill` except to end the set. Read at the lines.
2. `advance()` (`:1633–1667`) calls `releaseRhythmHold()` (`:1648`) unconditionally, before `current = drill.next()` (`:1652`), and then — with no gate of any kind — `if (drill instanceof RhythmDrill) startCountIn(drill)` (`:1664`). `rhythmJudgedFromMs` is left at its module default, `Number.NEGATIVE_INFINITY` (`:568`), for the whole of a first open: nothing on this path ever sets it to `+Infinity`. Read at the lines.
3. `RhythmDrill.next()` (`special.ts:80–90`) sets `this.startedAtMs = this.plannedStartMs ?? this.clock.now()` — the grid's origin is the card-open wall-clock moment, fixed before any sound has been asked for and before `startCountIn` is even called. Read at the lines.
4. `RhythmDrill.feed()` (`special.ts:156–185`): `if (this.latchPending) { if (this.waitingForStart) return; … }`. `latchPending` is declared `false` (`:51`) and is set `true` only by `latchOnFirstTap()` (`:123–126`), called only from inside `startCountIn`'s `.then()`/`.catch()` (`DrillScreen.ts:1337`, `:1372`), both of which run only once `ensureStarted()` has settled. Before that, `feed()` skips its own guard entirely and scores a tap against `startedAtMs` directly — the first gap the backlog row names. Read at the lines.
5. `latchOnFirstTap({ awaitCountIn: true })` (`DrillScreen.ts:1337`) sets `waitingForStart = options.awaitCountIn === true && this.plannedStartMs === null` (`special.ts:125`) — `true` on first open, since nothing has named a downbeat yet. It is cleared only by `startAt()` (`special.ts:102–106`), called from the count-in's own tick handler at the count's last beat or the downbeat (`DrillScreen.ts:1349–1352`, `:1355–1359`). Neither tick fires while the underlying `AudioContext`'s own clock is standing still — a suspended context's `currentTime` does not advance (entry-196's own mechanism note; modelled in the test double's `freezeFrom`) — so a `.then()` that resolves with a context not yet `'running'` leaves `waitingForStart` stuck `true` indefinitely: every tap is refused by `feed()`'s own guard, and nothing on this path ever rechecks the engine's state once `ensureStarted()` has resolved once. The second gap the backlog row names. Read at the lines.
6. `whenSoundRuns` (`:1482–1517`) and `showSoundPaused`/`hideSoundPaused`/`wakeSound`/`wakeSoundByKey` (`:1535–1569`) are general-purpose: none reads anything specific to a resume (no `hold`, no hidden span). They read only `audioEngine.state`/`ensureStarted`/`onStateChange`, `disposed`/`finished`/`suspended`/`asked`/`drill`, and the shared `stopSoundWatch`/`soundCheck`/`pausedStatusWas`. Read at the lines; nothing in them would need to change to be called from `advance()` instead of `resumeRhythmClick`.
7. `suspendDrill` (`:1907–1920`) and `resumeDrill` (`:1973–1988`) already key off the shared `stopSoundWatch`/`rhythmHold`/`rhythmJudgedFromMs` state, not off which caller created it: `suspendDrill` calls `stopSoundWatch?.()` unconditionally (`:1918`), which is exactly the `stop` closure `whenSoundRuns` installs, and which itself calls `hideSoundPaused()`. So a page hidden mid-wait already tears the paused affordance down correctly with no new code. On return, `resumeDrill` calls `resumeRhythmClick` (`:1987`) whenever `drill instanceof RhythmDrill` and the page was suspended; `resumeRhythmClick` (`:1443–1453`) already reconstructs a `{ from: 'top', pointMs: 0, wasSounding }` hold whenever `firstTapAt === null`, which is exactly a first-open hold's state — so hiding the page during a first-open wait and returning already re-enters `whenSoundRuns` correctly through the existing resume path, with no change to either function. Read at the lines.
8. `resumeRhythmClick`'s own `!audioEngine.supported` guard (`:1444–1447`) calls `startCountIn(target)` directly and returns, bypassing `whenSoundRuns` entirely, because `whenSoundRuns`'s own `check()` (`:1498–1508`) would otherwise find `audioEngine.state !== 'running'` forever on a browser with no Web Audio (`state` reads `'unsupported'`, `:59–63`) and hold the card indefinitely. The same guard is required at the first-open call site for the same reason. Read at the lines.

## Hypothesis and its refuting test

**Hypothesis.** Premises 2, 4 and 5 are the whole mechanism: `advance()`'s rhythm-card start treats "`ensureStarted()`'s promise settled" as sufficient to arm the latch, and nothing holds either the engine-level latch or the screen-level `rhythmJudgedFromMs` gate open while that promise is pending or resolves to a context that is not yet `'running'`. There is no second gate elsewhere on this path (no global input-suspend reaches a visible, non-suspended screen).

**Refuting test, run before any edit (red first).** Reuse the extended double (`holdStarts`/`releaseStarts`, `suspendAudio`/`resumeAudio`, `gesture`/`wakesOnGesture`) exactly as CL05b's own resume cases do, but applied at mount rather than after a hide.

- **Part A — the start never answers.** Set `audio.available = true` and `audio.holdStarts = true` before mounting a rhythm item, so the first `ensureStarted()` call `startCountIn` makes never settles. Send taps at the times the pattern's own onsets would fall if the grid's origin were the card-open moment. On the committed tree, assert at least one of those taps is matched (`result().correct` or `.answered` > 0) and `firstTapAt` is not `null` — judged against the moment the card opened, the red line. After the fix: assert `result().answered === 0` and `firstTapAt === null` for as long as the start is held, and that the status line reads `Sound is paused — tap to continue.` with the stage a keyboard-reachable `role="button"` target. Then `releaseStarts()`; assert the ordinary count-in now plays and the first tap after it is the first judged onset.
- **Part B — the start answers while the context stays suspended.** `audio.holdStarts` false, but `audio.engineState` suspended (the same freeze `suspendAudio()` already models) before the card opens, so `ensureStarted()` resolves at once while `audioEngine.state` stays `'suspended'`. Advance the clock well past where a four-click count-in would have finished if it were playing. On the committed tree, assert the status line never reads `Count-in —` and every tap sent in that span is refused; then call `resumeAudio()` alone — the platform's sound coming back with no further gesture — and advance the clock again: assert the card is still stuck refusing every tap, with no count-in ever begun — the count-in hangs, the second red line. After the fix: the same `resumeAudio()` call, through the watch's own `onStateChange`, is what lets the ordinary count-in begin with no gesture needed.
- **Part C — the gesture path.** As Part B, held and paused, but the context never comes back on its own (`wakesOnGesture = true`, no `resumeAudio()` call). After the fix: a tap or click on the card asks for the sound exactly once, inside that gesture; the ordinary count-in follows; the first tap after it is the first judged onset — the same assertions CL05b's own point-3 cases already use for the resume path.
- **Guard — sound already running.** The existing `openRhythm()`/`intoALiveRhythm()` path (`audio.available = true`, `holdStarts` false, `engineState` running by default) must behave exactly as today: count-in, first-tap latch, scoring unaffected. The existing cases already assert this; they must stay green, unmodified.
- **Guard — no Web Audio at all.** `audio.available = false` (jsdom's own default): the card must still carry on at once, with no `Sound is paused` line ever shown. The existing "with no Web Audio there is no sound to wait for" case (`:1135–1153`) already mounts a rhythm item with no prior `openRhythm()` call, so it already exercises first open directly; it must stay green, unmodified.

If all of the above already hold on the committed tree, the hypothesis is refuted and the real gap is elsewhere — look for whatever already guards this path before touching `advance()`.

## What is decided

Decided by the orchestrator under the entailed-decision rule (`operating-procedure.md` §11, "The orchestrator may settle a decision that is already entailed"), citing the reviewer's ruling on this row (`responses/1a89de52.md`) and CL05b's own already-approved rule for the identical principle on the return path (`responses/8764c643.md`, `responses/questions-91f683ff.md`):

- **A first-open rhythm card holds — no judged grid, no answer accepted — from the moment it opens until the sound is actually running** (`audioEngine.state === 'running'`); then its ordinary count-in plays and the card proceeds exactly as it does today. This is CL05b's own rule, read one edge earlier: "no judged rhythm timing against an inaudible or unestablished pulse, on first open as on return" (the reviewer's own phrase).
- **If the platform needs a gesture to start the sound, the same held-card resume affordance CL05b built for point 3 applies, unchanged.** The card's own stage becomes the non-judged, keyboard-reachable target, with the same sentence, `Sound is paused — tap to continue.` No new control and no new sentence: the reviewer already ruled this affordance for a held rhythm card, and X45's gap is the same held state reached one call earlier.
- **With no Web Audio at all, a first-open rhythm card carries on at once, exactly as today.** There is no sound state that can ever become available, and the reviewer already confirmed this for the identical case on return (`responses/1a89de52.md`, question 1): "the existing 'no metronome — your first tap starts it' behavior remains the truthful fallback for the unsupported-audio case" — which holds on first open for the same reason and must not regress.
- **Which function carries this is the builder's judgement, not a new ownership question.** `whenSoundRuns`, `showSoundPaused`, `hideSoundPaused`, `wakeSound` and `wakeSoundByKey` are already general-purpose (premise 6); `suspendDrill`/`resumeDrill` already compose correctly with a first-open hold with no change to either (premise 7). Whether `advance()`'s rhythm branch calls `whenSoundRuns`/`startCountIn` directly — the same shape `resumeRhythmClick`'s own `'top'` branch already uses — or through a small shared helper, is mechanical.
- **Unlike the resume path, a first-open hold has nothing to re-anchor.** Nothing has been played yet, so the ordinary `startCountIn` top-of-pattern count-in is sufficient on its own: no `RhythmHold`/`countInAgain`/second re-anchor is needed for this lane. If the builder finds that constructing a `{ from: 'top', pointMs: 0, wasSounding: false }` hold is the cleanest way to let `onNote`'s existing `rhythmJudgedFromMs` check do the work unmodified, that is the same kind of mechanical choice, not a new one.
- **The `!audioEngine.supported` guard is required at the new call site**, for the reason premise 8 gives: `whenSoundRuns` would otherwise hold an unsupported browser's first-open card forever.

## What a learner meets differently, for itemisation

On a platform where sound comes back on its own, a rhythm card's very first open now waits, silently, until the sound is actually running before its first count-in begins, instead of starting the clock the instant the card appears and either judging a tap against a click that was never scheduled, or playing no click at all and refusing every tap with no explanation once the context turns out to need more than one answered `ensureStarted()` call. A tap sent in that gap does nothing, rather than being scored against the moment the card opened or lost into a hang nothing ever recovers from. On a platform that needs a tap to start the sound, the card itself says `Sound is paused — tap to continue.` and is the one way back — the same sentence and the same card-as-button affordance already met on return from a locked phone. With no Web Audio at all, nothing changes: the card still carries on at once, silent, as it does today. This needs no ear.
