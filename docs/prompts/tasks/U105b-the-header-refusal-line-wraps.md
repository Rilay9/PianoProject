# U105b — the header's refusal line wraps to every line it needs, not clamped to one (fix-forward under the fast path; U105a's ruling extended to the header)

**A fast-path lane** (`operating-procedure.md` §11, the orchestrator's entailed-decision rule, `responses/questions-b96a36c8.md`). No product choice is open here. CI run 36779781211 on `122a5224` (the runner's face, Linux Chromium) failed `app/tests/e2e/score.screen.spec.ts:1379`, "a refused tap on the summary, upright (342 × 740): the sentence read once, whole, the sheet's copy a status," with "the sentence overflows its line: expected <= 283, received 302" (:1509) and "the sentence runs outside its line" (:1510) — the runner's own measurement, at its own size, not asserted here as general. Locally at the same 342 × 740 the sentence fits (the U105a pictures under `docs/prompts/pictures/u105a/`); the gap is the runner's font metrics, not the viewport. The header's line is styled by the same shape of one-line clamp (`white-space: nowrap; overflow: hidden; text-overflow: ellipsis`) that the reviewer already ruled against for the sheet's copy of this same sentence (U105a's third choice, verbatim below) and that G101 already ruled against for the Library title, under the identical runner-font mechanism.

**Decided by the orchestrator:** the header's refusal line (`#score-waiting`, the help strip's *now* line) wraps to every line it needs instead of being clamped to one, the same way the sheet's copy and the Library title already do. **Reason:** `responses/d0e1b01f.md` ruling 3 — "Wrap, do not force one line. A refusal sentence is state/explanation text, not a density-critical toolbar label. Keeping it whole at larger text/display settings outranks preserving one-line height. The current measurements showing one line at 740 px are a guard, not a reason to encode a clamp." — plus G101's ruling and measured fact, "a fixed line count would therefore encode a font/sample accident, not the invariant" (`responses/cbdfe6f0.md`), plus the code fact (verified below) that the header ever carries this sentence only while a run is not active, which is outside the one guard this particular clamp legitimately protects. No reviewer round precedes dispatch; the ordinary post-build seam review still applies.

## Hypothesis and its refuting test

**Hypothesis.** The rule at `style.css:6127–6132` is the whole mechanism holding `#score-waiting` to one line. Nothing else — no other CSS rule, no inline height, no ancestor `overflow: hidden` between `#score-waiting` and `.score-head` (`:2712–2718` has none) — cuts or hides an overflow of this element.

**Refuting test, run before any edit (red first).** Take the existing upright case (`score.screen.spec.ts:1379`, `342 × 740`) and force the sentence wider than the line by one of the two established techniques (`plan.spec.ts`'s Verdana/DejaVu stand-in, or `documentElement.style.fontSize = '115%'`), and separately by writing a synthetic sentence into `#score-waiting` directly (`page.evaluate`) that is far wider than any real font could keep under 283 px. If, under either technique, `copies.header.scrollWidth` still reads `<= clientWidth` and the sentence is not cut — the hypothesis is refuted, and something else (a fixed width upstream, a build-only class, or the runner substituting a narrower rather than wider face) must be found before touching `style.css`. If instead all three reproduce the CI shape locally (`scrollWidth > clientWidth`, `textInside` false, `ellipsis` true, the "not read once" failure), the hypothesis holds and the fix is exactly the rule named above.

## What is decided

- `#score-waiting` wraps to as many lines as its text needs while it is showing the refusal sentence (i.e., while the run is not active — the only state in which it ever carries that sentence), instead of `white-space: nowrap` / `overflow: hidden` / `text-overflow: ellipsis`. No fixed line count replaces the clamp (G101's lesson: "a fixed line count would therefore encode a font/sample accident, not the invariant," `responses/cbdfe6f0.md`).
- Its height follows its text: nothing pins the header, the help strip or `#score-waiting` to a fixed height (premise 5), and the stage below it in the same flex column (`.score-head { flex: 0 0 auto }`) moves down by the extra line, the ordinary consequence of a taller flex sibling — no new code needed for that, only a look to confirm it.
- Nothing is drawn over the now-taller line: the summary sheet is bottom-anchored (`#score-summary`, up to 72 % high per `docs/prompts/runs/U105a/ENTRY.md`) and the header sits above the stage in document flow, never overlaid by the sheet.
- **The mid-run guard is not weakened.** While a run is active, every other sentence `#score-waiting` shows (the ones `score.fuzz.spec.ts` seed 4 exists to protect, per the rule's own comment) stays clamped to one line exactly as today. The fix must be scoped to the state the refusal sentence actually occupies — not running, summary up — rather than removing the clamp unconditionally from `.score-head .help-strip__now`, or it reopens the regression the comment at `style.css:6105–6126` records. How that scoping is expressed (a `data-running` attribute selector, a class the summary state already sets, or another mechanical equivalent) is the builder's implementation choice; it is not a product decision.
- `.help-strip__what` (the mode name, e.g. "Keep tempo") keeps its clamp; it carries no part of this invariant and is not touched.
- The sideways rule (`.summary-refusal`'s own wrap, U105a's fix) is untouched.
- Sound-start policy stays out of CSS and U63's Today rules are untouched, as U105a's ruling already required.

**Learner-facing change, for itemisation:** upright, on a face or text size wide enough to need it, the header's line under *Keep tempo* may now take two lines instead of one, and the score moves down by that one line's height while it does. Nothing else about the screen, the sentence's wording, or what the refusal means changes. This needs no ear.
