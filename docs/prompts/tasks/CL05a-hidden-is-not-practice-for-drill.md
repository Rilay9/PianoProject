## Premises at the lines (HEAD `2c87b682a8c87d779d2824335a1bc3610bcda7c9`)

None reads `pageHidden()` or any suspended flag: `drill.feed(...)` (:692) and, for a settled non-manual-advance kind, `settled()` (:704) run while the page is hidden.
2. `onControl` (`:707–712`), the pedal drill's CC64 path, has the same shape — guards on `!drill`, `finished`, `disposed`, `cc !== 64`, none on visibility — and calls `drill.feed(...)` (:709) regardless of visibility.
3. `MANUAL_ADVANCE` (`:215–221`) is `{rhythm, backing-track, harmonic-dictation, dynamics, pedal}`. The comment at `:682–684` ("Only the manual-advance kinds can be in this state with the drill still accepting input") is true because the other kinds' own `feed()` already refuses a second answer once settled (`PromptDrill.feed`, `:93–96`, `this.answeredCurrent`) — a "stronger existing rule" in the review's own phrase (`4923be59.md:27`), but one that only fires **after** a card has been answered. It does nothing for a card that is still open and unanswered when the page hides: a key pressed on a note-flash, chord, interval or ear-* card while hidden is still that card's first and only answer, fed, scored and advanced in full.
4. `suspendDrill()` (`:1593–1638`) stops the backing-track loop, the form ticker, the dictation ticker, a live Simon chain (holding its gate shut, never calling `advance()`) and a running feedback timer (turned into a tap-hold via `holdAwaitsTap`, :1627). 5. The rhythm click is started by `startCountIn` (`:1234–1294`): `metronome = new Metronome(...)` (:1241), `metronome.start()` (:1286), kept alive by `metronome.onTick` (:1261–1285) until something calls `stopMetronome()` (defined `:1218–1222`, not shown above but grepped: it calls `metronome?.dispose()`). That happens at the top of `startCountIn` itself (:1235, stopping the *previous* card's click) and in `advance()` (:1338, same reason) — never in `suspendDrill`. `resumeClickAfterFirstTap`'s `stopMetronomeTicks?.()` (:1308–1309) unregisters the count-in's own tick listener, not the metronome itself. `Metronome.stop()` (`Metronome.ts:130–144`) does cancel not-yet-heard scheduled clicks and clear its scheduling timer, so the primitive to silence the click on hide already exists and works; nothing in `DrillScreen.ts` calls it from `suspendDrill`.
6. Every tap after that is judged against it — `at = input.tMs - this.startedAtMs` (:145), matched to the nearest unmatched onset in `this.pattern` (:148–159) within `this.toleranceMs` (:156). Nothing outside `special.ts` ever moves `startedAtMs` once it is set, and `suspendDrill`/`resumeDrill` never call into the `RhythmDrill` instance (premise 4) — so a hidden span does not just leave the click running (premise 5), it also leaves the origin every tap is scored against exactly where it was, unadjusted for the time that passed.

8. ## Hypothesis and its refuting test, per residue

**Residue 1 — the rhythm card's click and judged grid.**

*Hypothesis:* `suspendDrill()`/`resumeDrill()` never touching `metronome` or the live `RhythmDrill` (premises 4–6) is the whole mechanism by which both the click keeps sounding and the scoring origin stays unadjusted across a hidden span — there is no second path (a `requestAnimationFrame` loop, a second timer, an audio-graph scheduler outside `Metronome`) that also drives the rhythm card's click or grid.

*Refuting test, run before any edit (red first):* mount a rhythm item (`fromCatalog.ts:576–594`'s shape: `drill: { kind: 'rhythm', params: { bpm, bars, timeSig } }`, as the existing item-builder functions in `drillLifecycle.test.ts:150–238` are built), tap once to start the pattern (`press(midi)`, latching `firstTapAt` and starting the post-tap click), hide the page, advance the fake clock by several pattern-lengths, and assert the piano/metronome spy fired no more clicks after the hide and that a tap sent while still hidden matched no onset and moved `result().correct`/`result().answered` by zero. If either assertion is already green on the committed tree (no edit made), the hypothesis is refuted — something already silences the click or freezes the grid, and that must be found before touching `suspendDrill`.

**Residue 2 — `meanReactionMs` including the hidden span.**

*Hypothesis:* the shared `promptAtMs = clock.now()` / `reactionMs = tMs − promptAtMs` shape (`PromptDrill.ts:89,124`; `harmony.ts:508`; `simon.ts:588`), fed by `systemClock`'s unthrottled `performance.now()` (`engine/types.ts:26–28`), is the whole mechanism by which a hidden span inflates the interrupted card's `reactionMs` — there is no separate place a card's answer time is computed or stored (e.g., inside `DrillScreen.ts` itself) that would already exclude it.

*Refuting test, run before any edit (red first):* mount a note-flash (or any `PromptDrill`-backed) item, let a card show, hide the page, advance the fake clock by several minutes, show the page again, and answer correctly. Assert `drill.result().meanReactionMs` (or the single answer's `reactionMs`) is close to the visible time only (a few tens or hundreds of ms), not the full hidden-plus-visible span. If it already reads the visible-only figure on the committed tree, the hypothesis is refuted.

**Residue 3 — hidden key/MIDI input still feeding a card.**

*Hypothesis:* the absence of any `pageHidden()` (or suspended-flag) check in `onNote` (`:678–705`) and `onControl` (`:707–712`) is the whole mechanism by which a key or MIDI note sent while the Drill screen is hidden still reaches `drill.feed(...)` — no other guard (a global input-suspend elsewhere in the app shell, a MIDI-source-level pause) already refuses it upstream of `onNote`.

If this is already true on the committed tree for the kind chosen, try a second kind before concluding the hypothesis is refuted — premise 3 already shows one kind (post-settle `PromptDrill` cards) is protected for an unrelated reason, so the discriminating case must be a card still **open** when the page hides.

## What is decided

- The three residues are fixed together, as the review requires (`4923be59.md:23`, quoted in full at premise 11): stopping the rhythm click without re-anchoring its scoring origin is explicitly ruled out ("Do not leave the judged clock running merely because re-anchoring takes work").
- **The re-anchoring mechanism** — how `RhythmDrill`'s `startedAtMs` (and, if the same shape is reused, `PromptDrill`/`ChordDictationDrill`/`SimonDrill`'s `promptAtMs`) is shifted forward by the hidden duration on resume, and where that hidden-duration figure is computed and carried (a value read off `performance.now()` at suspend and again at resume inside `suspendDrill`/`resumeDrill`, the same pattern already used for the backing-track loop's held bar, premise 10) — is the builder's judgement. It must be a mechanical suspend/re-anchor: a fresh reading taken at suspend, applied once at resume, so "the same visible-time relationship" (the review's phrase) holds — not a restart, not a skip, not a running clock left to drift.
- **The engine shift method is decided**, per the second read of the responses at `7de0ee2d`: an optional shift method on `Drill`, following the precedent of the existing optional `reveal?()` (`types.ts:258`), is the smaller of the two mechanical routes (premise 14) — not a visible-time clock threaded through `drillFromCatalog`'s `clock` option and `toEngineInput`, which would also have to translate the audio-anchored conversions and the dictation tick. Each drill moves its own `promptAtMs` through this method; `RhythmDrill` moves its origin (`startedAtMs`, by calling its own `startAt`, premise 13) through the same method rather than a second, bespoke one.
- **Where the input refusal lives** is the builder's judgement, within the review's constraint: it must be owned by the suspension boundary, not duplicated per drill kind, unless a kind already has a stronger rule of its own (premise 3's `answeredCurrent`/`simonAnswerFromMs` precedent — leave those alone). A `pageHidden()` check placed once, at the top of `onNote` and `onControl`, or a `suspended` flag flipped by `suspendDrill`/`resumeDrill` and read in the same place, are both consistent with the review's wording; which one, and whether `onControl` (the pedal drill's CC64 path) is included, is left to the builder, since the review names "Key/MIDI events" and does not single out CC.
- **This is now resolved**, per the second read of the responses at `7de0ee2d`: the flag `suspendDrill` sets and `resumeDrill` clears, not a direct `pageHidden()` read, because the suspend/resume boundary also fires on `pagehide` (`screenLifecycle.ts:77`), which `pageHidden()`'s point-in-time check of `document.visibilityState` (`screenLifecycle.ts:46–48`) would miss (premise 15). `onControl` is included: the review names "Key/MIDI events" without singling out CC, and the pedal drill's CC64 path has the same shape as every other kind's note input (premise 2).
- **The stop condition, verbatim** (`4923be59.md:31`): "If preserving the rhythm card's scoring origin requires a new state/ownership decision rather than a mechanical suspend/re-anchor, stop and bring that architecture choice back instead of approximating it." If shifting `PromptDrill`/`ChordDictationDrill`/`SimonDrill`'s `promptAtMs` needs a change to what owns a card's identity or lifecycle — rather than a new method that moves an already-private timestamp forward by a number handed in from `DrillScreen.ts` — that is the trigger. Bring it back rather than approximate it.
- **This condition is not met**, per the second read of the responses at `7de0ee2d`: premise 13 shows `RhythmDrill`'s origin re-anchors through its own existing `startAt`/`startedAt` pair with ownership unchanged (the drill still owns the origin; the screen still only decides when, `screenLifecycle.ts:35–38`), and premise 14's shift method moves each drill's own already-private timestamp without changing what owns a card's identity or lifecycle. The fix proceeds as the mechanical suspend/re-anchor the review asks for; no architecture choice needs to come back.
- **What a learner meets differently**, for itemisation: a phone locked mid rhythm card, or mid any Drill card, now behaves like the other three screens CL05 already fixed — no clicks sound into the locked screen, no taps or key presses during the lock are charged as misses or extra taps, the card's reported average time to answer is not inflated by how long the phone was locked, and the card resumes exactly where it was, judged against the same grid, rather than the learner finding it either frozen mid-click or silently caught up. This needs no ear.
