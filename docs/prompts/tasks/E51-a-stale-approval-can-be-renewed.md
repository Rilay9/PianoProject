## What is decided

1. **The rule, verbatim** (`responses/f972756.md:12`): *"**CONSTRAINS NEXT BRIEF — E51 is the next excerpt-approval workflow repair.** `merge_text` refuses a second approval of the same parent/range/selection even when the existing approval is stale by parent bytes or cut version. The validator tells a person to re-decide all five, but the current merge offers no way to record that decision. Build E51 before seeking or claiming renewed boundary approval, preserving the old event and allowing a new explicit decision for the current parent and cut version. This does not make a stale boundary current by implication."* And :15: *"**PRUNE/MERGE — no automatic carry-over for the three byte-identical cuts.** Their file identities match, but the boundary approval was made under cutter version 1. The cutter version is part of the reviewed boundary contract. A person may reapprove them quickly after comparison through E51; carrying them by byte equality would contradict the approved E33 ruling."* The premise checked at the line: `merge_text` is at excerpts.py:729 and its refusal at :764–770 never asks whether the stored approval is stale.
2. **Stale, in the code's own terms.** A stored approved row is stale when either (a) **stale by provenance**: its `parentSha256` is present and differs from the sha256 of the parent's current built file (validate.py:1077–1081; the provenance block's `stale`, excerpts.py:651–656, which keeps that one meaning, :647–649); or (b) **stale by cut version**: `approved_cut_version(row)` — version 1 for a row with no `cutVersion` (excerpts.py:79–81) — differs from `CUT_VERSION` (validate.py:1082–1085). A row with no `parentSha256` is not stale by provenance (the validator's `if approved and …`), only possibly by cut version. The merge reads the parents' current bytes the way the validator and the build do (`sha256_of(content / parent["file"])`, validate.py:1077–1078, excerpts.py:605), handed to `merge_text` by `main` beside `known_ids` (:902–904). Without them (`None`) the merge judges cut version alone, so a row stale only by provenance is not renewable there: it fails closed.
3. **The merge's new path.** An incoming decision on the same parent, bars and selection as a stored approved row that is stale by (a) or (b):
   - **approve or adjust**: accepted only when the event names the parent's current bytes (its `parentSha256` equal to the current sha; missing or different is refused, with the reason that a renewal is a decision on the current parent). The new row is stamped `cutVersion = CUT_VERSION` by `_row_of`, as every approval is, and becomes the one active row.
   - **reject**: the stale approval is withdrawn — the rejection kept in `rejected` with its reason, the stale row no longer active, so the build stops cutting it. Why it is in: the ruling says *a new explicit decision*, the merge's decisions are three (excerpts.py:98), and a person re-deciding may decline. Today a rejection of an approved range is appended beside the still-active approval and the build goes on cutting it; for a range whose approval is *current* that stays as it is (not E51's; a follow-up line).
   - **The old row preserved, byte for byte**: every field as it was — its absent `cutVersion` still absent, its old `parentSha256` unchanged — in a top-level `superseded` list, each entry the old row plus the id of the event that superseded it; a chain of renewals keeps every earlier row, in order. Why a list beside `rejected`, not the old row left in `excerpts` or nested in the new one: the build and the validator read `excerpts` only and refuse two rows with one signature (validate.py:1028–1030); `_same_decision` compares whole rows, so a nested old row would make the renewal, merged again, read as *other content*. `read_definitions`, `serialise_definitions` and `COMMENT` carry the key; the serialiser writes it only when it is non-empty, so the committed file still round-trips byte-identical (test at :400–407) and a merge with no renewal leaves it so. `by_event` indexes superseded rows too: the old export merged again is skipped (not refused, not re-appended), and the renewal merged again is skipped.
   - **A current approval still refuses**: an approval of a range whose stored approval is stale by neither (a) nor (b) is refused exactly as today, with the row named (the test at :371–381, green unchanged).
   - **Nothing current by implication**: the merge never rewrites a stored row's `parentSha256` or `cutVersion`; byte-identical cuts carry nothing over (the three the reviewer names); no row is renewed without an incoming event with its own id, reviewer and time.
   The lane widens beyond `merge_text` by exactly: `main`'s one call, and `read_definitions`, `serialise_definitions` and `COMMENT` for the key. The consumers of `content/sources/excerpts.json` as read at drafting: `attach_excerpts` and the build (through it; `build.py:1031–1033` reads the carried event), `validate.excerpt_findings`, `test_measured_truth.py:418` — all read `excerpts` only; `DevExcerptView.ts` reads the proposer's projection (`dev/review/excerpts.json`), not this file, and `excerpt_proposer.py` reads no approvals. If a consumer breaks on the list, say so and take the better path, recorded.
