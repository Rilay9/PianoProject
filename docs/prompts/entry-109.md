## The mechanism

**The fault.** D4 set `transferRelationship` from an unawaited `Promise.all([rungRows(), catalogIndex()])` after the score loaded, while ▶ was already live, and passed `intent` to `runFacts` whether or not it had resolved (`ScoreScreen.ts`, D4's 4289–4292 and 3192–3196); `runFacts` wrote the intent alone when the relationship was undefined. So a quick run stored the intent without a relationship, and any run stored a relationship recomputed at opening, not the card's.

**The discriminating tests** (red on D4's code, green now): the pending read with a forced finish (a row with the intent and no relationship → none); the history changed between offer and opening (the recomputation → the snapshot's bytes); the happy path (the relationship stored ≠ the snapshot's → equal).

**The change, on the mechanism:**

1. **Today keeps the offer as shown** (`TodayScreen.open`): the session's own claim — item, skill, the item's material, `relationship`, `contact`, the card's day (`dayKey(now)`) — with the card's offer token, written by `offerSnapshot.writeOfferSnapshot` to one `settings` row (`pianopath.transferOffer`); the route opens only when the write has settled, as `?intent=transfer&skill=…&offer=<token>`. A second tap is ignored.
2. **Bound to the exact offer instance**: a token minted each time the card is composed (and again when the offer's row is swapped away), and every composition or swap clears the kept row (`supersedeOffer`), except after the tap (`leaving`), so a composition already in flight cannot undo the tap's own snapshot.
3. **The read before play** (`ScoreScreen`): started as the screen is built (`loadOffer`), awaited in the load flow before the keys are attached and the bar shown; while it is out the screen is still "Loading…", ▶ is disabled (`render`), `startRun` — the one gate every start passes — starts nothing, and a finish would build no run. `kept` needs the route's token, this item, this skill and today; anything else is a named refusal (`missing`, `superseded`, `other-item`, `other-skill`, `other-day`, `corrupt`, `unreadable`) and the screen shows the line and records practice.
4. **The pair as one fact** (`material.ts`): `RunFacts = MaterialFacts & (TransferFact | NoTransferFact)`, and `runFacts`'s argument the same union; an intent handed in without its relationship (only a cast can) gives no transfer fact at all.

**The builder's calls, each with its reason.** The `settings` store, not `plan`: a key-value row, as the daily read's days are kept; the `plan` store is keyed by `PlanRow.id` and a snapshot is not a plan row. Every recomposition supersedes (the reviewer: "recomposed … or its row swapped away"): a recomposed card is a new decision even on the same item, and the cost is one refused stale link. Two variants of the line, one shown per case: *no longer on today's card* is untrue where the stored value could not be read, so `corrupt`/`unreadable` say *This offer could not be read back; opened as practice.* The line has its own element under the header (`#score-offer-note`, a CSS rule of its own): the header's status line is cut at phone width. The snapshot stores the material and does not match on it (the brief's four conditions). A failed write still opens the route, where the Score screen finds no snapshot and says so.
