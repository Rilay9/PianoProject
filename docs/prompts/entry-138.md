## The mechanism

**The fault.** The app had no layer for what the learner intends to do with a piece. Every surface guessed from `ProgressRow.status` (`new | started | passed | mastered`, which C5 took out of rung truth and which says nothing of intent), so a piece learned long ago read as new or as merely due, "learn this" had nowhere to go, and Stage 9's page presented its units' ordinary `runs` requirements as a rung to count (L86).

**The orchestrator's hypothesis, tested:** the lifecycle can live beside `ProgressRow.status` with no consumer needing both. The refuting test was a reader that must read the project state to stay truthful. Readers read at the lines: `learnedPieces` (a measured pass or mastery, true whatever the project), the repertoire retention in `session.ts` (fed by `learnedPieces` from `TodayScreen.ts`, line 706), `contact`/`familiarity` (facts of what was met), the Progress repertoire list (mastered pieces), the Library's status filter (not opened: X3's; it reads `ProgressRow.status`, whose words stay true). **It held for truthfulness:** no reader prints a false sentence with projects in the store. The guard test exercises `learnedPieces`, contact, familiarity, the rung state, the skill ladders and the progress row unchanged across every transition; the session's retention reader and the Library's filter are held only by the source walk (neither imports the store) and were not exercised. **One tension of policy, not truth:** repertoire retention can offer a piece the learner put away or paused — *Keeping this piece playable* is still a true reason, but it overrides a stated intention. R19's note has the reviewer deferring exactly this ("the no-rung retention decision is presented to the owner when these semantics are specified"); I left the reader as it is (the brief's item 3) and put it as Questions 1.

**The change, on the mechanism:**

1. **The store** (`db.ts`): `DB_VERSION` 9 creates `projects` (keyPath `id`, index `byItem`) and touches no other store; `ProjectRow { id, material, itemId, state, since, history: [{ state, at, why, performedOn? }], goal?, problem?, sections? }`; in `STORE_NAMES`, so the backup carries it. `why` is the learner's action (two actions enter `maintaining`); `performedOn` is *I performed it*'s day. The brief's `why?` is kept as the action, always written.
2. **One writer, one door** (`projectStore.ts`): `applyProjectAction` enters the action's state (`ACTION_STATE`) from the one the project is in, appending one history line, and refuses — writing nothing — an action the sheet does not offer for that state (`OFFERS`, the table below). No state moves by time or by a run. Its only caller in `app/src` is `ui/projectSheet.ts` (a test walks the source and holds it so). The store's changes run one at a time: two quick edits (a goal typed, then the problem) each read the row and wrote it back, and the second erased the first — found by the sheet's notes case, fixed by queueing the read-modify-write, and held by a mutant.
3. **Identity fails conservatively** (`projectIn`): a project is keyed by the piece's material (`material.materialKey`: the built file's sha256; an import's stored bytes, hashed where the Score screen loads them), so a second catalogue id of the same file finds the same project; where the item names no material the row is `id:<itemId>` and answers for that id alone. A material project is also found by the id it was made under (the catalogue building the same id's file again), never by another id.
4. **The sheet** (`projectSheet.ts`): title; state and since, or *Not a project yet*; the history's last line (*I performed it*'s day, else the state before this one and its day — the state line already says the current one); the encounter line from `encounterStore.familiarity` with the piece's bars as its extent (without them a whole-piece run read as "part of it" — caught by the finish-sheet case); the offered actions; R18's three fields once there is a project. Opening it writes nothing. It closes with the screen that opened it (found in the pictures: it stayed over Progress and a lesson page after the route changed).
5. **The doors:** the Score screen's finish sheet (`ScoreScreen.ts`, one button, a song only, the material this visit played) and Progress (`ProgressScreen.ts`: the Projects block, newest change first, and *Make it a project* for a passed or mastered song with no project).
