### 4a-3. What an audit of §3 found, and what it corrects

### 4a-4. What writing the rotation spec turned up

Reported, not fixed. `app/tests/e2e/score.rotate.spec.ts` exists now (10 tests, unrun) and covers
every edge case §3a asked for, at the round sizes *and* at the owner's 740x342 / 342x740.

- **At `barsPerWindow: 1` a turn never re-engraves.** `updateReadAhead()` returns `single` both
  ways up and the slot count stays 1, so it returns `false` and `stageChanged()` takes the branch
  that only re-fits. The five-bar sliding chunk stays on screen, scaled down into 360 px, until
  the next note arrives — and in Wait mode "the next note" is indefinite. This is the "one bar
  rotated to portrait drawn tiny" fault a previous round reported as fixed; the fit was fixed and
  the re-engraving was not. The handoff's four upright assertions all pass in that state, because
  five bars of ink *do* fill the width, so the honest assertion is on the drawn range.
- **`frozen` survives a same-arrangement turn.** It is nulled only when the arrangement or the
  slot count changes, which at one bar per window never happens — so a run frozen sideways keeps
  that scale as a ceiling through the turn. The comment above the guard describes exactly the case
  the guard does not reach.
- **`fitToStage()` early-returns on a width-only change**, so the OSMD zoom is never re-chosen —
  only the CSS scale. The screen's `onResize` clears the cached height first, so a window resize
  is fine; a stage that changes width *without* the window doing so is not, which is a tablet
  side panel arriving.
- **`engravedWidth` is not on the `scoreFit()` hook**, so a test cannot assert the field the
  scroll path actually compares; the spec reads the `<svg>` width attribute instead.
- **`inkBox()` in `tests/e2e/scoreControls.ts` is a trap for per-slot work.** It unions every
  element under the front `<svg>` — across both slots upright — and includes exactly the elements
  `WindowRenderer.inkBox` guards against: the metronome mark at 2584 units, a tie whose path
  lands at x = -5,000,000. Fine for what it was written for; wrong for rotation measurement.

### 4g. The folder import still hangs the phone — diagnosed 2026-09-10

The owner picked a folder on the S25 after the progress bar and Cancel button
landed. The files were read correctly and the listing is readable, but the app
froze, the phone struggled while it sat in the background, and no button
responded. Progress and cancel exist and are not the problem. Four causes, in
order of how much they cost:

**1. `onProgress` fires once per file, and the handler writes the DOM.**
`readDirectoryHandle` calls it for every entry, and `showReadingProgress` sets
two text nodes and a width on each call. For 1,533 files that is 1,533 forced
style-and-layout passes interleaved with file I/O. No single task is long, so a
long-task profile looks clean, and the UI is still unresponsive — death by a
thousand cuts. **Throttle by time, not by count: at most one update every
~100 ms, coalesced into a `requestAnimationFrame`.** This is the cheapest fix
and probably the largest single win.

**2. `await entry.getFile()` is serialized, once per file.** Each call is an IPC
round trip to the browser process, and on Android that is not cheap. A thousand
of them in sequence is dominated by latency, not work. **Collect handles during
the walk and resolve them in chunks with `Promise.all` — 32 or so at a time —
so the latency overlaps instead of accumulating.**

**3. `yieldToUI` uses `setTimeout(resolve, 0)`, which is the wrong yield.** It
puts the continuation at the *back* of the task queue, so anything else queued
in the meantime runs first, and Chrome clamps the delay to 4-10 ms — far more
when the page is not visible. `scheduler.yield()` keeps the continuation at the
front and preserves priority. **Use `scheduler.yield()` where available and keep
`setTimeout` only as the fallback.**

**4. Backgrounding is the "phone hanging" symptom, and it is not a bug in the
loop.** When the owner switches away or the screen locks, Chrome on Android
throttles timers aggressively and may freeze the page outright. An import built
on `setTimeout` therefore *stops* rather than continuing, and on return the app
has a backlog to work through — which is exactly "it hung in the background and
then no buttons worked". Two things follow: the work belongs off the main
thread, and the screen has to say so.

**The structural fix: do the walk in a Worker.** `FileSystemDirectoryHandle` and
`FileSystemFileHandle` are serializable, so the picked handle can be posted to a
worker and the whole traversal run there, reporting progress by message. The main
thread then stays responsive by construction — 1, 2 and 3 stop mattering, cancel
works instantly because it is a message rather than a flag checked between
blocking hops, and backgrounding degrades to "slower" rather than "wedged".

**What the owner should see, so a slow import stops reading as a broken one.**
The confusion is a separate fault from the slowness and worth fixing even if the
worker is deferred:

- **Name the phase.** Counting and reading are different waits and should not
  share one sentence. "Looking through the folder… 412 files so far", then
  "Reading 412 of 1,533". A number with no denominator reads as a hang; a number
  that stops climbing reads as a crash.
- **Never let the bar sit still.** While the total is unknown the bar should be
  indeterminate rather than at 0%, which is indistinguishable from stuck.
- **Say it is safe to wait, and what not to do.** One line: "This can take a
  couple of minutes for a large folder. Keep this screen open." Backgrounding is
  the thing that actually breaks it, so say so rather than letting the owner
  discover it.
- **Make Cancel reachable and instant.** It exists, but a saturated main thread
  cannot honour it. In a worker it is immediate.
- **Finish with a sentence, not silence.** "1,533 scores added, 12 skipped" and a
  way to see the skipped ones. The owner's report — that the files did in fact
  arrive and look right — means the import succeeded and simply never said so.
- Consider a `navigator.wakeLock` request for the duration, released on finish.

Test that would have caught it: drive an import of a fixture folder of a few
thousand files and assert the main thread stayed responsive — that a click on
Cancel is honoured within a few hundred milliseconds while the walk is running.

### 4g-2. The import walk moved to a worker — 2026-09-10

`4g`'s structural fix, built. `src/data/folderWalk.worker.ts` takes the picked
directory handle, walks it, opens the scores in chunks and posts progress back;
`readDirectoryHandle` is now a thin client for it and the old main-thread walk
survives as `readDirectoryHandleOnThisThread`.

Three fallbacks, because this feature only exists in Chromium and a handle is
not guaranteed to survive `postMessage`: no `Worker` constructor, a constructor
that throws, and a `postMessage` that throws `DataCloneError`. Each of them runs
the old walk and returns the same listing. A refused clone reading as "no scores
found" instead of "slower" is the failure this could plausibly have shipped
with, so it has a test.

`walkFolder` is exported and the `self.onmessage` shell is a guarded five lines
around it, so the walk is driven directly by
`tests/unit/folderWalkWorker.test.ts` — seven tests. Routing the real walk
through a fake `Worker` was tried first and asserted a module-loading trick
rather than the walk; the trick broke before the walk did.

What this buys, beyond speed: cancel is a message rather than a flag checked
between blocking hops, so it lands when pressed; and a browser throttling a page
it cannot see now slows the import instead of wedging it, which is what "it hung
in the background and then no buttons worked" was.

Still on the main thread, deliberately: parsing the manifest and building the
listing. They are fast, they need no file system, and moving them across the
boundary would cost a second copy of every file for nothing.

### 4i-3. Overlays covered the screen without disabling it — fixed 2026-09-10

The third item in `4i` ("worth one look at whether the summary should take the
bar's controls out of the tab order") turned out to be app-wide rather than the
summary's alone, and it is the same fault as the folded control bar: something
the owner cannot see answering a tap.

**Every sheet.** `openSheet` in `ui/widgets.ts` set `role="dialog"` and drew over

### 4p. A recurring mic flake was a float comparison, not the microphone

### 4m-3. The bar cannot give every control forty pixels. 4i-2 was right.

Two CI runs settled it, and both of my arguments against 4i-2 were wrong.

**Run 67.** Widening `#score-play` and `#score-more` to 40 wrapped the row on
the Linux runner at 342 px. The first argument — "4i-2 added the minimums as
fixed widths, and flex absorbs" — is false.

**Run 68.** Making `.score-bar > .score-select` shrinkable did not help either,
and the reason is worth writing down because it is easy to get wrong: **a flex

within a line afterwards.** Wrapping happens *before* shrinking, so a shrinkable
item still starts a new line. The measurement that seemed to vindicate it — "the
row holds at twice the font size" — was taken on Windows, where the title and
the tempo readout absorb everything, and proved nothing about the runner.

to get them is to carry fewer controls, not to find pixels that are not there.
That is 4i-2's option 1, and it is still the owner's call.

valve. Kept, because each was free: the tempo readout's height (43 x 17 was the
worst target on the screen and the height cost nothing horizontally), the

sweep skipping `inert` subtrees, and the count-in's clearance above the bar.

### 4m-4. The bar carries less when it cannot afford more — the obvious answer

Two CI runs and three attempts went into finding forty pixels for `#score-play`
and `#score-more` in a 342 px row. The pixels are not there, and looking for
them was the wrong question. The owner's words: "of course not every control has
to have 40 px, or even show up if there's not enough room... less likely to be
used controls can always be hidden in the `...` menu when necessary."

`fitBarControls` in `ScoreScreen` measures the row and moves controls into the

phone turned sideways gets its controls back rather than keeping whatever the
narrower way up decided. It is skipped while the sheet is open, because the
stash's children are inside it then.

least. Hearing the piece is occasional. Play, the mode, the tempo readout and
`...` never leave — `...` is where the others go, and a gateway that could hide
itself would be a trap.

So the 40 px floor is back on Play and `⋯`, and it is affordable now: whatever
it costs, the bar stops carrying something.

Measured: at 280 px and 320 px the hands group moves to the sheet and everything
left is at least 40 x 40 on one row. At 342 px and above nothing overflows *on
Windows* — and that is the point of measuring rather than choosing a breakpoint,
because the runner's fonts are wider and it will overflow there if it needs to.

`score.bar-targets.spec.ts` gained the assertion that matters most: a control
that leaves the bar is still **in the sheet, under its own name, and enabled**.
A control that quietly vanished at a narrow width would be worse than either
drawing it small or wrapping the row.

### 5q. The silent hang at boot — a real fault, and the best candidate for 5p

5p's lead was wrong and checking it is what found the right one. The unawaited
`indexedDB.deleteDatabase` cannot be the cause: Playwright gives each test its
own browser context, so storage is already empty and the delete has nothing to
block on.

What *can* hang is the content read. `readJson` called `fetch` with no timeout
of any kind, and `fetch` has none of its own — so a response that is accepted
and then never arrives leaves the await pending for ever. The retry beneath it
never runs, nothing rejects, and every screen waiting on the catalog never
appears. **It is the only path in the boot that can hang without saying
anything**, which makes it the best available explanation for a screen failing
to mount inside a 120 s wait and passing on a re-run — a serial 42-minute suite
making thousands of requests of one preview server is exactly where a stalled
response would show up.

It matters more off the runner. The app is offline-first and these files are
precached, so a read normally costs nothing; a stalled one is a blank screen
with no message on a bad connection, which is the owner's phone on a train.

Fixed with an explicit `AbortController` and a 12 s timer, cleared the moment
the response arrives, and the retry given twice the patience because the case it
exists for — a first launch that lost the network mid-precache — is slow rather
than dead. Not `AbortSignal.timeout`: that schedules on a clock no test can
advance, and unassertable is how this came to be missing in the first place.

`contentFetchTimeout.test.ts` holds a request open for ever and asserts the read
rejects rather than hanging. **Verified by reverting**: with the signal removed,
two of its three fail.

**This is a candidate, not a demonstration.** It is a real fault fixed on its own
merits; whether it was *the* cause of 5p will only show in whether those
failures stop. Worth watching rather than declaring.

### 5t. The rotation cell's 41 % — cause found, fix attempted, fix reverted

**The cause, measured.** At 342 x 740, one bar per window, Hot Cross Buns:

| how you got there | slots | ink each | share of stage |
| --- | --- | --- | --- |
| opened upright | 4 | 88 px | **53 %** |
| turned upright | 2 | 140 px | **42 %** |

The same screen, at the same size, differing only in how it was arrived at —
and one of the two is under §9.35's 45 % floor, which is the gallery's
complaint.

**The chain.** `stageChanged` clears `held` and `pieceInk` on a turn, correctly:
they were taken at the old width. `updateReadAhead` then chooses the slot count
in the same breath, and `chooseSlotCount` with nothing to measure returns its
fallback of **2**. The run re-freezes 150 ms later (`freezeAfterSettle`), and
once frozen `chooseSlotCount` returns the count already held — so when the probe
finally re-measures, the fallback is what the rest of the run keeps.

**The attempted fix, and why it was reverted.** Marking the count provisional
when it is chosen without measurements, and letting `fitSlots` re-choose once

squeezed score the owner photographed in the first place. Reverted, code and
test both, so the suite stays honest.

**What a real fix has to do**, for whoever takes it: re-choosing the count after
a turn has to happen *together with* the re-engrave, not as a separate later
event. `fitSlots` only applies a changed count when `currentStep <= 0`
(`08` §9.6 forbids re-drawing the system holding the cursor), and a turn

### 5w. A bug hunt in skills, curriculum-edge and chord-chart — three fixed, one flagged

Scoped to `SkillsScreen.ts`, `ChordChartScreen.ts`, `prerequisites.ts`,

**The chord chart never comped its own first bar, and a one-bar chart never

### 5y. A bug hunt in PDF, paper-book and shelf storage — six fixed, four flagged (2026-09-11)

Scope: `app/src/pdf/**`, `PdfScreen.ts`, `PaperScreen.ts`, `booksStore.ts`, `levelOverrides.ts`.
Same shape as §5i and §5x: right on the data a test uses, wrong on the data the owner has —

**Fixed, each with a test that fails without it (all reverted and re-run to prove that, then
restored).** Ranked by how often the owner meets it.

1. **Opening a PDF detected every page's systems before drawing the first one, and never wrote
   the result back except through "Adjust cuts"' own Save button.** A long book paid the full
   detection cost — a rendered page plus a pixel-by-pixel projection profile, per page —
   sequentially, on every single open, whether or not the owner ever touched a cut. Only the
   page being opened is detected before anything is drawn now; the rest run afterward, nearest
   the opening page first (`pdf/detectionOrder.ts`'s `backgroundDetectionOrder`), and the result
   is persisted once so the next open of the same book costs nothing.

   cuts, only after the background pass finishes. A second case proves a book whose cuts are
   already stored triggers zero further detection calls.
2. **The rendered-page cache could evict the page on screen.** `PAGE_CACHE_SIZE` is 3,
   `ensurePage`'s eviction was insertion-order regardless of what a draw currently needs, and
   `followCount()` is uncapped — a piece with small systems on a tall stage can want four or five
   pages of read-ahead at once. The page inserted first (the current one) is also evicted first

   removing a system on an earlier page — the normal way to work through a scanned book, flipping
   back to fix page 2 while reading page 40 — shifts every later system's index, so closing
   "Adjust cuts" landed on a different system with nothing on screen to say it had moved.
   `pdf/systemPlan.ts`'s new `reindexAfterRebuild` finds the same `(page, indexOnPage)` pair in
   the rebuilt list (or the last system left on that page, if the exact one was removed).
   `tests/unit/pdfSystemPlan.test.ts`.
4. **A twin the catalog no longer has is not a twin — the exact fault `ShelfScreen`'s own piece
   row was fixed for, unfixed one screen over.** `PaperScreen`'s "Practise with the score" button
   showed whenever a piece had an `itemId`, with no check that the import or bundled item behind

   the score screen's own "unknown item" page. It now checks `findItem` first, the same as the
   Shelf list does. `tests/unit/paperScreenTwin.test.ts`.
5. **`levelOverrides.setLevelOverride`/`clearLevelOverride` broke their own comment's promise.**

   its quota. Both now swallow a failed write and always notify. `tests/unit/levelOverrides.test.ts`
   gains two cases that spy a rejecting `db.put`/`db.delete`.
6. **A page number past the end of a linked PDF silently opened at page 1 with no

### 5z-2. A bug hunt in the engine and drill logic — two fixed, several checked and clean (2026-09-11)

Scoped to `app/src/engine/**` — the note-matching in `PracticeEngine.ts` and the drill
generation under `drills/**` — which nothing this week had touched. Same brief as 5i/5w/5x/5y:
right on the data a test uses, wrong on the data the owner has. Two real faults, both in
`PracticeEngine.feedTempo`, both about a note that does not behave the way a clean unit test
assumes; the rest of the area — Wait mode's chord and hand-filter logic, the drill factories,
the harmony/theory translation layer, `steadiness.ts`, the pedal/dynamics/rhythm drills — was
read closely and is clean.

**1. A bouncing key in Tempo mode turned one correct strike into a hit *and* a wrong note.**
A cheap contact (or a flaky USB cable) can fire two Note-Ons for one physical strike with no
Note-Off between them — the key never came up. The first Note-On matched its slot and closed
it; the second found the slot already gone and, since it still matched no *open* slot, was
scored as an extra wrong note on top of the hit that had just been earned correctly. docs/05's
own robustness list ("expect duplicate Note-Ons ⇒ idempotent") already covers this for Wait
mode's `satisfied` set; Tempo mode had no equivalent. Fixed in `PracticeEngine.feed`/`feedTempo`:
a Note-On for a pitch that is already down, with no Note-Off since, is dropped before judging —
but only when the source is deterministic (`!accuracyEstimated`). The exception matters: the
microphone cannot see a key come up at all, so `audio/pitch/detector.ts`'s re-strike detection
(the dip-then-rise in energy that is its *only* way of ever reporting a repeated note) reports a
genuine repeat exactly the same way, as a second Note-On with no Note-Off in between — the guard
would make every repeated note invisible to a mic-driven run if it applied there too, so it is
keyed off `accuracyEstimated` rather than being unconditional.

The same "already down" signal was tried first as a blanket guard, ahead of the mode split, and
broke three passing Wait-mode tests: strict mode's own reset asks the learner to re-strike a
chord tone with nothing but a wrong note in between and no Note-Off simulated (or, on real
hardware, needed) before the replay is judged again, and the loop-wrap/pause-resume tests hit the
same shape. Wait mode's matching does not promise a Note-Off has arrived before a pitch can be
struck again, so the fix is Tempo-only, where each step's slot is independently timed and closes
for good the moment it is filled — there is no path in Tempo mode that needs the same pitch
re-matched without a release. `tests/unit/engineTempo.test.ts` gained the bounce case (reverting
the guard fails it: hits 1 → 0, wrong 0 → 1) and a same-shape regression case (a genuine repeated
note, released and re-struck, is still judged twice); `tests/unit/engineMic.test.ts` gained the
mic-specific counter-case (a repeat with no Note-Off, judged twice, because the run is a
microphone one).

**2. A wrong note near a barline was blamed on the wrong bar.** Tempo mode opens a step's
matching window up to `toleranceMs` before the cursor reaches it (so playing early can still
match), but the cursor itself only advances once the clock actually gets there. A wrong note
struck in that gap — after the next bar's window has opened, before the cursor has moved into
it — was attributed to `this.step`'s measure, i.e. wherever the cursor still visually was,
rather than to the bar its own timing was actually nearest. "Loop the weak bars" (`Scoring.ts`'s
`hotSpots`) is built directly from this map, so a mistake made right at a barline could send the
learner to loop the bar *before* the one they actually fumbled. Fixed with
`PracticeEngine.measureIndexNear`, which scores every step in the run by distance to the note's
own time and returns that step's measure, instead of reading the cursor. `tests/unit/
engineTempo.test.ts` gained a case: a wrong note struck 100 ms from bar 2's own note and 3900 ms
from bar 1's, with the cursor still shown on bar 1 at the moment it is played — reverting the fix
puts the `wrongs` entry back on measure 0 instead of measure 1.

**Checked and clean.** `drills/factories.ts`, `drills/harmony.ts` and `drills/theory.ts`: every
generated interval, chord and mode is built from a root within a semitone or two of middle C
(60), so none of the shipped generators can walk off either end of the keyboard — this is by
construction rather than by a clamp, and no combination of the catalog's own parameters pushes
one out. Degenerate pools (an unparseable catalog `chords`/`targets`/`keys` list, a chord symbol
with no settled scale) all fall back to a sensible default set rather than building an empty or
broken drill — checked in `fromCatalog.ts`'s `chordsFromParams`, `buildFindKey`, `chordScaleDrill`
and `extendedChordDrill`. `steadiness.ts`, `special.ts` (pedal/dynamics/rhythm) and
`coaching.ts` were read end to end and have no falsy-zero or off-by-one shape like the chord
chart's bar-1 fault.

**Found, not fixed.** Wait mode has the same bouncing-key exposure on its *wrong*-note path
(`feedWait`, `PracticeEngine.ts` — the `wrongCount`/`retries` block) as Tempo mode's hit path did:
two Note-Ons for one bounced mis-strike are two wrongs, not one. It could not be closed the same
way — see above, Wait mode's own strict-reset flow needs a same-pitch replay with no Note-Off
in between to keep working — and closing it needs either a real elapsed-time threshold (which
this session could not size safely: a genuine hardware bounce and this test suite's convention of
feeding two Note-Ons at the same synthetic timestamp are indistinguishable by time alone) or a
change at the MIDI parsing layer (`app/src/midi/WebMidiSource.ts`, `parseMidiMessage.ts`), which
is outside this session's files. Also unclamped, and not chased because nothing in the shipped
catalog reaches it: `ChordDictationDrill`'s and the roman-numeral/secondary-dominant translation
in `theory.ts` spell every root with flats (`ROOT_NAMES`/`rootName`) regardless of the key, so a
custom drill built with sharp-key roots (a `D` or `A` major roman-numeral or chord-scale drill,
say) would show `G♭` where a reader expects `F♯` — cosmetic, and the pitches it asks for are
still correct either way, but a teacher would call the spelling wrong.

### 6a. A bug hunt in device connection and offline — eight fixed, five flagged (2026-09-11)

The brief was MIDI, the microphone's permission, the service worker, updates and the error
boundary — none of which had been looked at. Same hunt shape as 5i: **right on the data a test
uses, wrong on the device the owner has.** The MIDI half turned out to be one fault wearing five
faces, and it is first because it is the one the owner meets every time the phone moves.

Fixed, worst first by how often the owner meets it.

**1. An unplugged piano counted as connected, for the whole session.** `WebMidiSource` asked
`access.inputs` whether a device was there. The Web MIDI API does not answer that question: when
a device goes, the `MIDIPort` **stays in the map** with `state: 'disconnected'` — deliberately,
so a page can recognise the same device when it returns — and the browser closes the port.
Nothing in the file read `port.state`, although `MidiPortInfo` carries it and its comment says
what it means. So with the OTG cable out of the phone, `connected` stayed true, `inputs` still
listed the HP-130, the MIDI screen said "1 input", Today's chip said MIDI, and Wait mode sat
waiting for a note off a wire that was not there.

**Why no test saw it:** both MIDI fakes model an unplug as *deleting* the map entry
(`tests/unit/helpers/fakeMidiAccess.ts:removeInput`, `tests/e2e/fixtures/midiMock.ts`), and their
ports were hard-coded `state: 'connected'` — `readonly state = 'connected'` in the Playwright
one. The whole suite agreed with the bug. Both fakes now carry a faithful
`disconnectInput`/`unplugInput` and `reconnectInput`/`replugInput` pair, and both model the one
piece of port lifetime that matters (below). `removeInput` is kept: a port genuinely can leave.

Four things followed from the same read, and all four are fixed.

- **`inputs` and `outputs` filter on presence**, `knownInputs` is the unfiltered list for
  Diagnostics, and the status line separates "MIDI input unplugged — plug the cable back in"
  from "Connected — no MIDI inputs found". Two different problems; the cure for the first is a
  cable.
- **A key held when the cable went stayed down for ever.** The Note-Off is on the wire that has
  just been pulled, so nothing else ever sends it: the keyboard strip kept the key lit, the
  engine kept believing the note was held, and `pressedNotes` reported it for the rest of the
  session. It is released now — the same cure the CC123 path already applied to a *dropped*
  Note-Off. `pressed` carries the input id, so a second adapter being unplugged cannot drop the
  chord being held on the piano; `disconnect()` releases too.
- **The piano was silent after being plugged back in.** The device comes back as the *same*
  `MIDIPort`, so `attached` still held it and `onmidimessage` was still non-null — and the
  `continue` meant nothing re-assigned it. Assigning a non-null `onmidimessage` is the only
  thing that opens a port the browser closed, so the cable was in, the port was listed, and no
  message arrived. It re-assigns (and calls `open()`) for a present port whose `connection` is
  `closed`.
- **`send()` to a departed output threw on every note.** `MIDIOutput.send` on a port whose
  device has gone raises `InvalidStateError`, and this is called once per note of the part the
  piano is playing — a cable pulled mid-piece would have raised the error banner a few hundred
  times over the score. `resolveOutput` now skips absent ports and falls through to one that is
  there; `send` is guarded.

`tests/unit/WebMidiSource.test.ts` has seven new tests. Reverting the presence filter fails
three of them; reverting the release-and-reopen half fails three others; nothing overlaps.

**2. A dismissed microphone prompt was treated as a permanent refusal, and the Connect button
was taken away.** Chrome throws the same `NotAllowedError` whether the learner tapped **Block**

## §5ab — the freeze was in the wrong units (2026-09-11, late)

The corpus was re-run after §5aa's fit fix and Satie's Gnossienne at

`frozen` is the size a run holds to. The scale is a CSS transform on a sheet

`frozen` now carries its zoom and is dropped when the engraving moves.

### §5ab-3 — the rotation cell: the owner's ruling, and why it is still not fixed

The owner answered the question §5ab-2 left open: **after a turn the sheet may
resize, as long as turning back gives the old size again.** That unblocks the
freeze. It turned out not to be the blocker.

Instrumented `fitSlots`'s page decision and read it live across a turn. After
the turn the loop is entirely self-consistent, which is why nothing had caught
it:

| | after the turn |
| --- | --- |
| expected scale | 0.774 |
| page engraved | 442 px |
| stage | 342 px |
| ink | 444 x 145 |
| `pageIsStale` | false, 442 against 442 |
| scale applied | 0.743 |

The page is `stage.width / expected`, so a small expectation buys a wide page.
`expectedSlotScale` takes its expectation from the piece's **tallest** window —
177 px here — while this window's ink is 145, so the page came out 22 % too wide,
the ink with it, and the width-bound scale fell by the same proportion.

**Tried: make the expectation at least what the width can give.** It does
exactly what it should on this cell — expectation 0.774 to 0.965, page 442 to
354, scale 0.743 to 0.876, and turning back restores the sideways size to the
pixel. It also breaks four other cells, because **the wide page is
load-bearing**: a page near the stage width lets OSMD lay the window out and
stop, so the ink no longer *fills* the width. Satie fell to 47 %, ode-to-joy to
53 %, twinkle to 51 %, jingle-bells to 44 %, and `score.density`'s phone case
from 85 % to 76 %. Reverted.

So the two rules pull against each other. A wide page fills the width and costs
scale; a narrow page buys scale and leaves the width unfilled. Today's code
picks the first, and this cell is the case where that choice is visibly wrong
because the window is shorter than the piece's tallest.

**What a real fix looks like**, for whoever takes it: the expectation has to come
from *this window's* ink rather than the piece's worst, which means a second
pass — engrave, measure, re-engrave on a page sized from what was measured. The
`pageIsStale` machinery is already exactly that shape; what it lacks is a reason
to fire, since it compares the page against the same stale expectation that
chose it. And the owner's ruling means the second pass is now allowed to happen
after a turn even mid-run.

## §5ac — the score folder: the manifest is the index now, and every path through it (2026-09-12)

The previous pass fixed four faults in this folder and left the design itself
standing. The design was backwards, and `folderLibrary.ts` said so in its own
words: *"A manifest describes the files; the files decide what is listed."* So
pointing the app at the owner's archive walked all 37,261 directory entries to
work out what existed, and then used `library.json` — the file the archive
carries precisely so that nothing has to be worked out — only to put titles on
what the walk had found.

Three platform facts settle it:

1. `showDirectoryPicker` is in Chrome for Android from 132, and Chromium's own
   intent-to-ship thread records that **opening a very large folder makes the
   browser unresponsive**. At 37,261 files the first walk was therefore not
   merely slow; it was a documented way to wedge the phone.
2. **An installed PWA keeps File System Access permissions across sessions**
   from Chrome 122. The handle still has to be stored in IndexedDB and
   `queryPermission` still has to be called each launch, but there should be no
   repeated prompt. The app is installed as a PWA.
3. Handles stored in IndexedDB survive across sessions.

So the reversal: **`library.json` is the index; the walk is the fallback.**

### Can the manifest carry the whole listing? Yes — and here is why that is the crux

`tools/content/pdmx/manifest.py` writes each row's first field as
`f"{shard_of(cid)}/{cid}.mxl"` — a path *relative to the folder the manifest
sits in*. That is exactly the string `addFromFolder` descends
(`getDirectoryHandle('bb')`, then `getFileHandle('Qm….mxl')`) when it wants one
score's bytes. So a manifest row is a complete index entry: it names the file,
it says where the file is, and it carries everything the browse list draws —
title, composer, estimated level, bars, style, status, rating, views, lyrics,
the garbled flag and the MuseScore link.

Nothing else in the folder is needed to build the listing. Reading one 6 MB file
replaces enumerating 37,261 directory entries, and
`tests/unit/folderManifestFirst.test.ts` asserts it as *work* rather than as
outcome: the double counts every `values()` and every `getFile()`, and on the
manifest path it records **zero directory listings and one file opened**.

The one correction the read has to make is the path *prefix*. Samsung's Extract
unpacks `pianopath-library` into a folder of the same name, and the owner, told
to pick `pianopath-library`, picks the outer one; the manifest is then one level
down and its paths are one level short. The probe looks for `library.json` at
the root first, and failing that in the root's own subfolders (up to 24 of
them), and prefixes every row's path with wherever it found it. That is one
directory listing in the nested case and none in the ordinary one.

### The walk, which is what a folder with no manifest still gets

It had to survive 37,261 files without a manifest to shortcut it. Four changes:

- **It opens nothing.** The listing is built from paths now, so the second pass
  — `getFile()` on every score, a round trip each, and by the old code's own
  comments most of the wait on Android — is gone.
- **It reports in folders.** The root's directories are counted before any of
  them is entered, so "Indexing 319 of 619 folders — 12,430 scores found" is a
  real fraction from the first second. A count of files has no denominator until
  the walk is over, which is to say until nobody needs one.
- **It writes rows down as it goes.** Each top-level folder finished is a
  checkpoint: the first is saved immediately and the rest no oftener than every
  four seconds. A phone that kills the app keeps every score reached.
- **It is resumable.** The checkpoint stores the folders *not yet* reached, and
  `rescanFolder(id, { resume: true })` walks only those. Cancelling keeps what
  was found instead of throwing it away, which is what made Cancel a button
  nobody could afford to press.

### The seven situations, end to end

| When | What the owner sees | What he does | What it costs |
| --- | --- | --- | --- |
| **First run**, archive with `library.json` | "Pick a folder", then the listing | pick the folder once; Allow | one file read and a parse — no enumeration at all |
| **Every later run** | the listing, "folder open" | nothing | one `queryPermission` — no prompt, no files |
| **After a phone restart** | the listing, "folder open" | nothing | the handle comes back out of IndexedDB; one `queryPermission` |
| **Permission lapses** | "Chrome did not allow it — try again and tap Allow", with **Open folder** | one tap and Allow | one permission call. Nothing is re-read |
| **Folder moved, card out** | "Folder moved or gone — pick it again" | pick the folder again | a fresh read — instant again if the manifest is with it |
| **The archive changes** | nothing, until he looks for the new score | **Rescan folder**, in the fold under *How this works* | the full walk: minutes, resumable, cancellable |
| **A listed file has gone** | under the row he tapped: "… is in the listing but not in the folder any more. It has been taken off the list." | nothing, or Rescan if more has changed | one failed lookup. The row leaves the listing and the screen |

Written out:

**First run.** `Library → Score folder → Pick a folder`, choose
`pianopath-library`, allow. The probe finds `library.json`, reads it, and the
browse list is there. No progress bar worth watching, because there is nothing
to watch. With *Remember the score folder* on, the handle is stored beside the
listing.

**Every later run, and after a restart.** The screen loads the listing out of
IndexedDB and calls `queryPermission` after the first paint — free, needs no
gesture, reads no files. An installed PWA should answer `granted`, and the top
line says "37,261 scores in pianopath-library from PDMX — folder open." Adding a
piece is one file.

**When permission has lapsed** — or the PWA was not installed when the folder
was picked — `queryPermission` answers `prompt`. That is not a refusal and is
not reported as one: the notice above the list says the folder is not open and
offers **Open it**, which asks Chrome once. Nothing is re-read either way; that
was the first of the four faults the previous pass fixed, and it still holds.

**When the handle no longer resolves** — folder moved or renamed, card out,
permission revoked in Chrome's own settings — the liveness probe throws, the
notice says "Folder moved or gone — pick it again", and the picker is the only
way back. With the manifest there, picking again is as cheap as the first time.

**When the archive changes.** This is the trade manifest-first makes, and it is
stated on the screen rather than left to be discovered. A score copied into the
folder after `library.json` was written is **not in the listing**, and the app
cannot know: it never looks. So on a manifest-listed folder the fold is labelled
"How this works, and what it misses", and the note inside says it in full and
names **Rescan folder** as the only cure. Rescan walks the folder with the
manifest beside it, so the archive's own scores keep their titles and the new
one is listed under its filename. Regenerating the manifest — re-run
`manifest.py`, copy it over — is the cheaper route and stays instant.

**When a listed file has gone.** The manifest cannot know this either, and the
only thing that ever looks is `Add`. So the discovery is kept rather than spent
on one error message: the row is removed from the stored listing, it disappears
from the list where it was tapped, and the sentence that takes its place offers
**Rescan folder** for the case where more of the folder has changed. There is
nothing left to tap twice, and the next launch does not offer it again.

**When indexing is interrupted** — Cancel, or the phone killing the app during a

## §5ae — the drill screen and the score screen disagree about what a stop is (2026-09-12)

`08` §16 is explicit for the score screen: **"A stop is not a finish: no summary,
nothing recorded."** The drill screen does the opposite and nothing says it may.

`End drill` calls the same `finish()` that a completed set calls. So abandoning a
ten-card chord drill after one chord writes a run to the practice history with
the accuracy of the one card, `missed: 9`, and `passed: false` — a failure the
learner never attempted, in the one record `DrillScreen`'s own comment calls the
thing that "cannot be regenerated". Every drill kind has a natural ending:
`advance()` calls `finish()` when `next()` runs out, and the four manual-advance
kinds get a `Done` / `Next` button that calls `advance()`. So `End drill` is
never the only way to complete a set.

**Why this is the owner's call and not a fix I took.** `End drill` is overloaded
and the code cannot tell the two meanings apart: over a set you have worked
through it reads as "I am done", and over one you have barely started it reads as
"get me out of here". Two existing tests use `#drill-end` as the quick way to
reach the summary — including "the backing-track drill loops and judges nothing",
where it stands in for completing the single card — so changing what it records
changes what those tests mean, not just whether they pass. And `docs/05` §7's
table settles only *scoring* (`backing-track`: "none (records)"), not recording.

**Paper practice already answers it, and answers it better than either of the
other two.** `PaperScreen.stop()` draws the summary and records *nothing*: the
report buttons underneath it call `save()`, so what the app heard is always shown
and what goes into the history is a thing the learner chose. Three screens, three
behaviours — score records nothing and shows nothing, paper shows everything and
records on request, drill shows and records unasked — and only the drill's is
undocumented.

Three answers, in the order I would rank them:

1. **Do what Paper does.** `End drill` draws the summary and records nothing; a
   button under it ("Count this", or the self-report Paper uses) writes the run.
   The learner keeps the numbers for the cards they did and the history keeps
   only attempts they meant. It needs no new rule, because the rule is on the
   screen next door.
2. **Follow `08` §16 literally.** `End drill` stops: no record, and a status line
   saying the set was ended and nothing kept, so it does not vanish silently.
   Simpler, and it throws away a summary worth reading.
3. **Leave it and write the rule down**, if a partial set is worth recording
   unasked — but then `08` §16 needs the exception beside it, because three
   screens reading the same gesture three ways is what makes any of the rules
   useless as a guide.

**Taken (2026-09-12): answer 1.** `End drill` draws the summary and records
nothing; a `Count this set` button under it writes the run, and a line beside
it says the set is not in the history unless you keep it. A set that runs to
its end still records itself — finishing it is the choosing. Neither test that
used `#drill-end` as a shortcut needed moving: one only reads the summary and
the other only presses `Again`, and the test that asserts a recorded run plays
all ten cards.

One thing the tests found on the way: leaving the screen discards an un-kept
set, because the summary and its button go with the screen. That is the right
behaviour — you left without keeping it — but it means `Count this set` has to
be pressed before navigating away, which is why the line saying so is beside
the button rather than in the status line.

### And on the lesson page, two buttons that now do the same thing

`I already know this` and `Mark done` both loop `idsToCompleteLesson` calling
`selfPass`, so they always wrote the same progress rows. They used to differ in
one way that mattered: the first also marked the lesson's concepts `known`.

The `markLessonLearnt` fix (commit "the review screen was empty for anyone who
actually practised") closed that gap without meaning to. `Mark done` self-passes
every option, the next `draw()` finds the lesson complete, and
`markLessonLearnt` marks the concepts — so the two buttons now reach the same end
state. What is left between them is a confirmation dialog on `Mark done` and none
on `I already know this`, and a `lastReviewedAt` that the latter refreshes
because it calls `markSkill` unconditionally.

So the *less* guarded button is the one with the extra side effect, which is
backwards, and two controls on one row lead to one place. Worth one of:

- keep both labels, because "I knew this already" and "I have done this now" are
  different sentences to a person, and give them the same guard; or
- keep one, and let the status line say which sense it was.

Not taken here: it is a two-button question on a screen the owner reads often,
and the convergence is three days old at most.

## §5af — the arrangement race, attempted and measured (2026-09-12)

Third pass at it, this time with the fit instrumented and every count forced and
measured. It is still not fixed, but the map is now complete enough that the next
attempt need not rediscover any of this.

### What every count actually draws

Forced `chooseSlotCount` to 2, 3 and 4 in turn and measured the owner's geometry,
342 x 740, mid-run: height used, ink width as a share of the stage, and the drawn
stave in pixels.

| piece | 2 slots | 3 slots | 4 slots |
|---|---|---|---|
| hot-cross-buns | h47 w94 staff140 | h74 w94 staff140 | h75 w95 staff98 |
| twinkle.ht | h91 w103 staff153 | h87 w76 staff89 | h95 w88 staff73 |
| happy-birthday | h56 w96 staff98 | h89 w96 staff97 | h82 w96 staff65 |
| jingle-bells | h77 w83 staff139 | h90 w82 staff102 | h91 w83 staff73 |
| greensleeves.68 | h50 w86 staff79 | h88 w104 staff90 | h84 w96 staff60 |
| ode-to-joy | h91 w96 staff153 | h86 w76 staff89 | h96 w91 staff74 |
| petzold minuet | h48 w55 staff86 | h79 w90 staff95 | h75 w78 staff62 |
| **satie gnossienne** | **h66 w103 staff117** | h67 w93 staff58 | **h70 w55 staff39** |
| chopin scherzo | h72 w89 staff110 | capped at 2 | capped at 2 |

Two things fall straight out. Two slots wastes half the height on the beginner
pieces — 47 %, 48 %, 50 %, 56 % — which is the fault. And **Satie gains nothing
from more systems**: 66 → 67 → 70 % of the height, for a stave that falls from
117 px to 39. Its systems are tall, so the extra slots shrink everything without
fitting more music. The owner's rule as the code states it — the largest count
whose stave clears `MIN_STAFF_PX` — assumes more systems means more music, and
for this piece that is false.

A long piece is capped at two slots regardless: `sourceMeasureCount >
PROBE_MAX_BARS` gives the renderer two buffers, not four. That is why the Scherzo
never moves.

### Why the cheap fixes do not work, each one ruled out by measurement

1. **Make the freeze wait for the measurement** (the obvious fix; it does turn
   `score.arrange-race.spec` green). Beginner pieces go to 3 or 4 slots and 64–86 %
   of the height. Satie goes to four and 53 % of the width, which `score.fill`
   rejects, correctly.
2. **Apply `MIN_STAFF_PX` to the stave that was actually drawn** rather than to a
   prediction. The prediction is the probe's stave times the fit's scale, and it
   is 25 % optimistic — 49 px predicted against 39 drawn — because the engraver
   sizes a system to the page it is laid on and a slot's page comes from the
   arrangement. Implemented; it does not fire, because on the natural path the
   stave measures 43 px, over the floor. Only the forced-count run reaches 39.
3. **Apply `score.fill`'s width floor to the drawn ink.** Implemented, and the
   measurement is wrong at the moment it is taken: a slot's box is the *page*,
   which the fit makes fill the stage by construction, so it reads 96 % on a
   system whose notes cover 53 % of the glass. Measuring `inkBox` instead reads
   102 % — the ink runs past the page edge — because at that instant the slot is
   still engraved on the *previous* count's page.

### The actual blocker, stated precisely

The honest ink measurement exists only after the slot has been re-engraved for
the new count, and **no fit happens between that re-engrave and the freeze**.
The instrumented sequence on Satie, every entry at step 0: seven fits at two
slots, then one fit that changes the count to four while still measuring the
two-slot engraving, then the freeze. The re-engrave that follows is never
measured before the arrangement is locked.

So the fix needs one more fit, after the re-engrave and before the freeze, whose
result can lower the count. That is a loop in `fitSlots`, which is the most
fragile code in the app, and it wants doing deliberately rather than at the end
of a long session. Everything above is the evidence it needs.

`score.arrange-race.spec.ts` stays `fixme` and now has this section to point at.

## §5ag The generator, read twice — 2026-09-13

The owner asked for a complete examination of `generate_exercises.py`, its

### First pass: read every maker, print what it engraves

Thirty-nine makers and about thirty tables, by printing the pitches, fingerings,
chord symbols and bar lengths each one produces and reading them. Everything
here shipped.

- **Left-hand fingering that was a right hand.** Every two-octave left-hand
  scale in C, G, D, A, E, B and F major and seven harmonic minors printed the
  fifth finger on the middle tonic — 150 chords. One octave-join rule was used

  octave group, the left thumb *ends* one. The seven flat keys hid it, because
  their tables begin and end on the same finger, so it was invisible in exactly
  the keys a beginner plays. Broken sevenths put 5 on the seventh and 1 on the
  octave above it. Octave tremolos fingered the left hand as a right hand.
  Descending double thirds and sixths kept cycling the ascending table, so the
  hand was told to move down the keyboard and up through its own fingers.
- **Symbols that lied.** The comping and turnaround intro tiers printed Dm7, G7
  and Cmaj7 over plain triads, at the level that teaches what a chord symbol
  means. Stride printed a dominant over a triad in every bar of every key.

  D6. The ii-V-I shells tier ran 32 quarters in the left hand against 16 in the

Reading makers again would have found the same things. These are questions no
single maker can answer, asked of all 1,012 items together.

- **44 items asked for keys that are not on a piano** — every run started at
  `tonic4` whatever its span, and G4 plus four octaves is G8. 206 notes above

## §5ah The read-ahead, re-priced; the race, closed; the bar over the stage — 2026-09-14

The tree was found with an uncommitted half-edit in `WindowRenderer.ts` that failed
the typecheck, the lint and one unit test, and CI red on the last commit: three
rotation cases and the control-bar test. The half-edit is saved as a patch in the
session scratchpad and was not kept; what it was reaching for is done properly below.

**What the last commit cost.** "Keep the next bar on the glass" was right about the
fault — Hot Cross Buns sideways ran its bar of eight quavers off the right edge — and
priced the cure at a *quarter of the bar*, to the right of the one-third slide target.
On that piece the cap took the sheet to 55 % of the height sideways, and the rotation
verdicts (which ask for 70 %) said so on CI. Looked at on the phone's 740 x 342, the
sheet was a third black below the staff. Two things were wrong with the price:
the eye needs the next *note*, which is a fixed size on the staff and not a share of
the bar it starts; and `SLIDE_TARGET_MIN` (a quarter) was exported, asserted by the
sequence, and read by nothing — a bar that needs the room can start there. Now:
`readAheadScale` prices the peek at half a staff (`NEXT_NOTE_PEEK_STAVES`) right of
the quarter, and `slideToStep` puts a bar's first note at the third unless that
leaves the next bar's first note off the glass, in which case it moves left as far
as the quarter. Hot Cross Buns on the phone sideways: 65 % of the height with the
next note always on, against 55 % before and 82 % with no read-ahead at all. The
stage now records which term decided in `data-fit`, and the rotation verdict
accepts a sheet under 70 % only when that says `read-ahead` and the stave is over
the 40 px floor. The control-bar test asserted the opposite of decision 5 whenever
the music stopped short of the bar — a branch nothing had taken until the cap made
it the ordinary case — and now asserts decision 5 outright.

**The bar sat 16 px over the stage at rest.** `--strip-height` was set on the strip
and read by the bar and the stage from the screen, so the bar floated at the default
72 px over a 56 px strip: a gap under the bar and 16 px of stage behind it, and at
rest the fit fills the stage, so Twinkle's ledger-line C4s were drawn under the
controls. The ribbon had the same fault at 40 px. The variable is on the host now.

**The arrangement race (§5af), closed.** The freeze waits for the piece's
measurement — bounded by `FREEZE_WAIT_FOR_MEASURE_MS`, asked for directly rather
than left to idle, shared with the idle path through one memoised load — and a
pending freeze pins the count only once a note has been played. The blocker §5af
named was Satie: the predicted stave passed the floor and the drawn one did not, at
half the width. So after each re-engrave the fit measures the drawn stave
(`staffHeightOf`) and the width the piece uses at that scale, and either under its
floor (`MIN_STAFF_PX`, `SLOT_WIDTH_FLOOR`) lowers the count by one and remembers it
for that zoom and stage width. `score.arrange-race.spec.ts` runs; the `fixme` is
gone.

**Also found, not fixed.** At rest — no run — the probe's measurement can take
seconds to land after a change of bars per window, and the sheet is drawn at the
first chunk's fit until it does, then shrinks. The run path no longer depends on it;
the at-rest picture still does.

   "arpeggios hands separately, two octaves, in C, G, F, A minor, D minor and E

   `arpeggio_level` has a hands-separate branch (4.3) that no call ever takes, so

   nothing caught it.

   in the left hand**; it is not on the rung or in the library (10/3, 25/1 and

   fingering.** `ARPEGGIO_FINGERING_RH = [1, 2, 3, 5]` is commented "white-key
   roots" and is applied to A♭, B♭, D♭, E♭, G♭ major, B♭/C♯/E♭/F♯/G♯ minor, and
   every seventh arpeggio on a black root, including the diminished sevenths on
   C♯ and G♯. The thumb lands on the black key in every one. `confirm_fingering`
   cannot see it — a melodic line is not a chord — and `fingeringVerified` is not
   set false on these the way `make_blues_scale` does when it declines to guess.
   Standard practice (and the scale tables' own rule, "the thumb avoids black
   keys") puts 2 or 3 on the black root and the thumb on the first white chord
   tone.

    the bar.** `make_walking_bass` fingers root–third–fifth–approach as

    C2 E2 G2 then B1, F2 A2 C3 then B1. Finger 1 on a note below finger 2 is a
    left hand crossing itself. Sixteen items, on the rungs that introduce the
    line.

    fingering.** `chromatic_finger` puts 2 on F and C (the white after a white,
    ascending) and the docstring says "both hands use this shape". The left hand
    ascending takes 2 on E and B — the white *before* — because its thumb is the
    upper finger; E1–F2 going up is the second finger crossing the thumb by a
    semitone. Twelve items with a left hand. The scale tables were verified
    against Clementi; the chromatic was "a deliberate departure" and never
    verified against anything.
12. **Two imported scores ask for keys the piano does not have** and the
    importer lets them through where the generator refuses: `mariage-damour.alt2`
    (D8) and `bach-toccata-fugue-bwv565` (G♯0). `validate.py` prints the note
    and passes.

### C. Mechanics that undercut learning

- **The chord-chart rungs list songs with no chord symbols.** `chords-pop.4`
  says so itself ("written out in both hands with no symbols: play them as
  printed, then name the chord"), which is a fair exercise, but four of ten
  options on a rung about reading symbols do not have any.
- **Every technique rung is 12 exercises and 0 songs**; every improv and theory
  rung 0 songs. Intended (song-optional), fine, but `technique.4`'s concept list
  is fourteen tags, which is what the Plan screen shows.
- **`4.6` and `4.7` both require Performance/Blind at 90 %** with the same three
  pieces; the two rungs are nearly the same assignment twice.
- **The tumbao's beat-4 note ends at the barline.** The docstring says the
  anticipated chord "stays through the barline"; the note is one quarter long and
  the next bar opens with a rest. Tie it.
- **The montuno plays exactly the clave.** A guajeo is an eighth-note figure
  locked to the clave, not the five clave strokes themselves; what ships is a
  clave in chords. Defensible as "two notes at a time", but it is the only latin
  right-hand material there is.
- **Mastery criteria are per-rung strings nobody evaluates**
  (`custom: 'chord-drill-20-changes>=0.95'` and 24 others); the generic
  accuracy/tempo rule is what actually decides. Either wire them or stop
  printing them in the plan.

- **Lesson `unit:` ids use three conventions** (`4.6`, `blues-boogie.4.1`,

- **`tips/find-key.build-scale.md` sends the learner to build C flat major**,

## §5aj — The night after: notes lost on import, the archive's duplicate flag, and the rule that made dumps (2026-09-15)

Three things happened between §5ai's batch and its commit, and they are all in the
same commit because they touch the same files.

**The mazurka was not a flake.** The Op. 56 No. 1 render failure on the CI runner was
traced to its source: music21's Humdrum importer cannot follow a spine split inside a
split, or some merges, and drops the notes it loses track of. The mazurka had lost over
half of its notes and one other piece more than that, and every check the pipeline runs
— the render check, the step-parity check, the validator — passed them, because none of
them counts notes against the source. The production build alone threw, and only
because the minified score loader handles the resulting shape differently. **53 of the
first editions are excluded** in `content/sources/kern.json`, each with the reason in
the row; six were replaced by the same work from the PDMX archive (two preludes, a
nocturne, an étude, a rag, the Op. 28 No. 1 prelude) and the classical rungs at Stages
6–9 and their lessons re-counted. The three specs that used the Op. 27 No. 1 nocturne as
their dense case use Op. 48 No. 1 now, which opens on octaves and is denser, so each is
asked the same question. Twenty-six pieces with losses under one percent are still on
rungs. **The gate is the next piece of work**: count the notes in the source and in the
converted score, refuse above a threshold, report the rest — and run it over the
MuseTrainer and PDMX imports, which nobody has checked either. The production-only
crash is a second, unexplained bug that removing the piece hides; a file the owner
imports himself could reach it.

**PDMX's `subset:deduplicated` was a gate and it was the wrong one.** It rejected more
rows than every other gate together. The dataset built it for training generative
models: titles are clustered by embedding similarity, arrangements within a few percent
of each other's note count are one arrangement, and the cluster keeps its highest raw
rating. For repertoire every step is wrong — formulaic titles cluster across works, a
different composer's rag was "the same" rag, and one five-star vote beat thousands of
ratings, which is how Bach's C major prelude, Maple Leaf Rag, K. 545 and the first
Ballade were all rejected. `shortlist.py` carries the flag as a label now and chooses
editions itself: `work_key` names the piece (composer, genre, catalogue numbers,
movement; the whole title when there are no numbers) and `best_editions` keeps one
upload per work per band, wants and references first, then our own ranking, ties to the
lower CID. `index.py` applies the same rule so the index does not carry every upload of
Für Elise. The tempo gate's ceiling is 320: it exists for garbage tempos, and at 220 it
had rejected a boogie, a swing tune and the Presto prelude. **Not yet run on the real
archive** beyond a dry index in `build/pdmx-dedup/`; the yield before and after, and a
review of what it newly admits, are the second piece of work, after the note gate
exists so the intake is checked on the way in.

**The rule that made dumps.** §5ai added "no song may sit on no rung" and placed 255
songs by feature rules to satisfy it. That was the wrong instrument: it turned rungs
into lists — 704 song slots over 86 rungs, the big classical rungs offering thirty to
seventy pieces — when a learner at a rung needs a handful of pieces that are right. The
rule is withdrawn; the reach rule stays. The placements stand until the rungs are
reshaped, which is the third piece of work and starts from the plan, not the build: per
rung, generated exercises plus a few verified pieces, with "more at this level" a link
into the Library, which already filters by track and level. The shelf-style rungs
(holiday, hymns, the classical shelf) are lists by nature and stay so. `docs/02` has
drifted from the build through all of this and is updated first, so rungs and lessons
follow from it.

**Also in this commit.** Two concepts added to the technique ladder's stage lists
(two-hand independence at Stage 5, melody in octaves at Stage 7); the tumbao tests
count attacks rather than tie continuations, which the barline tie in §5ai's generator
change required.

Classical in the Library"); classical.5's sonatina and pedal paragraphs were rewritten
because they named pieces that had left. Two pieces had lost more than a third of their notes on

**The gate, and what it found.** `convert_file` now counts note events on both sides
(`docs/03` §3b): the source from its own bytes, the output from the normalised score, chord
symbols excluded; a loss over two percent is a refusal with both counts in the sentence, a
smaller one a warning. Building it found the second mechanism's cause: `collapse_to_two`
asked a part for the offset of a note that lived inside one of its measures, which raises,
and the `except` around it swallowed every raise — so every note of every third part
vanished under a warning that said "merged". The merge is rewritten to match bars by offset
and give each strand its own voice, and the (offset, pitch) multiset is identical before and
after on both broken files. The full no-cache rebuild through the gate changed the catalog

own measurement. Also open: the hand exclusions in `kern.json` could now be derived by the
gate rather than maintained.

**The export refusals.** The quarry rerun's best classical admissions were failing at
`write_mxl`, and the three messages (a "2048th", "inexpressible durations", `KeyError:
'5'`) turned out to be one fault seen from three sides: an editor writes each note of an
irregular tuplet as the nearest whole tick, the run comes out a tick or two long, `makeTies`
ties the overhang across the barline, and the sliver left over has no note value. `normalise`
now runs `settle_durations` (`docs/03` §3c): each note is taken at its printed word — value,

Ballade, bars of five and six quarters in Glinka's *Lark* — which `makeTies` splits at the
notional barline. A hidden time signature of the bar's real length was prototyped and buys

practice engine and the metronome read, so it is not shipped; those files are refused with a
sentence that names the bar. Three more never reach the writer at all (a `'7/5'` in an
integer field, a `'?'` pitch step, a duplicated measure) and stay parser faults.

## §5al — The tour looked at, and the instants counted (2026-09-15, evening)

**The tour.** Run once on the built app after the reshaped curriculum and the twenty-five
admissions, all four form factors, and read against the guidance in `tour-review`: the
score screen was driven bar by bar, both ways up, on a single-staff tune and a
grand-staff one. Nothing on it is wrong. The cursor lands on the right note, the played
notes go green and the wrong note is named, the next bar is on the glass before the
current one ends, the fingering and chord symbols draw where they should, the strip
tracks the hand. Three things worth the owner's eye rather than a fix:

- **A single-staff piece sits small.** Sideways, Suo Gan's stave takes a third of the
  stage height with the rest empty; upright, four one-bar systems leave the bottom
  quarter empty. The width rule that keeps the next bar's first note on the glass caps
  the scale, and a fifth system would fit upright. Grand-staff pieces fill the stage.
  Whether a lullaby should be one big bar and a peek, or four small ones, is a matter
  of taste and is left as it is.
- **The two-slot carousel reads bottom-then-top half the time.** On entering bar 2 the
  top slot is already bar 3, so the eye reads the current bar below the next one. This
  is the design from §5ag ("keep the next bar on the glass") working as intended, and
  it is what a page-turner does; it is noted because a first look finds it odd.
- **The bar counter chip** at the top right of the stage sits over the last fingering
  of the first system on an upright phone. Cosmetic; unchanged.

The audit's tap-target rows for the R and L hand segments are the segmented control
`ScoreScreen` already explains (one 92 x 40 control, not three targets); the owner's
word on 2026-09-15 was that sizes are fine as long as they are pressable, and they are.
The clipped folder-row meta and the alphabet rail's letters are by design.

**The instants.** A library-wide comparison of (offset, pitch) instants between the
parsed source and the conversion found 54 of 581 imported scores with notes present but
at other instants, always the same count moved as new. Traced on *Cleopha*: a 2/4 bar
whose last eighth is written after a mid-bar double barline as the pickup to the next
strain. Nothing in `normalise` pads it; **music21's MusicXML exporter does**, with a
`makeRests` on every measure before it writes, so the 1.5-quarter bar and the half-bar
after it both became full bars and everything after them moved by two quarters. The
cure (`docs/03` §3d) declares the partial bars as partial — the same `paddingLeft` and
`paddingRight` an opening anacrusis already uses — so the writer leaves them alone, and
drops the empty seam bar the parser makes when the double bar falls exactly on a
barline. Twenty-one of the 54 are exact now, every flagged Joplin among them; two are
much improved; eight were never wrong, only displaced by a tick of §3c's rounding,
which is why the comparison should read the size of a displacement, not the count. The
23 that still shift are the ragged-bar family — a bar longer in one staff than the
other, or than its time signature, in the source itself: two PDMX files whose XML
contradicts itself, and the Chopin editions with written-out cadenzas. Refusing them is
a catalogue decision (it costs several good Chopin pieces) and is left open, as is
padding the short staff instead. Found on the way: music21's Humdrum parser leaves a
